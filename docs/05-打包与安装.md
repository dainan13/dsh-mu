# 05 · 打包与安装（apk）

本文档说明如何把 dsh-mu 打成 Alpine 包、装上机器、升级与卸载，以及包内**故意不含**什么。

## 1. 构建

```sh
# 在任意有 abuild 的 Alpine 上（推荐；产出带签名的现代 .apk）
apk add abuild
sh packaging/make-apk.sh --version 0.1.0
# -> dist/dsh-mu-0.1.0-r0.apk

# 可选参数
sh packaging/make-apk.sh -o /tmp/out --version 0.2.0
sh packaging/make-apk.sh --legacy-v2      # 手写容器，不签名，仅老 apk-tools 2.x 需要
```

`make-apk.sh` 的内部：

1. **首选 `abuild`**（`packaging/APKBUILD`，`abuild -F -q -P <tmp> rootpkg`）：
   缺签名密钥时自动 `abuild-keygen -a -n`，并把 `PACKAGER_PRIVKEY` 写进 `~/.abuild/abuild.conf`；
   生成公钥会复制到 `/etc/apk/keys/`，于是本机可以不带 `--allow-untrusted` 安装；
   产物拷到 `dist/`。
2. **没有 abuild** 时退回手写打包器：gzip tar + `.PKGINFO` + 每个动作一个脚本成员
   （`.pre-install`/`.post-install`/…），**不签名**，安装时必须 `--allow-untrusted`。

> **Alpine 3.22+ 的坑（已踩过并记录）**：apk-tools 3.0.6 **不再接受**携带单个 `.INSTALL` 成员的
> v2 包，报 `v2 package format error`。脚本必须像 abuild 那样作为**独立成员**（`.pre-install` 等）存放。
> 另外 `tar --format=posix` 在 BusyBox tar 上不存在——手写路径只用可移植选项。

## 2. 包内容（`apk info -L dsh-mu`）

```
/usr/local/sbin/dsh-muctl              控制面 CLI（14 行 shim）
/usr/local/sbin/dsh-mu-jail            实例 jail 启动器
/usr/local/sbin/dsh-mu-cgroup-init     cgroup 委派初始化
/usr/local/sbin/dsh-mud                管理后端（回环 JSON API + 管理页面）
/usr/local/lib/dsh-mu/python/dshmuctl.py   控制面库（CLI 与后端共用）
/usr/local/lib/dsh-mu/lua/*.lua        网关 Lua（登录/会话/代理/API/管理门禁）
/usr/local/lib/dsh-mu/nginx/dsh-mu-*.conf  网关片段模板
/usr/local/lib/dsh-mu/admin/index.html 管理页面
/usr/local/lib/dsh-mu/tests/*          自检与验收脚本
/usr/share/doc/dsh-mu/README.md
```

**包里故意没有**：

| 不含 | 原因 |
|---|---|
| jail 模板（~140 MB Alpine rootfs） | 首次 `dsh-muctl install` 时按 `ALPINE_MIRROR`/`ALPINE_TEMPLATE_PACKAGES` 在本机构建 |
| `/etc/dsh-mu/*`（配置、密钥、令牌、provider 目录） | 首次 install 生成，权限随机器而定；卸载时**保留** |
| `/etc/init.d/dsh-mu-*`、`/etc/nginx/{conf.d,http.d}/dsh-mu-*.conf` | 由 `dsh-muctl install` 按本机配置渲染（监听端口、server_name、cgroup 路径） |
| `/var/lib/dsh-mu`、`/var/log/dsh-mu` | 运行时数据与日志，卸载时**保留** |

依赖：`python3 nodejs npm pnpm openresty util-linux logrotate lua-resty-string lua-resty-hmac lua-resty-openssl`
（`apk add` 会自动装；`openresty`/`pnpm` 在 community 仓库，先确保 `/etc/apk/repositories` 里有 community，
`dsh-muctl doctor` 会检查这一点）。

## 3. 安装

```sh
# 有签名密钥（make-apk.sh 已把公钥放进 /etc/apk/keys）
apk add ./dsh-mu-0.1.0-r0.apk
# 否则
apk add --allow-untrusted ./dsh-mu-0.1.0-r0.apk

dsh-muctl doctor        # 先看这台机器缺什么（30+ 项）
dsh-muctl install       # 装依赖、全局装 DSH、构建模板、装网关片段、起服务、维护管理员记录
```

`post-install` 会打印上面这三步。`install` 结束时打印一行 doctor 摘要，并在管理员**系统账号还没设口令**时
明确提示（管理员 = 宿主系统账号，默认 `root`）：

```sh
passwd root             # 然后用 root + 这个系统口令登录 /admin/
```

## 4. 升级

```sh
apk add ./dsh-mu-<新版本>.apk     # apk 覆盖文件，执行 pre-upgrade/post-upgrade
dsh-muctl install                 # 重渲染服务与 nginx 片段、补齐新依赖
```

- 老版本已装过同一个包名时，apk 走 **upgrade 路径**（实测：`pre-upgrade`/`post-upgrade` 被执行）。
- `state.json` 的 schema 迁移是**惰性**的：任何 `dsh-muctl` 命令读 state 时按需升级并回写。
- `post-upgrade` 提示重跑 `dsh-muctl install`；实例的 jail 模板不会因为升级而重建（除非 `--force-template`）。

### 4.1 从 0.7.x 之前的版本升到 0.8.x（运行时就位）

0.8.x 起 DSH 运行时（DSH + node/npm）放在**网关模板**里，宿主机不再需要 node。已有实例升级后：

```sh
apk add --allow-untrusted ./dsh-mu-0.8.1-r0.apk
dsh-muctl install            # 模板装运行时；渲染 jail 配置
dsh-muctl sync               # 重写每个实例的 .conf（含 KEEP_CAPS / DSH_RUNTIME_IN_JAIL）
dsh-muctl instance restart <name>   # 每个实例都重启一次，让新 runner 生效
dsh-muctl doctor             # 期望 38 PASS, 0 WARN, 0 FAIL
```

- 新装的 cgroup2 未挂载的机器：`dsh-muctl doctor --fix` 会自动挂载（`install` 也会）。
- 若之前手工设过 `instance_keep_caps`，0.8.x 的默认值已是 `sys_admin,setuid,setgid`（bwrap 需要）。

## 5. 卸载与数据保留

```sh
apk del dsh-mu
```

- `pre-deinstall`：停 `dsh-mud`、停所有 `dsh-mu-<实例>` 服务，把它们从 runlevel 摘掉；
  **`dsh-mu-cgroup` 保留注册**（重装后开机委派不能丢）。
- `post-deinstall`：打印"什么被保留了"以及彻底清除的命令。
- 实测（dsh-mu 上真机执行）：卸载前后
  `/etc/dsh-mu/state.json`、`/etc/dsh-mu/dsh-mu.conf`、`/var/lib/dsh-mu/templates/alpine/bin/sh`
  的 md5 **完全一致**，`/var/log/dsh-mu/audit.log` 行数不变，`/etc/dsh-mu/` 下账号与密钥仍在。

重装后让平台回到"记录的期望状态"：

```sh
dsh-muctl install        # 会重新拉起 state 里记为 running 的实例（reconcile）
dsh-muctl doctor --fix   # 或一条命令：gateway 片段 + sync + cgroup + 拉起实例
```

实测：卸载把 alice/bob 停掉后，`doctor --fix` 报告
`starting instance alice (recorded as running but its port is closed)` 并拉起两者，
随后 `doctor: 31 PASS, 0 WARN, 0 FAIL`、selftest `ALL CHECKS PASSED`、acceptance `PASS=23 FAIL=0`。

## 6. 在干净 Alpine 上从零安装（验收清单）

1. 干净 Alpine 3.2x（LXC 或裸机）能联网，`/etc/apk/repositories` 含 main + community；
2. `apk add --allow-untrusted dsh-mu-<ver>.apk`（或先 `apk add abuild`，用 `make-apk.sh` 现场构建）；
3. `dsh-muctl doctor` → 期望 0 FAIL（WARN 逐条看修复建议）；
4. `dsh-muctl install` → 打印一行 doctor 摘要；若管理员系统账号还没口令会明确提示：
   `passwd root`（**管理员 = 宿主系统账号**，默认 `root`；平台账号一律普通用户）；
5. 浏览器打开 `http://<host>/` → 登录页 → 用**系统账号 + 系统口令**登录 `/admin/`；
6. 在 `/admin/` 建用户（可选自动建实例）、到「模型接入」设 key、测试连通性；
7. `dsh-muctl sync-state`、`dsh-muctl doctor`、`dsh-muctl selftest --user <u> --password <p>`、
   `dsh-muctl acceptance`（等价 `sh /usr/local/lib/dsh-mu/tests/acceptance.sh <inst> <user> <pass>`）
   全部通过；
8. `apk del dsh-mu` 再 `apk add` + `dsh-muctl install`，确认账号与实例数据仍在。

### 包生命周期（升级 / 卸载 / 重装）

`tests/fresh-rehearsal.sh --apk a.apk --apk2 b.apk`（b 是**更高版本**的同一份源码）会在全新 rootfs 里：
`apk add a` → `dsh-muctl install` → `apk add b`（必须走 `Replacing`/`Upgrading` 并执行 `pre/post-upgrade`）
→ `apk del dsh-mu`（校验 `/etc/dsh-mu/state.json` 与 `secret.key` 逐字节保留）→ `apk add b` + `dsh-muctl install`
（校验 CLI 与记录都回来了）。同版本重装时 apk 视为"已满足"，是干净的 no-op。

> `make-apk.sh` 现在给 abuild 传 `-f`：否则 abuild 可能把"另一个版本"的既有构建判为最新，交回旧包。

### 不需要清空机器的排练

```sh
sh tests/fresh-rehearsal.sh --clean        # 在 chroot 里搭全新 Alpine 并跑完整安装路径
```

用 `apk --root` 现搭干净 rootfs → 绑定 `/proc /sys /dev` → 拷入 checkout → 跑 `install/install.sh`
→ 检查首次配置产物、jail 模板、网关片段与 `nginx -t`、`doctor`、`bootstrap`。
chroot 无 init 且共享网络，因此服务启动/端到端仍由下面的 `fresh-machine.py` 在真机覆盖。
实测 `PASS=17 FAIL=0`；它发现过"先跑 doctor 会让 install 跳过 `secret.key`"这类只在干净机器上出现的 bug。

### 一键版本

```sh
# 平台已装好的机器
python3 /usr/local/lib/dsh-mu/tests/fresh-machine.py --skip-install

# 全新机器（没有 /etc/dsh-mu/state.json 时会自己跑 dsh-muctl install）
python3 /usr/local/lib/dsh-mu/tests/fresh-machine.py

# 只验管理员面（纯 admin 账号，无实例）
python3 /usr/local/lib/dsh-mu/tests/fresh-machine.py --skip-install --user ops --password '…'

# 机器可读
python3 /usr/local/lib/dsh-mu/tests/fresh-machine.py --json
```

脚本行为：不带 `--user` 时自动创建 `smoke` 账号与其实例（随机密码），验证完**自动停止并删除**
（`--keep` 可保留并打印密码）；带 `--user/--password` 时用给定账号，若该账号没有实例，
则跳过实例相关步骤并改为断言"网关返回自己的 503 页"。返回码非 0 表示有 FAIL。

实测（dsh-mu）：`--user alice` → `PASS=10 FAIL=0`；自动建号 → `PASS=10 FAIL=0`；
`--user ops`（纯管理员）→ `PASS=8 FAIL=0`。

## 7. 已知限制

- 未签名包在各发行版默认策略下需要 `--allow-untrusted`；要免此参数就把 `make-apk.sh` 生成的
  `~/.abuild/*.rsa.pub` 分发到目标机 `/etc/apk/keys/`，或把包放进自建 APKINDEX 仓库。
- `--legacy-v2` 产物在 apk-tools 3.x 上可能被拒（见第 1 节说明），仅作老机器兜底。
- 包是 `noarch`：负载全是 Python/Lua/shell/HTML，与架构无关。
- HTTPS、日志轮转策略、实例端口段等运行期选项在 `/etc/dsh-mu/dsh-mu.conf`，不属于包的内容。

## 模板（jail rootfs）怎么来

`dsh-muctl install` 会准备 `/var/lib/dsh-mu/templates/alpine`（约 140 MB）。它现在这样生成：

1. **列出可用的 Alpine 系统镜像**：`ALPINE_IMAGE_INDEX`（默认 `http://download.proxmox.com/images/system`，
   这是唯一必须可列目录的地址；镜像站通常不提供索引）。安装时会按架构（`uname -m` → `amd64`/`arm64`）
   列出最近 10 个，输入序号选择，**回车默认最新**；`--yes` 或非交互环境直接取最新；
   也可用 `--template-image alpine-3.24-default_20260714_amd64.tar.xz` 钉死。
2. **下载**（缓存到 `/var/lib/dsh-mu/images/`，重装不再重复下载）：`ALPINE_IMAGE_BASE`，
   默认按公网 IP 归属地选择（中国 → `https://mirrors.tuna.tsinghua.edu.cn/proxmox/images/system`，
   其他 → `http://download.proxmox.com/images/system`），交互时会提示确认。
3. **解压**到模板目录，并做两次准备：把 `/etc/apk/repositories` 写成 `{ALPINE_MIRROR}/v<版本>/{main,community}`；
   复制宿主 `/etc/apk/keys/*` 与 `/etc/resolv.conf` 进去。
4. **进 chroot 装包**：`chroot <模板> /sbin/apk add --no-cache --keys-dir /etc/apk/keys <ALPINE_TEMPLATE_PACKAGES>`。
   在真 chroot 里装，包脚本/trigger 会正常执行（旧做法 `apk add --root` 不会，曾需要额外打补丁）。
5. 最后写入 `profile.d`、`/home/dsh/workspace`、`/usr/local/bin/dsh` 指向全局 DSH 包。

重建：`dsh-muctl install --force-template`；只换版本：改 `ALPINE_TEMPLATE_IMAGE` 后再 `--force-template`。

> 不校验镜像哈希（按你的要求）。镜像站若滞后于索引，下载会自动回退到官方地址。

## 0. 从 GitHub Release 安装（0.15.0 起）

CI（`.github/workflows/release.yml`）在推送 `v*` tag 时自动打包并发布 Release。

### 一行安装

```sh
cd /tmp
wget -O dsh-mu.apk \
  https://github.com/dainan13/dsh-mu/releases/latest/download/dsh-mu.apk
apk add --allow-untrusted ./dsh-mu.apk
dsh-muctl install --gateway-host <host>
```

> **`apk add <URL>` 不支持**（实测 Alpine 3.24 / apk-tools 3.0.6）：
> apk 只接受**本地文件**或**仓库包名**，所以必须先下载再安装。
> 校验可选：`wget -O SHA256SUMS <同一 URL 的 SHA256SUMS> && sha256sum -c SHA256SUMS`。

### 为什么这个 URL 能"永远指向最新"

GitHub 的 `/releases/latest/download/<asset>` **按 asset 名字**解析，而 `latest` 指
"**最新的、不是 draft、也不是 prerelease** 的那个 release"。所以三件事必须同时成立：

| 条件 | 本仓库怎么保证 |
|---|---|
| asset 名字**固定** | workflow 每次都额外上传一份 `dsh-mu.apk`（版本化名字另存一份 ✓） |
| release 不是 draft / prerelease | `draft: false`、`prerelease` 只在手动触发且勾选时才为 true |
| 是最新 release | tag 推送即发布，并显式 `make_latest: true` |

> 反过来：如果你把某个版本标成 **prerelease**，`/releases/latest/` 会**跳过它** ✓
> —— 这正是发"预览版"的正确方式（用 `workflow_dispatch` + 勾选 prerelease）。

### 每个 Release 的资产

| 文件 | 用途 |
|---|---|
| `dsh-mu.apk` | 稳定名字，给 `/releases/latest/download/` 用 |
| `dsh-mu-X.Y.Z-r0.apk` | 同一份字节，版本化名字（固定版本/归档用） |
| `SHA256SUMS` | 两个文件的校验和 |

### CI 里的门（不是"打完就发"）

1. tag 与 `VERSION` **必须一致**，否则直接失败；
2. `doc-lint` + `ui-lint` 必须过；
3. 在 **Alpine 3.24** 容器里构建（`apk mkpkg` 只在 apk-tools 3 里有）；
4. 再起一个**干净** Alpine 容器，用 `apk add --allow-untrusted` **真的装一遍**并检查
   `dsh-muctl --version`、三个二进制、admin 页面与 tests 都在位；
5. 才上传资产。

### 本机手工模拟同样的流程

```sh
sh packaging/make-apk.sh --version 0.15.0
# 本机装（等价于 Release 场景里的"wget 之后装本地文件"）
apk add --allow-untrusted --force-overwrite dist/dsh-mu-0.15.0-r0.apk
```

### 已知限制：包是**未签名**的

现在的包是 `apk mkpkg` 生成的**未签名**包，所以安装时必须 `--allow-untrusted`。
要改成可信签名分发：生成一对 RSA 密钥 → 用私钥签包（`abuild-sign` 或 `apk mkpkg --sign-key`）→
把公钥放进目标机 `/etc/apk/keys/`（或随包分发），安装时就能去掉 `--allow-untrusted`。
