# 18 · 跨端插件与资源代理（broker）规范

> 本文回答两件事 ✓：
> **① dsh-mu 要为"跨端插件"做哪些改造（由平台侧实现 ✓）；**
> **② 写一个跨端插件必须满足什么标准和约束（由插件作者遵守 ✓）。**
>
> 具体到 SSH **扩展**的需求，见工作区 `dsh-mu-ssh-ext/REQUIREMENT.md` ✓。

## 1. 为什么要"跨端"

DSH 插件跑在**实例 jail 里** ✓：它能看到资源，也能干活 ✓，但它所处的网络受**出网策略**约束 ✓
（默认 `no-intranet` ✓），而且**实例是不可信域** ✗（用户/模型都能改它的文件 ✓）。

因此凡是"访问受控资源"的插件 ✓，都必须拆成两端 ✓：

```
实例侧：dsh 插件（面板 UI + 给模型的工具）      ← 不可信，只能提需求
宿主侧：dsh-mu-broker（服务 P）                ← 可信，掌地址、凭据、审计
```

**判定规则**（写给插件作者）✓：

> 如果插件要连的东西**不在公网**、或者**地址/凭据不能让实例知道**、
> 或者**平台需要知道谁在什么时候用了什么** ✓ → 就必须走 P ✓，不准在插件里直连 ✗。

## 1.5 两个词，别混用

| 词 | 指什么 | 例子 |
|---|---|---|
| **扩展（dsh-mu 扩展）** | 一个 **apk 包** ✓：自带 rootfs ✓、在受管 jail 里跑自己的服务 ✓、携带自己的 dsh 插件 ✓ | `dsh-mu-ssh-ext` ✓ |
| **插件** | **dsh 侧**的 npm 包 ✓，装进实例的 profile 里 ✓ | `@dsh-mu/dsh-ssh` ✓ |
| 服务 P | 扩展里那个跑在 jail 里的守护进程 ✓ | 扩展自带 ✓ |

> 由扩展带来的插件，后台显示 **`随扩展`** ✓，不能删/不能更新 ✓（见 §3.5）✓。

## 2. 术语（两端必须统一）

| 术语 | 含义 | 谁能改 |
|---|---|---|
| **resource（资源）** | 一个具名目标：`ssh/dockerA`、`tcp/db-prod`、`image/ubuntu-24.04` ✓ | 平台/管理员（或平台代用户创建 ✓） |
| **catalog** | 资源目录（静态 ✓）：名称、归属、真实地址、凭据引用、配额 ✓ | 只有宿主侧 ✓ |
| **mount（挂载）** | **会话级**授权记录 ✓：`(session, resource, capabilities, ttl)` ✓ | 运行时由插件请求 ✓，P 记录 ✓ |
| **capability** | 允许的动作族 ✓：`ssh:exec` / `ssh:terminal` / `ssh:transfer` / `market:read` … ✓ | catalog + 审批 ✓ |
| **approval** | 每次动作是否要人在面板点确认 ✓ | mount 上的开关 ✓ |
| **token** | 实例身份凭证 ✓（每实例一把 ✓）+ 每次挂载的**一次性**令牌 ✓ | P 签发 ✓ |

**地址与凭据永远不出宿主** ✓ —— 客户端只说 resource 名字 ✓。

## 3. 平台侧：扩展包机制（dsh-mu 负责的只有这些）

> **形状**：扩展 = **自带 rootfs 的受管 jail（appliance）+ 一份清单** ✓
> 平台只负责"跑 jail"和"把端口/页面/包/命令接上" ✓ —— SSH 的代码一行都不在 dsh-mu 里 ✓。
> 好处：扩展自己带运行时 ✓，宿主不加依赖 ✓，换宿主 OS 也能用 ✓。

### 3.1 扩展包放什么（apk 只负责铺文件）

```
/usr/share/dsh-mu/extensions/<name>/
    manifest.json      ← 唯一契约（见 3.2）
    rootfs/ 或 rootfs.tar.zst   ← 自带运行时（python/asyncssh/ssh …）
    admin/             ← 可选：扩展自己的配置页（也可由 P 直接提供）
    bundles/*.tgz      ← dsh 侧插件的 npm 包（会被导入为"已批准资产"）
```

### 3.2 manifest.json

```json
{
  "name": "ssh",
  "version": "1.0.0",
  "summary": "SSH 资源代理",
  "requires": { "dsh-mu": ">=0.32", "jail-api": 1 },
  "service": { "port": 8790, "entry": "/opt/ext/p/broker.py", "health": "/health" },
  "net": { "egress": ["10.0.0.0/8"] },
  "admin": { "tab": "SSH", "url": "http://127.0.0.1:8790/admin" },
  "cgroup": { "cpu": "1", "memory": "512M", "pids": 256 }
}
```
- `requires`：平台版本不够就 **跳过并 WARN** ✓（不半装 ✓）
- `service.port`：只绑 loopback ✓；实例出网里**自动放行**这个端口 ✓
- `admin.port`（可选 ✓，**强烈建议** ✓）：配置页专用端口 ✓。
  `service.port` 会被实例 egress 放行 ✓（实例能直连 ✓），**`admin.port` 不会** ✓ ——
  这样"配置 API 只有平台网关进得来"✓。取值顺序 ✓：`admin.port` → `admin.url` 里的端口 → `service.port` ✓。
- 网关代理 `/ext/<name>/` 时**不转发**平台管理员令牌 ✓，改发每扩展一把
  `X-DSH-MU-Ext-Token` ✓（`/var/lib/dsh-mu/extensions/<name>/admin.token` ✓）——
  扩展用它区分"管理员"和"实例里的伪造请求"✓，**不要**信任 `X-DSH-MU-Admin` ✗。
- `net.egress`：扩展**自己**的出网白名单 ✓（默认 **deny-all** ✓）
- `admin`：平台把它做成后台「扩展」页里的 **配置按钮 + iframe** ✓
  —— ⚠️ `admin.url` 是**服务器侧**地址（`http://127.0.0.1:<port>/…`）✓；
  **浏览器走的是网关代理 `/ext/<name>/`** ✓（回环地址在操作员电脑上是错的 ✗）。
  因此扩展的页面**必须用相对 URL** ✓（`fetch('broker/v1/…')` ✓，不要写 `/broker/v1/…` ✗），
  否则在 `/ext/<name>/` 下会 404 ✗。
- `bundles/`：导入成 `source=apk` 的已批准资产 ✓（免下载 ✓ 不可被"更新"覆盖 ✗）

### 3.2b 端口从哪来（现状 + 目标）

- **现状** ✓：端口由**扩展自己在 manifest 里选** ✓（平台不分配 ✗），服务也在扩展的 jail 里 bind ✓。
  平台会做两件事 ✓：`ext reload` 时检查**重复** ✓ 与**平台保留端口** ✓（gateway ✓ / admin 8787 ✓ /
  relay 8099 ✓ / 实例端口段 ✓），冲突就 WARN ✓，`doctor` 里一条 `ext ports` ✓。
- **为什么这还不够** ✓：manifest 写死的端口有两个后果 ✗：
  1. 两个扩展选了同一个端口 ✗ → 后起的直接 `EADDRINUSE` ✗（人工发现 ✓ 机制不拦 ✗ 只告警 ✓）；
  2. `service.port` 必须被实例 egress 放行 ✓（插件要连 ✓）→ **实例也能直连服务端口** ✓（§3.2 那条边界 ✓）。
- **现在（0.39 起 ✓）：unix socket 优先，TCP 作为回退** ✓
  ```
  /run/dsh-mu/ext/<name>/api/api.sock     # 给实例里的插件：只绑进实例 jail（ro）
                                          #   实例内路径 /run/dsh-mu-ext/<name>/api.sock
  /run/dsh-mu/ext/<name>/admin/admin.sock # 给网关 /ext/<name>/：目录 0700，**不进实例** ✗
  ```
  - manifest 写法 ✓：
    ```json
    "service": { "socket": "api.sock", "entry": "/opt/ext/p/broker.py" },
    "admin":   { "socket": "admin.sock", "tab": "SSH" }
    ```
    （扩展在 jail 里写到 `/run/dsh-mu-ext/api/api.sock` ✓ 与 `/run/dsh-mu-ext/admin/admin.sock` ✓ ——
    两个目录由平台以 rw 挂进 appliance ✓）
  - 平台做的事 ✓：建目录（api 0711 ✓ / admin 0700 ✓）✓、把 api 目录 **ro 绑进每个实例** ✓、
    网关用 `proxy_pass http://unix:…:/` ✓、`ext status` 显示两个 socket ✓、`doctor` 检查 api socket 出现 ✓；
  - 有 `socket` 时 **不再放行任何 loopback 端口** ✓ → 没有端口可撞 ✓，实例也**只能**经过被绑定的那条 socket ✓；
  - 仍支持 `"port"` ✓（运行时做不了 unix socket 的扩展 ✓、排障 ✓），两者都有时 **socket 优先** ✓。

### 3.2c 扩展专用的平台接口：`/ext-api/<name>/…`

扩展的 appliance 可以**反向调用平台** ✓，但只能走这个命名空间 ✓：

| 方法 | 路径 | 作用 | 门槛 |
|---|---|---|---|
| GET/POST | `/ext-api/<name>/market/list` ✓ | 市场列表：**平台资产 ∪ 实例已安装** ✓（匿名计数 ✓ / `installed_here` ✓） | manifest 必须声明 `"caps": ["market"]` ✓ |
| POST | `/ext-api/<name>/market/stage` ✓ | 把**已批准离线包**放进**该实例**的 `<home>/.cache/dsh-mu-market/` ✓，返回 jail 内路径 ✓ | 同上 ✓ |

- **认证** ✓：`X-DSH-MU-Ext-Token`（= `/var/lib/ext/admin.token` ✓，每扩展一把 ✓），
  **不涉及**平台管理员令牌 ✗ —— 所以 appliance 被写坏也摸不到 admin API ✓；
- **路径固定** ✓：`stage` 的目标目录不可由请求指定 ✓（防穿越 ✓）；
- **能力声明** ✓：manifest 没写 `caps` 的扩展，调 `/ext-api` 直接 403 ✓（不会白拿能力 ✓）；
- **出网** ✓：扩展的 `net.egress` 要包含 `127.0.0.1/32` 才能到平台（8787）✓。

### 3.3 平台做的 8 件事

| # | 机制 | 命令/产物 |
|---|---|---|
| 1 | **发现与注册** ✓ | 扫 `manifest.json` ✓ → `dsh-muctl ext reload` ✓（apk post-install 里调 ✓） |
| 2 | **跑成 jail** ✓ | 生成 `/etc/dsh-mu/extensions/<name>.conf` ✓ + unit `dsh-mu-ext-<name>` ✓；cgroup `dsh-mu-ext/<name>` ✓；**无 capability** ✓；只 bind 自己的 data（rw ✓）+ 扩展目录（ro ✓） |
| 3 | **端口与出网** ✓ | 实例 egress 只放行 `service.port` ✓（**不放行 `admin.port`** ✓）；扩展自身按 `net.egress` 生成 `ext_<name>` 链 ✓（默认全拒 ✓） |
| 4 | **admin 注入** ✓ | 「插件」页多出该扩展一栏 ✓（iframe 指向 `admin.url` ✓）+ 继续复用 预装/推送 ✓ |
| 5 | **插件资产导入** ✓ | `bundles/*.tgz` → `source=apk` 已批准资产 ✓（幂等 ✓ 按 sha256 ✓） |
| 6 | **CLI 透传** ✓ | `dsh-muctl ext cli <name> <args…>` ✓ → 扩展自带的 `cli` ✓ |
| 7 | **doctor 汇总** ✓ | 每扩展一项 ✓：service 状态 ✓ + 端口应答 ✓（另有 `ext doctor <name>` 调扩展自带检查 ✓） |
| 8 | **卸载清理** ✓ | 清单消失 → 停 unit ✓、删 conf ✓、资产标 `orphaned` ✓（数据保留 ✓） |

### 3.4 CLI（平台侧，全部已实现）

```sh
dsh-muctl ext list               # 已装扩展：版本 / 端口 / 服务状态 / 插件包数
dsh-muctl ext reload             # 注册/刷新；被删掉的会停服务并标 orphaned
dsh-muctl ext status ssh         # 版本 / 服务 / 端口 / jail conf / data / egress
dsh-muctl ext start|stop|restart ssh
dsh-muctl ext logs ssh -n 100
dsh-muctl ext doctor ssh         # 调扩展自己的 cli doctor
dsh-muctl ext cli ssh resource add …   # 透传给扩展
```

### 3.5 扩展自带的 dsh 插件是"受管插件"

扩展 `bundles/*.tgz` 导入后 ✓，资产上会带 `source: "apk"` 与 **`managed_by: "<扩展名>"`** ✓。

**规则（平台已强制 ✓）**：

| 操作 | 受管插件 |
|---|---|
| 受保护 / 预装 / 推送 | **可以** ✓（决定"给哪些实例装"✓） |
| 更新 / 重新下载 | **不可以** ✗（升级 = 换扩展 apk ✓） |
| 移除 / 移除并删包 | **不可以** ✗（`apk del` 才是卸载 ✓） |
| 被同名 spec 覆盖 | **不可以** ✗（`plugin add` 会拒绝 ✓ 并说明由哪个扩展提供 ✓） |

后台「插件」页上这类包会显示 **`随扩展`** 徽章 ✓，操作列只剩说明文字 ✓；
`dsh-muctl plugin remove <name>` 会直接拒绝并提示卸载扩展包 ✓。

**命名与标记规范**（给扩展作者 ✓）：

1. npm 包名建议 **`@dsh-mu/dsh-<ext>`** ✓（例如 `@dsh-mu/dsh-ssh` ✓），便于人一眼认出；
   名字本身**不作判定依据** ✗ —— 判定只看 `managed_by` ✓；
2. 扩展的 `bundles/` 里只放**这一个**扩展自己的插件 ✓（不要夹带别人的包 ✓）；
3. 插件的 `package.json` 里建议写 `"dsh": { "ext": "<ext>" }` ✓（便于人工核对 ✓，平台不依赖它 ✓）；
4. 版本对齐 ✓：`manifest.version` 与插件包版本一起升 ✓，方便"扩展换版 → 插件换版" ✓。

### 3.6 参考实现

`examples/extension-ssh/` ✓ 就是按本规范写的示例 ✓（P 的骨架 ✓、`/health` ✓、`/admin` ✓、
`build-rootfs.sh` ✓、`bundles/` ✓）—— 新会话把它当起点 ✓。

## 4. 插件侧规范（跨端插件必须遵守）

### 4.1 包结构与命名

```
@<scope>/dsh-<name>            package.json
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" },
           "client": { "platform": "web", "inject": [ …ui… ] } }
  cordis.patch.yml             - insert: { id, name, config }
```
- 必须能在**离线**（`file:` tarball ✓）安装：**不许**在 install/postinstall 里联网 ✗
- 必须兼容平台的 `受保护 / 预装 / 推送` ✓（策略只认包名 ✓，不要做同名多包 ✗）

### 4.2 如何发现 P（唯一允许的入口）

```
broker_url  = process.env.DSHMU_BROKER_URL  或  ${DSH_HOME}/.dsh-mu/broker.url
token       = 读 ${DSH_HOME}/.dsh-mu/broker.fifo（一次性，读完立刻 unlink）
```
- **严禁**自己扫端口 / 猜地址 ✗
- **严禁**在实例里保存长期凭据 ✗（包括 ssh 私钥、密码 ✗）
- 面板里也不要显示真实地址/凭据 ✗（只显示资源名 ✓）

### 4.3 必须实现的工具（以 SSH 插件为例）

| 工具 | 前置 | 说明 |
|---|---|---|
| `ssh_list_resources` | 无 | 列出**可挂载**的资源（只有名字/能力 ✓） |
| `ssh_mount` / `ssh_unmount` | 无 | 绑/解绑到当前会话 ✓（P 校验 ✓） |
| `ssh_exec` | mount + `ssh:exec` | 一次性命令 ✓ |
| `ssh_terminal` | mount + `ssh:terminal` | 交互终端 ✓ |
| `ssh_upload` / `ssh_download` | mount + `ssh:transfer` | 文件 ✓ |

**闸门写法**（每个工具第一步）✓：

```ts
const mount = requireMount(ctx, sessionId)          // 没有就抛
// 报错必须告诉模型下一步怎么走 ✓
throw new Error('当前会话没有挂载任何 SSH 资源，请让用户在「远端」面板挂载后再试。')
```

### 4.4 会话语义（照 `@lemoncat7/dsh-ssh` 对齐 ✓）

- **mount 是会话级的** ✓：一个会话挂什么，另一个会话看不到 ✓（即使同一实例 ✓）
- 子会话**默认继承**父会话的 mounts ✓；父会话撤销时子会话一并失效 ✓
- 支持**按 turn 的临时租约** ✓（不动持久 mount ✓，用户说"撤销"立刻清 ✓）
- `approval` 打开时，每条命令/每次传输都要人在面板点确认 ✓
- mount 有 TTL ✓（默认与会话同寿 ✓，硬上限 12h ✓，可续期 ✓）

### 4.5 API 约定（P 提供，插件调用）

```
GET    /broker/v1/resources                    → [{id, kind, caps, label}]
POST   /broker/v1/mounts   {session, resource, caps, approval?, ttl?}
                                               → {mount, token, expires_at}
DELETE /broker/v1/mounts/{mount}               → 200
POST   /broker/v1/mounts/{mount}/ssh/exec   {command, timeout_ms, cwd?}
                                               → {stdout, stderr, exit}
POST   /broker/v1/mounts/{mount}/tunnel        → {port}   # 本地端口，用于终端/文件
```
- 所有请求：`Authorization: Bearer <token>` ✓ + `X-DSHMU-Plugin: <name>/<version>` ✓（只用于审计 ✓）
- 错误格式统一 ✓：`{error:{code, message, hint}}` ✓，`hint` 必须可执行 ✓（如"先在面板挂载"✓）
- 插件**不得**把 `port`、`token` 打印到日志或返回给模型 ✗

### 4.6 面板 UX 规范（与平台一致 ✓）

- 一切增改都是「按钮 → 弹窗 → 确认」✓；卡片只显示状态 ✓
- 状态顺序：**先展示当前会话已挂载什么** ✓，再是"可挂载列表" ✓
- 危险动作二次确认 ✓（删除资源引用、降级权限 ✓）
- 文案中文 ✓、短句 ✓、不用感叹号 ✓；错误要写"下一步怎么做"✓
- 面板里**不出现**真实地址/端口/凭据/令牌 ✗

### 4.7 测试与交付

- 单测：mount 闸门 ✓、错误分派 ✓、TTL 过期 ✓、子会话继承 ✓
- 提供 `scripts/broker-fake.mjs`（假 P ✓）让插件可脱离平台开发 ✓
- 交付物：`README.md` ✓、`CHANGELOG.md` ✓、`docs/releases/<ver>.md` ✓、`package.json` 版本 ✓
- 通过平台的 `plugin add`（tarball ✓）安装后，`受保护/预装/推送` 三开关均可正常使用 ✓

## 6. 一页速查（贴给插件作者）

```
只连 127.0.0.1:8790 ✓        绝不直连资源 ✗        绝不保存凭据 ✗
只发 resource 名字 ✓          不发地址 ✗            不打印 token/port ✗
每个工具先 requireMount ✓      报错写"下一步" ✓       挂载是会话级 ✓
增改走 按钮→弹窗→确认 ✓        面板不显示地址/凭据 ✗   离线可安装 ✓
```
