# 25 · 服务监控与进程启停控制（结构图）

本文用图说明三件事，便于排查与交接：

1. **谁在跑**：宿主上的服务、jail 里的进程、cgroup 的层级
2. **谁在控制**：一次 `instance restart` 从 CLI/API 到 jail 里 node 的完整路径
3. **谁在兜底**：watchdog / doctor / apk 钩子各自负责什么


**两条控制轴（不要混）**

| 轴 | 由谁驱动 | 影响范围 |
| --- | --- | --- |
| **配置/状态轴** | `dsh-muctl sync` / admin API | 重写 conf、gateway 视图、profile patch、service 文件；**不等价于重启进程** |
| **进程轴** | `rc-service` / `dsh-muctl instance restart` / watchdog | 真正 stop/start 进程（会写 `cgroup.kill` 或发 SIGTERM）|

## 2. 进程启停：一次 `instance restart` 的完整路径

```
  用户/CLI                        admin 页面
    │  dsh-muctl instance restart <name>        │ POST /api/instances/<name>/restart
    │                                           ▼
    │                              dsh-mud（8787）→ dshmuctl.apply_instance_runtime / restart
    ▼                                           │
  cmd_instance_restart ────────────────────────►│
            │                                   │
            ▼                                   ▼
     stop_instance(st, name)             start_instance(st, name)
            │                                   │
            │  ① service_action(name,"stop")     │  ① render_instance_conf()   ← 写 conf
            │     → rc-service dsh-mu-<name> stop│  ② install_phase(push)      ← 补推送插件
            │     → supervise-daemon 发 SIGTERM  │  ③ prune_stale_bundles()    ← 清失效 bundle
            │                                    │  ④ service_action(name,"start")
            │  ② kill_cgroup(name)               │     → rc-service … start
            │     → echo 1 > cgroup.kill         │     → supervise-daemon 起 dsh-mu-jail
            │       （清掉整个实例的进程树）      │     →（未受托管则自动 stop+start 一次重注册）
            │                                    │  ⑤ refresh_cookie()：拿 harness 启动 token
            ▼                                    ▼     换实例自己的浏览器 cookie
       服务状态 = stopped                    服务状态 = started
```

### jail 内部：`dsh-mu-jail` 做了什么

```
rc-service 起 supervise-daemon
   └─ exec /usr/local/sbin/dsh-mu-jail <name>
        ├─ 读 /etc/dsh-mu/instances/<name>.conf（PORT / MEM_MAX / CPU_MAX / PIDS_MAX /
        │   DSH_RUNTIME_DIR / RO_PATHS / BUNDLED_PLUGINS_HOST / EXTRA_MOUNTS / KEEP_CAPS）
        ├─ setup_cgroup()：mkdir cgroup，写 memory.max / memory.high / cpu.max / pids.max
        ├─ exec unshare --mount --uts --propagation private /bin/sh <inner>
        │     ├─ 自己写入 cgroup.procs（先入组，之后 fork 出来的都继承）
        │     ├─ 一组 bind mount（见上面 L1）
        │     ├─ hostname <name>（UTS 隔离）
        │     └─ chroot <rootfs> /bin/setpriv --bounding-set=-all … exec node …
        └─ 无 --fork：**工作负载就是被托管的那个进程** ✓（SIGTERM 能直达）
```

> 关键设计：`dsh-mu-jail` 不 fork。如果 fork，服务管理器只能杀到 wrapper，
> 真正的 node 会被 reparent 并继续占用端口，下一次 start 就报 "Address in use"。

## 3. 监控与自愈：三个角色

```
┌──────────────┬────────────┬───────────────────────────────────────────────┐
│ 角色         │ 触发方式    │ 做什么 / 不做什么                             │
├──────────────┼────────────┼───────────────────────────────────────────────┤
│ supervise-   │ 常驻        │ 只管**自己那一个**直接子进程：崩了 5 秒后重拉  │
│ daemon       │            │ （respawn-max=0 = 无限重试）；不跨服务         │
│              │            │ 注意：它有时会自己退出 → 服务显示 unsupervised │
├──────────────┼────────────┼───────────────────────────────────────────────┤
│ dsh-mu-      │ 每 60 秒    │ ① 平台自身：dsh-mud / 网关 没跑 → 拉起        │
│ watchdog     │            │ ② 扩展设备：真的 stopped → 拉起               │
│ (1.9.99+)    │            │    （unsupervised 但进程活着 = 视为健康，别动）│
│              │            │ ③ 实例：state=running 且端口连不上            │
│              │            │    · 启动后 240 秒内不动（冷启动保护）        │
│              │            │    · 连续 2 次探测失败才重启                  │
│              │            │    · 顺手把丢掉的 supervisor 重新注册          │
│              │            │ ④ 只报告不重启：--dry-run                     │
├──────────────┼────────────┼───────────────────────────────────────────────┤
│ dsh-muctl    │ 手动 / 页面 │ 一次性体检，不进后台：                        │
│ doctor       │            │ · 服务/端口/告警/cgroup/磁盘/egress/插件 bundle│
│              │            │ · 两条 freshness 检查会**自愈**（重启 admin、  │
│              │            │   重载网关），其余只报告 + 给修复命令          │
└──────────────┴────────────┴───────────────────────────────────────────────┘
```

### 实例健康判定（watchdog 的规则）

```
        ┌─────────────────────────────┐
        │ 每个实例（state == running） │
        └──────────────┬──────────────┘
                       ▼
        now - started_at < 240s ？ ──是──► 跳过（还在冷启动，别动）
                       │否
                       ▼
        TCP connect 127.0.0.1:<port> 成功？
              │是                        │否
              ▼                          ▼
         misses[name] = 0          misses[name] += 1
        （并修 supervisor）               │
                                         ├─ misses < 2 → 只记录，下一轮再看
                                         └─ misses ≥ 2 → stop + start（含 cookie 重取）
                                                          fail 则写日志，下一轮再试
```

## 4. 停止路径：为什么"stop"一定能停下来

```
service_action(name,"stop")
   ├─ rc-service dsh-mu-<name> stop
   │    → supervise-daemon 给直接子进程（= jail = node）发 SIGTERM
   │    → init 脚本的 stop_post()：echo 1 > /sys/fs/cgroup/dsh-mu/<name>/cgroup.kill
   └─ kill_cgroup(name)：再写一次 cgroup.kill（幂等）
        → 该 cgroup 里**所有**进程（含 node 的子孙、被 reparent 的）全部被杀
        → 之后 free_instance_port() 再确认端口已释放，必要时补刀
```

> 这也是为什么"不要在钩子里重启 `dsh-mu-cgroup`"：它会连带清掉实例的 cgroup，
> 所有实例瞬间 000，只能靠 watchdog 逐个拉回。

## 5. 服务清单与依赖顺序（openrc）

```
boot
 ├─ dsh-mu-cgroup        # 挂 cgroup2 并委托 cpu/io/memory/pids（其余服务的 need）
 │
default
 ├─ dsh-mu-runtimes      # before dsh-mu-gateway：把 squashfs 镜像重新挂上
 ├─ dsh-mu-gateway       # need cgroup；只有它 KEEP_CAPS=NET_BIND_SERVICE（要听 80/443）
 ├─ dsh-mud              # need cgroup；监听 127.0.0.1:8787（含 /run/dsh-mu/resp.sock）
 ├─ dsh-mu-watchdog      # need cgroup, after dsh-mud：每 60 秒巡检
 ├─ dsh-mu-ext-<name>    # 扩展设备（如 ssh）：独立 cgroup dsh-mu-ext/<name>
 └─ dsh-mu-<instance>×N  # 用户实例：独立 cgroup dsh-mu/<name>
```

每个单元的文件与运行时物料：

| 物料 | 路径 |
| --- | --- |
| 服务定义 | `/etc/init.d/dsh-mu-<name>` |
| 启动参数 | `/etc/dsh-mu/instances/<name>.conf`（扩展：`/etc/dsh-mu/extensions/<name>.conf`）|
| pid | `/run/dsh-mu-<name>.pid` |
| 日志 | `/var/log/dsh-mu/<name>.log` / `.err.log`（watchdog：`watchdog.log`）|
| cgroup | `/sys/fs/cgroup/dsh-mu/<name>`（扩展：`/sys/fs/cgroup/dsh-mu-ext/<name>`）|
| 数据 | `/var/lib/dsh-mu/instances/<name>/{rootfs,home}` |

## 6. apk 升级期间发生了什么（为什么这一步最容易出事）

```
apk add dsh-mu-x.apk
  ├─ pre-upgrade   ：停服务（openrc 行为）
  ├─ unpack        ：替换 /usr/local/{sbin,lib/dsh-mu}
  ├─ post-upgrade  ：① dsh-muctl sync（渲染 conf、重启 admin、重载网关）
  │                 ② setsid + sleep 5 → restart runtimes / gateway / mud / watchdog
  │                    （不能在钩子里直接 restart：apk 未结束，会失败）
  │                    （不能 restart dsh-mu-cgroup：会清空所有实例 cgroup）
  └─ 结束
```

装完之后仍未就绪时（例如钩子被跳过）：

```sh
dsh-muctl sync        # 立刻：渲染 + 检查并启动 dsh-mud
# 或者等 ≤60 秒，让 dsh-mu-watchdog 自己把 dsh-mud / 网关拉起来
```

## 8. 常用命令速查

```sh
# 看谁在跑
rc-status -a | grep dsh
for c in /etc/dsh-mu/instances/*.conf; do n=$(basename "$c" .conf); \
  P=$(grep -o 'PORT=[0-9]*' "$c" | cut -d= -f2); \
  echo "$n $(curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:$P/)"; done

# 单台启停（安全路径）
dsh-muctl instance restart <name>      # 渲染 conf + stop + start + 取 cookie
dsh-muctl instance stop <name>
dsh-muctl instance start <name>

# 兜底与体检
dsh-muctl watchdog --once --dry-run    # 只看不改
dsh-muctl doctor                       # 全量体检（含自愈项）
dsh-muctl sync                         # 渲染 + 保证 admin/网关在跑

# 扩展设备
dsh-muctl ext status ssh
dsh-muctl ext restart ssh
```

## 9. 已踩过的坑（图上看不出来，但必须知道）

| 现象 | 原因 | 现在怎么防 |
| --- | --- | --- |
| 实例 `000`、日志只有 jail 两行 | 内置插件 bundle 声明了但文件不在 → DSH 在绑端口前退出 | 启动前 `prune_stale_bundles` + `instance-repair` |
| 实例反复被重启、起不来 | watchdog 在冷启动窗口里重启它，stop 写 `cgroup.kill` | grace 240s + 连续 2 次失败 |
| 扩展被反复 SIGTERM，依赖它的实例卡住 | `ext_reload` 每次 sync 都 restart 扩展 | 幂等：只在配置变化/未运行/无 supervisor 时重启 |
| 装完包 admin 打不开（502） | apk 停服务，钩子里 restart 失败 | 延迟重启 + sync 保证启动 + watchdog 托管 |
| 所有实例同时 000 | 重启了 `dsh-mu-cgroup` | 钩子明确不碰 cgroup；watchdog 逐台拉回 |
| 实例显示 `unsupervised` | supervise-daemon 自己退出，但进程还在跑 | 视为健康（只要端口通），不重启；需要真正托管时再 restart |
