# 12 · 图片发不了？先看宿主 CPU；扩展起不来？先看启动顺序

这两条是同一类故障的两个面孔：**表面错误信息完全不指向真因**。
把它们写在这里，是因为每一条都花掉过几个小时。

## 12.1 症状：`prompt rejected (session/agent-busy)`

DSH 的图片准入（`dsh-api-session-controller`）把**任何**未分类异常都报成 `agent-busy`：

```js
catch (error) {
  if (error instanceof AttachmentError) throw new RemoteError("session/attachment-invalid", …);
  throw new RemoteError("session/agent-busy", "prompt rejected", { reason: String(error) });
}
return hasImage ? this.agents.serializeImageAdmission(agent, admit) : admit();
```

所以：

- **只有带图**才会走到 `serializeImageAdmission`；文字永远正常 → “文字好、图片坏”是它的指纹。
- `reason`（真因）**界面不显示**，只藏在响应体里。

### 12.1.1 真因排查顺序

```sh
# ① 宿主/虚机 CPU 是否满足 x86-64-v2（DSH 用 sharp 处理图片，官方预编译要 v2）
grep -m1 "model name" /proc/cpuinfo
for f in sse4_1 sse4_2 popcnt avx avx2; do printf "%-8s " "$f"; grep -qw "$f" /proc/cpuinfo && echo 有 || echo "没有"; done
```

`Common KVM processor` + 没有 `sse4_2`/`popcnt` ⇒ **就是它**（Proxmox 默认 `kvm64`）。
sharp 会报：

```
Could not load the "sharp" module using the linuxmusl-x64 runtime
Unsupported CPU: Prebuilt binaries for Linux x64 require v2 microarchitecture
WebAssembly.Module(): Wasm SIMD unsupported
```

**修法**（不是改软件）：

```
Proxmox → VM → Hardware → Processors → Type: kvm64 → **host**（或 x86-64-v2-AES）
然后 **Stop → Start**（改 CPU 类型必须彻底关机再开，reboot 不生效）
```

开机后验证：`grep -m1 "model name" /proc/cpuinfo` 变成真实型号、`sse4_2` 有、
`node -e "require('…/sharp')"` 不再报错。

### 12.1.2 看到真因的办法（临时、可还原）

```sh
F=/var/lib/dsh-mu/gateway/rootfs/usr/local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-api-session-controller/lib/index.js
cp -a "$F" "$F.bak"
# 在 catch-all 的 throw 之前插一行 console.error
#   console.error("[dsh-mu-diag] image admission failed:", error && (error.stack || error.message || error));
rc-service dsh-mu-<实例> restart
# 触发一次带图请求，然后：
grep -A12 "dsh-mu-diag" /var/log/dsh-mu/<实例>.err.log
# 用完立刻还原：
mv -f "$F.bak" "$F" && rc-service dsh-mu-<实例> restart
```

> 还原后核对 `md5sum` 与另一台机器一致，确认没留下改动。

### 12.1.3 “当前模型不支持图片”

这条**是另一回事**：模型在 patch 里被声明成 `input: [text]`。
按 `docs/11` 的规则处理（空=放行 / `[text]`=禁止 / `[text,image]`=允许），
用 `dsh-muctl provider vision <provider> --auto` 或 `--model X --on`。

## 12.2 症状：实例“起不来”，端口永远 closed

判断链路：

```sh
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:<port>/   # 000 = 没起来
tail -20 /var/log/dsh-mu/<实例>.err.log        # 只有 jail "starting mode=serve" = 静默退出
dsh-muctl instance preflight <实例>            # 配置/依赖/patch 是否 ok
cat /sys/fs/cgroup/dsh-mu/<实例>/cgroup.events # populated/frozen
```

三种已知原因：

| 现象 | 原因 | 修法 |
|---|---|---|
| 日志只有 `starting mode=serve`，preflight ok | **会话 cookie 失效**（日志里会有 `could not mint a cookie`） | `dsh-muctl instance start <实例>`（0.95.7 起会自动 stop+start 重试一次） |
| `must be a top-level YAML array` | 旧 overlay 只剩注释 | `dsh-muctl sync`（0.91.6 起自动写 `[]`） |
| 前两者都不是 | jail rootfs 内部状态损坏 | `dsh-muctl instance rebuild <实例>`（保留 home/workspace） |

> **不要**因为“起不来”就删实例重建：会话历史会丢，而 cookie 问题一次 start 就能好。

## 12.3 症状：扩展（ext）重启后一直是 stopped

```sh
dsh-muctl ext status ssh          # service stopped / adm sock (connect: missing)
rc-service dsh-mu-ext-ssh status  # unsupervised = 连 supervisor 都没有
```

两个原因叠加：

1. **服务脚本是旧版**：缺少 `after dsh-mu-gateway`。扩展的套接字在
   `/run/dsh-mu/ext/<name>/`，由**网关**创建；先于网关启动就会退出。
   → 跑一次 `dsh-muctl install` 会重写脚本（0.95.0 起带 `after`）。
2. **broker 退出方式让 supervisor 也不留**（扩展包侧问题）→ 已反馈给
   dsh-mu-ssh-ext，期望“目录不存在时重试 + 非 0 退出”。

临时修：`dsh-muctl ext restart ssh`；`dsh-muctl doctor --fix` 也会把停着的扩展拉起来。
