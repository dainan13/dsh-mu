# dsh-mu 验收走查清单

> 给**验收人**（或未来的你）用：从一台空机器到"所有主张都被验证过"，每一步都写清**命令**、
> **期望结果**、**证据落在哪**、**失败时先看什么**。最后有一张签收表。
>
> 与之配套：[`docs/07-证据索引.md`](07-证据索引.md)（每条主张 → 验证脚本 → 最近结果）、
> [`DELIVERY.md`](../DELIVERY.md)（交接单：这是什么、怎么装、怎么证明）。
>
> 预计时间：装机 ~10 分钟；31 层全量 ~33 分钟（WebSocket 那次 75 秒保持占一部分）；真机 `fresh-machine.py` ~1–9 分钟。

## 0. 前置与判定标准

- 机器：Alpine 3.2x（裸机或 LXC 均可），有 `root`，能访问配置的 Alpine 镜像与 npm registry；
- 判定：**每一层的汇总行里 `FAIL=0`**。WARN 需要逐条看修复建议，`doctor` 的 FAIL 必须先清零；
- 所有命令都在机器上以 root 运行；`<用户>`/`<口令>`/`<实例>` 用你自己建的账号替换。

## 1. 产物核对（不安装，只读）

```sh
sh packaging/make-apk.sh --version 0.1.0        # 或在源码树里
python3 tests/artifact-audit.py . --tarball dist/dsh-mu-<ts>.tgz
```

- **期望**：`ARTIFACT AUDIT PASSED`，其中包含 `apk verify ... OK`、包 **227 KB 上下**、
  `all 17 promised files`、`no template, runtime state, secret or build leftover inside`；
- **证据**：脚本输出本身 + `dist/dsh-mu-0.1.0-r0.apk`；
- **失败时**：先看它打印的 `FAIL` 行（哪一项承诺不成立），再对照 `packaging/APKBUILD` 的 `package()`。

## 2. 安装（干净机器）

```sh
apk add --allow-untrusted dsh-mu-0.1.0-r0.apk   # 单文件包，未签名
dsh-muctl install                               # 依赖 / 全局 DSH / jail 模板 / 网关片段 / 服务
passwd root                                     # 管理员 = 宿主系统账号（默认 root）
dsh-muctl user add alice --password '<强口令>'   # 建第一个用户（自动建同名实例）
dsh-muctl doctor
```

- **期望**：`install` 打印一行 doctor 摘要；`doctor` 最终 **0 FAIL**（首装时会有 WARN，逐条按建议处理）；
  浏览器打开 `http://<主机>/` 能看到登录页；
- **证据**：`dsh-muctl doctor --json`、`/var/log/dsh-mu/`、`/usr/share/doc/dsh-mu/`（含本文件与
  `DELIVERY.md`、`docs/` —— 文档随包分发，不需要回头找源码包）；
- **失败时**：`dsh-muctl doctor --fix`；仍失败则看 `doctor` 给出的修复命令与
  [`docs/06-运维手册.md`](06-运维手册.md) 的故障对照表。

## 5. 这份清单**不覆盖**什么

| 未覆盖 | 为什么 | 怎么补 |
|---|---|---|
| 真实 OpenRC 起服务（网关/后端/每个实例服务） | 第 18 层跑在 chroot 里，没有 init，直接拉起守护进程代替 | 第 6/7 层在真机上验证服务与实例 |
| HTTPS、多机/高可用、容量数字 | 超出本期设计（单机多租户） | 见 [`docs/07-证据索引.md`](07-证据索引.md) §4 的选项清单 |
| 包签名信任链 | 当前是未签名包（`--allow-untrusted`） | 把 abuild 公钥放进 `/etc/apk/keys`，或用正式密钥重签 |

**第 7 层是唯一需要"干净机器"的一层**：它会真的建号、建实例、跑通模型再清理。若机器已经被用过，
`--skip-install` 仍可跑（跳过安装步骤），但"全新机器"的说服力来自真的从零走一遍。
