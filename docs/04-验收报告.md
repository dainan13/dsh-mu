## 7. opencode provider 接入实测（追加）

按你的选择把实例模型切到 opencode 推理端点，实现方式与实测结论：

**实现**（`dsh-muctl instance provider <名> opencode --key-file <文件>`）
- 覆盖 `llm-deepseek` 行：`baseURL=https://opencode.ai/inference/anthropic` + 6 个模型的目录；
- 覆盖 `agent-default-model` 行：provider 仍是 `deepseek-official` 路由，model 换成 `deepseek-v4.1-flash`；
- key 写进该实例凭据库的 `refs.DEEPSEEK_API_KEY`（浏览器会话签名记录字节不变）；
- 通过 `DSH_LAUNCH_ARGS="--patch /home/dsh/.dsh-mu-provider.yml"` 注入，jail 内实际命令为
  `dsh --patch <文件> --profile web --host 127.0.0.1 --port <p> --no-open`
  （注意 `--profile web` 必须显式给出：`dsh` 只把**首个参数**当 profile 位置参数，
  所以 `dsh --patch X web …` 会报 `--profile <name> is required`）。

**实测**

| 项 | 结果 |
|---|---|
| jail 内组合后的配置 | ✅ `baseURL: https://opencode.ai/inference/anthropic`、6 条模型目录、默认模型 `deepseek-v4.1-flash` |
| DSH 真实发起请求（headless，同一 patch） | ✅ 返回 `dsh: QUOTA: Upstream request failed: Insufficient account funds` —— 说明 baseURL/key/协议/模型 id 全链路正确，错误来自 opencode 账户 |
| 带鉴权头 | ✅ DSH 发的 `x-api-key` 被接受（不再有 `MISSING_CREDENTIAL`） |
| 网关两个账号自检 | ✅ 均 ALL CHECKS PASSED（UI 34846 字节、WS 15s/7 ping） |

### 7.1 第二轮：改用 Go 产品端点后**打通**

你提供的两条 opencode 事件日志给出了决定性线索：同一 key、同一模型，
`/inference/anthropic/v1/messages`（product=standard）402，而
`/inference/go/v1/chat/completions`（product=go，openai-chat）200。
即 Go 订阅只覆盖 **Go 产品的 OpenAI Chat 协议端点**，与协议适配层无关。

据此把默认 provider 换成新预设 `opencode-go`（走 `dsh-llm-pi-ai` 的 `openai-completions` 路由）：

```yaml
- id: llm-pi-ai
  config:
    providers:
      opencode-go:
        apiKeyEnv: DEEPSEEK_API_KEY
        api: openai-completions
        baseURL: https://opencode.ai/inference/go/v1
        headers:
          x-opencode-session: "dsh-mu-alice"
        models: [ deepseek-v4.1-flash, deepseek-v4-pro, glm-5.3, kimi-k3, ... ]
- id: agent-default-model
  config: { provider: opencode-go, model: deepseek-v4.1-flash }
```

另外两个必须的细节：

1. **`x-opencode-session` 是必需的**，缺失时报 `400 MissingSessionID`（你那条成功日志里也有这个头）；
   由路由 `headers` 提供，值 `dsh-mu-<实例名>`，实例期内稳定。
2. **一个 route 只能说一种协议**，而 Go 的模型分散在 `/chat/completions`、`/messages`、`/responses`
   三种端点，所以预设只收录前者；Qwen/MiniMax/Claude-Haiku（Go 的 `/messages`）需要另加一条
   `anthropic-messages` 路由。

**第二轮实测**

| 项 | 结果 |
|---|---|
| jail 内组合后的配置 | ✅ `llm-pi-ai` 路由 `opencode-go` + `x-opencode-session` 头 + 12 条 `/chat/completions` 模型 |
| **真实模型调用**（headless，deepseek-v4.1-flash） | ✅ **返回 `PONG`**（DSH → opencode Go → 内容） |
| 网关 Web UI 自检（alice） | ✅ ALL CHECKS PASSED（UI 34846 字节、WS 15s/7 ping） |
| 切换默认模型 | ✅ `dsh-muctl instance provider <名> opencode-go --model kimi-k3` |

**当前状态**：alice / bob 两个实例都已切到 `opencode-go`，UI 里可以直接对话。
换回官方 DeepSeek：`dsh-muctl instance provider <名> deepseek` + 注入 DeepSeek key。

## 本轮修掉的 5 个真 bug

1. `admin/dsh-mud` 缺 `import subprocess` → 系统口令校验抛 `NameError`，后端 500；
2. 网关 `config.json` 视图只有 3 个键，**缺 `admin_system_users`** → Lua 不认系统账号，登录回落到平台口令路径；
3. `instances` 视图缺 `provider`/`model` → 面板与 `/me` 显示错误的 provider；
4. `access_by_lua_file` **不会为 `ngx.location.capture` 子请求执行**（加临时日志实测确认）→ 内部通道的

# 十四、第 18 轮（补齐 CLI 侧的审计留痕）

## 实现方式：收敛到写入层做差异快照

所有状态变更都经过 `save_state()`／`save_config()`／`save_custom_providers()`，于是就在这三处比较

后端进程（`DSHMU_BACKEND=1`）跳过这三类通用记录，继续写它自己的请求级记录（管理员 + 客户端 IP + 状态码
+ 脱敏请求体），两边共用同一个审计写入函数。

# 二十六、第 30 轮（日志轮转：声称过，但从未真跑过）

目标条目 (1) 里写着"日志轮转"。它的**配置**被 `doctor` 检查（drop-in 存在），但**轮转本身**从没被执行过——
而轮转失效的后果是磁盘写满、整台机器上的所有实例一起挂。本轮补 `tests/log-rotation.sh`。

## 关键点：为什么必须是 `copytruncate`

nginx 与 `supervise-daemon` 都**长期持有日志文件描述符**。如果用"重命名"式轮转，它们会继续往被改名的旧文件里写，
新文件永远是空的——这正是很多平台"日志轮转后看不到新日志"的原因。因此断言里有一条专门检查 drop-in 用了
`copytruncate`，另一条验证**轮转后服务还在往新文件里写**。

## 验证内容（`tests/log-rotation.sh`，13 项）

| 检查 | 说明 |
|---|---|
| drop-in 存在且含 `copytruncate` | 否则 nginx 会写进旧文件 |
| `daily` / `maxsize` / `rotate` / `missingok` / `notifempty` / `compress` 齐全 | 调度与保留策略 |
| `logrotate -d`（dry run）无 error / unknown option | 配置语法与 Alpine 的实际解析 |
| `logrotate -f` 后**出现轮转副本** | 真的轮了一次 |
| **活文件被原地截断**（字节数变小） | copytruncate 生效 |
| 之后打一次网关与后端请求 → **日志继续增长** | 写入者没有丢 fd |
| **nginx worker 未被重启** | 轮转不需要 reload/restart |
| 轮转后写一条配置变更 → **审计日志仍在记录** | 审计链路不受轮转影响 |
| `dsh-muctl logs rotate --force`（无 logrotate 的兜底） | 输出说明它做了什么 |
| `dsh-muctl logs size` | 报告占用 |
| 保留份数有界（`rotate N`，N ≥ 2） | 不会无限堆积 |

## 新增能力（CLI + 页面 + API，同一实现）

| 入口 | 用法 |
|---|---|
| CLI | `dsh-muctl user kick <名>` |
| 管理页面 | 用户表新增「踢下线」按钮 |
| 回环 API | `POST /api/users/<名>/kick` |

语义：**推进该账号的会话 epoch**（所有既有会话立即失效，含正在使用的那一个），**口令不变**——
所以他可以立刻用原口令重新登录。

## 顺带修掉一个**审计盲点**

`_user_fingerprint()` 原本是 `(role, enabled, instance, must_change, pw[:16])`——**不含 epoch**。

现在 epoch 已纳入指纹：踢下线会产生 `user.change` 记录（口令变更本来就会记，不会重复）。

这条盲点说明一件事：**审计指纹必须覆盖"能被管理动作改变的字段"**，否则就会出现"操作了但查不到"的角落。

# 三十五、第 39 轮（抽查一条安全主张：它被"过度声称"了）

# 三十六、第 40 轮（抽查长连接：15 秒的检查证明不了 60 秒的超时）

抽查对象：FR-3.1"长连接不被 nginx 默认 60s 砍断"。翻开 `tests/selftest.mjs`，WebSocket 检查

## 先实测：把保持时间拉到 75 秒


| 6 WebSocket 保持 **75s**（默认值由 15s 改为 75s） | 连接在**有流量**时稳定、跨过默认超时窗口 | 超时值本身（心跳会重置计时） |

# 三十九、第 42 轮（续）：一次"我的测试把别的层搞挂了"的事故与修法

补上 cgroup 三项检查后跑全量回归，结果 **PASS=15 FAIL=3**：`fresh-machine`、`failure-modes`、`soak` 都挂了。
日志给出的线索是干净利落的一句：

```

```

**根因**：`login.lua` 的防爆破是**按来源 IP** 记 40 次失败（窗口 600 秒）。我上一轮加进 selftest 的 6d
检查会**连打 11 次失败登录**，把 127.0.0.1 的预算吃掉一大块；而 `fresh-machine.py` 与 `acceptance.sh`
**都会再跑一次 selftest**，于是在同一窗口内它们第 1 次登录就吃到 429 →
fresh-machine 的两个失败项（selftest、acceptance）、failure-modes 的"后端停机时普通用户"、soak 的 2 项，
全都是这一个原因的下游效应。

## 修法：把"会消耗预算"的检查隔离到最后一层

| 改动 | 说明 |
|---|---|
| 6d 从 `tests/selftest.mjs` 移出 | selftest 回到"无副作用"，可被其它层反复调用 |
| 新增 `tests/login-limit.py` | 独立脚本：建临时账号 → 打满 → 断言第 11 次 429 + 锁定期间正确口令也被拒 → 删号 |
| **排在回归最后（19/19）** | 它消耗的预算不再影响任何后续层 |
| **自检跳过** | 若第一次尝试就 429（说明预算已被别的失败测试用掉），它 **SKIP** 并提示"单独重跑"，而不是假失败 |
| 打印消耗量 | 结尾说明"本层消耗了 40 次中的 N 次（600 秒窗口）"，让运维心里有数 |

**教训**（值得写下来）：一个测试的**副作用半径**也是它的一部分。我上一轮只检查了"这个断言会不会失败"，
没检查"它会不会干扰别人"——**共享的限速预算就是被测试污染的典型资源**。同类资源还有：
登录会话、实例端口、cgroup 组、磁盘空间。以后加检查要先问一句"它会用掉什么别人也要用的东西"。

实机实验（建临时实例、写短密钥、查审计）显示当时"没泄漏"只是因为**根本没有审计记录**在写它；

`api-key` 之后的第二个词一律 `***`。脱敏自测：

```
dsh-muctl instance api-key alice ***
dsh-muctl instance provider alice deepseek --key ***
dsh-muctl user passwd bob --password ***
```

## 顺带修掉一个真 bug：`die()` 的原因在接口里**丢了**

第一版测试里"越界守卫"那条 FAIL，但守卫其实**触发了**（HTTP 400）——只是 `detail` 只有 `"1"`。
原因：`die()` 把消息打到 **stderr**，然后 `raise SystemExit(code)`；接口里
`except SystemExit as exc: str(exc)` 拿到的只是**退出码**。于是所有走 `die()` 的接口错误都只剩一个数字：

```json
{"error": "cannot move the port", "detail": "1"}
```

修法：`die()` 改为抛 **`CliError`（继承 `SystemExit`，携带 `message`）**，接口用 `mu_exc_message()`
取该消息。修完实测：

```
HTTP 400 port 3100 is already assigned to instance alice
HTTP 400 port 1 is outside the configured range 3100-3999 (change PORT_RANGE…)
```

**这是我第三次遇到"错误信息在传递中丢失"**（前两次：后端 500 的 traceback、`doctor` 的修复提示）。
它值得记成一条经验：**异常类型要携带原因，光有退出码/状态码不算报错**。

# 四十七、第 50 轮（备份漏掉了用户真正的工作区）

抽查管理页的"备份下载"按钮时，顺手核对了一件事：**备份到底包含什么？**结果发现一个会静默丢数据的缺口。

## 缺口：用户的工作区不在备份里

jail 的挂载表（实机 `dsh-muctl instance exec alice -- cat /proc/mounts`）：

```
/dev/loop7 /home/dsh            ext4 rw
/dev/loop7 /home/dsh/workspace  ext4 rw      <-- 单独挂载，遮蔽了 home/workspace
```

也就是：`instances/<名>/home` → `/home/dsh`（DSH_HOME：会话、凭据、profile），
而 **`instances/<名>/workspace` → `/home/dsh/workspace`**（用户实际写文件的地方）。

而 `backup_members(with_instances=True)` 只打包 `instances/<名>/home`。实机核对归档成员：

```
etc/dsh-mu/state.json ｜ dsh-mu.conf ｜ dsh-mu.conf.default ｜ providers.json
admin.token ｜ secret.key ｜ gateway/{users,upstreams,config}.json
var/lib/dsh-mu/instances/alice/home     <-- 只有 home
var/lib/dsh-mu/instances/bob/home
```

`tar tzf … | grep -c "instances/<名>/workspace/"` → **0**。

**后果**：灾难恢复后平台记录、凭据、会话都在，但**用户写在工作区里的文件全部消失**——
这恰恰是"备份"最该保住的东西。

## 修法与验证

1. `with_instances` 现在打包**两个持久卷**：`home`（DSH_HOME）与 `workspace`（实际工作区）。
   实测：把探针文件写进 `instances/alice/workspace/probe/file.txt` → 归档里能找到（计数 1）
   并解出内容 `hello` ✓；
2. **同时修掉第 26 轮那场演练的误导性检查**：它把标记写进 `home/workspace/marker.txt`——
   一个在 jail 内**被遮蔽**、用户从不写入的目录。演练现在**两个卷都放标记**，并额外断言
   **归档里没有 `rootfs` 拷贝**（备份只含记录 + 持久卷，不含 140MB 的根文件系统副本）；
3. 备份下载改为**流式发送**（256KB 块）。工作区是用户数据、可能很大，原来的 `open(...).read()`
   会把整个归档读进后端内存——会让后端 RSS 随备份大小增长。实测下载：`200 / application/gzip /
   Content-Disposition: attachment; filename="dsh-mu-backup-…" / gzip 魔数 ✓`；
4. 顺带把该处理器里最后一处 `str(exc)` 换成 `mu_exc_message(exc)`（第 49 轮漏网的一处）。

（挂载表、`/proc/mounts`、实际写入位置），而不是"看起来应该在的地方"。

# 五十三、第 56 轮（`0` 的两种含义，以及负值把限制反转）

本轮查限额取值。你之前的明确要求是"CPU 限额要和内存一起有[不限]选项"，所以 `0` 的语义必须准确——
而这正好是本轮两个问题的共同点。

## 问题一：原始形式里的 `0` 会真的写进 cgroup

命令行有两套旗标，名字只差几个字符：

| 友好形式（页面用） | 原始形式（直接写 cgroup） |
|---|---|
| `--mem-mb 0` → 不限 | `--mem 0` → `memory.max=0`（**一个字节都不许**） |
| `--cpu-cores 0` → 不限 | `--cpu 0` → 格式不合法，被拒 |
| `--pids-num 0` → 不限 | `--pids 0` → `pids.max=0`（**一个进程都不许**） |

我第一次测试时就**用错了旗标**（把 `--mem` 当成 MB）——这个混淆不是测试的专利，运维同样会犯。
实测结果：

```
FAIL  --mem 0 did not become unlimited  -- record=0 cgroup='0'
FAIL  --pids 0 misbehaved               -- record=0 cgroup='0'
```

一个"看起来像限额"的 0，实际效果是**让实例什么都做不了**。现在原始形式拒绝 `0` 并解释清楚：

```
mem: 0 is not 'unlimited' in the raw cgroup form (it allows nothing) - use 'max',
     or the --mem-mb/--pids-num form where 0 means unlimited
```

## 问题二：负值被静默当成"不限"

`--mem-mb -1` / `--cpu-cores -1` / `--pids-num -1` 都走 `if value > 0 else "max"` 这条分支，
于是**负值把限制整个移除**——方向恰好和运维想要的相反：

```
FAIL  a negative memory limit was accepted  -- record=max (silently unlimited?)
FAIL  a negative CPU limit was accepted     -- record=max (silently unlimited?)
```

修法：负数报错，`0` 保持"不限"：

```
dsh-muctl: memory must not be negative (use 0 or 'max' for unlimited), got '-1'
dsh-muctl: cpu must not be negative (use 0 or 'max' for unlimited), got '-1'
```

## 修完之后的证据（15 项）

```
PASS  --mem-mb 0 means unlimited, and the cgroup says `max`
PASS  --cpu-cores 0 means unlimited, and the cgroup says `max`  -- max 100000
PASS  --pids-num 0 means unlimited  -- record=max cgroup=max
PASS  a negative memory limit is refused, not silently unlimited
PASS  a negative CPU limit is refused
PASS  an explicit unit lands as the right byte count in the cgroup  -- 2G -> 2147483648
PASS  fractional cores become the right cpu.max quota  -- 150000 100000
PASS  the raw cgroup flags refuse 0 (it would allow nothing, not everything)
PASS  the raw form still accepts `max`
PASS  a very large limit is accepted and applied  -- cgroup=1099511627776
PASS  the instance's original limits were restored and verified
=== LIMIT VALUES: PASS=15 FAIL=0 ===
```

注意最后一条：**还原之后再验证**（第 54 轮那次清理失误的教训，这次写进了测试本身）。

## 一句总结

"不限"必须只有一种写法，而**任何看似数值的输入都不该悄悄反转它的方向**——
`0` 与负数在这套旗标里各有两种读法，本轮把两种都钉死成一种。

# 五十四、第 57 轮（密码最小长度：管理员重置那条路漏了）

继续沿"边界"走，本轮是**密码**——本地账号的唯一凭据，所以最小长度属于安全属性，
而且必须在**每一扇门**上都成立。

## 缺口：两道门有校验，另外两道没有

| 入口 | 修复前 | 应该 |
|---|---|---|
| 用户自助改密 `me_password` | ≥8 ✓ | ≥8 |
| 建号 `do_user_create` | ≥8 ✓ | ≥8 |
| **CLI `user passwd`** | **无校验** ✗ | ≥8 |
| **管理员页面重置**（`do_user_password` → `cmd_user_passwd`） | **无校验** ✗ | ≥8 |

实测（修复前 6 PASS / 6 FAIL）：

```
FAIL  the CLI accepted a 1-character password
FAIL  a refused change still altered the account  -- epoch 0 -> 1
FAIL  the CLI accepted a 7-character password
FAIL  an empty password was accepted  -- exit=0
FAIL  `user add` accepted a short password  -- exit=0
FAIL  the API accepted a short password  -- 200
```

其中"**空密码也能设置**（exit=0）"最刺眼。好消息是 Lua 侧 `verify_password` 对空/畸形记录
一律 `return false`（fail-closed），所以空密码不会变成"空密码即可登录"，代价只是把账号锁死。

## 修法与验证

唯一收口点 `require_password()`（≥8 且不许纯空白），由 `cmd_user_passwd` 与 `cmd_user_add` 调用——
CLI 与页面两条路因此自动一致。修后 **12 PASS / 0 FAIL**，其中三条是"边界本身"的证据：

```
PASS  a refused change left the account untouched (same hash, same epoch)
PASS  an 8-character password is accepted (the boundary)  -- epoch 0 -> 1
PASS  the new password really works for a login  -- HTTP 302
PASS  the old password no longer works
```

第一条尤其重要：**拒绝的副作用必须是零**——修复前那次 1 字符"成功"会把 `epoch` 加一、
把该用户所有会话踢下线；现在被拒的修改连 epoch 都不动。

四次都不是功能坏了，而是**同一个规则被写在了不同的地方**。修法也一致：**把规则收到唯一入口**，

## 大多数行为本来就稳（现在被钉住）

| 检查 | 实测 |

## 一个会误导人的判定：`ok = 2xx`

一个返回 **200 但正文是垃圾**的端点会被报成"连接正常"：

```
FAIL  a 200 with a junk body was reported as working  -- ok=True detail=HTTP ok (empty body parsed)
```

管理员会因此去查密钥、查模型名，而问题其实在端点本身。修法：`ok` 要求 **2xx 且正文里有可识别的模型回复**
（OpenAI 的 `choices` 或 Anthropic 的 `content`），否则 `ok: false` 并给出原因与正文片段：

```
PASS  a 200 with an unparseable body is NOT reported as working
      -- detail=HTTP 200 but the body carries no model reply (de…
=== PROVIDER PROBE: PASS=13 FAIL=0 ===
```

`status` 仍如实保留 200 便于诊断——**"状态码"与"结论"是两件事**，本轮把这个区别钉进了测试。

## 这一阶段的小结

第 49 到 58 轮这一串抽查的共同主题是**"系统对外说的话要可信"**：错误消息不能只剩 `"1"`（49）、
"包含实例文件"要说清会覆盖什么（52）、`ok` 不能只看状态码（58）。功能都在，坏的是**表达**——
而表达正是使用者据以行动的东西。
