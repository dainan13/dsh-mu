# M1 实测报告 — dsh-mu 隔离与资源原语

> 目标机：`dsh-mu` = 192.168.13.61，Alpine 3.24.1 LXC（特权容器），内核 7.0.14-19-pve
> 探针：`tests/m1-probe.sh`（可重复执行）
> 结论：**jail（mount ns + chroot）+ cgroup v2 限额方案在目标机上可行**，但有 3 处必须适配的坑。

## 1. 结论速览

| 能力 | 结果 | 证据 |
|---|---|---|
| `unshare --mount --uts --propagation private` | ✅ | 探针 T3/T4/T5 全程在私有 mount ns 内挂载，宿主未受影响 |
| `chroot` 进入独立 rootfs | ✅ | T3 |
| cgroup v2 `memory.max` | ✅ **真实生效** | T1a：192MB 组内分配 512MB → `oom_kill=1`，进程 rc=137 |
| cgroup v2 `pids.max=32` | ✅ **真实生效** | T1b：第 31 个子进程后无法再 fork |
| cgroup v2 `cpu.max=50000 100000` | ✅ **真实生效** | T1c：同一份固定计算，组外 271ms vs 组内 474ms（≈0.53 核） |
| 实例进程落入指定 cgroup | ✅ | T5：`cgroup.procs` members=2 |
| `apk add --root --initdb` 生成 rootfs | ✅ | T2：18MB（含 util-linux + bubblewrap） |

| jail 内 `apk add` 隔离 | ⚠️ 待 M2 | 探针用的 `hello` 包在 v3.24 不存在（`no such package`），非隔离问题 |

## 2. 必须适配的三个坑

### 坑 1：cgroup 控制器无法直接委派（EBUSY）

容器内 `/sys/fs/cgroup` 是 cgroup2 rw，但 cgroup namespace 根**不是层级根**，而是宿主上的一个普通 cgroup：

```
$ cat /sys/fs/cgroup/cgroup.procs      # 4 个进程：PID 1 + 3 个 getty
1 411 412 413
$ echo "+cpu +pids" > /sys/fs/cgroup/cgroup.subtree_control
sh: write error: Resource busy
```

内核的"无内部进程"约束因此生效，子组里根本不会出现 `cpu.max/pids.max`。

**解法**（已实现为 `dsh-mu-cgroup-init`，幂等）：把根组里的进程挪进 `/sys/fs/cgroup/init` 占位组 →
根组变空 → 打开 `subtree_control` → 委派给 `/sys/fs/cgroup/dsh-mu`。

```
$ sh /usr/local/sbin/dsh-mu-cgroup-init
dsh-mu-cgroup: root=[cpu io memory pids] tree=[cpu io memory pids]
$ ls /sys/fs/cgroup/dsh-mu/t1 | grep -E 'cpu.max|memory.max|pids.max'
cpu.max  memory.max  pids.max
```

因为 cgroup 状态不跨重启保留，这一步由 OpenRC 服务 `dsh-mu-cgroup`（runlevel `boot`）在每次开机执行，
每个实例服务都 `need dsh-mu-cgroup`。

### 坑 2：`apk --root` 需要显式 `--keys-dir`，且 jail 内要自带签名密钥

```
$ apk add --root $R --initdb busybox
WARNING: fetching .../community/x86_64/APKINDEX.tar.gz: UNTRUSTED signature
ERROR: unable to select packages: busybox (no such package)
$ apk add --root $R --initdb --keys-dir /etc/apk/keys busybox     # ✅
```

构建模板时额外把宿主 `/etc/apk/keys/*` 复制进 rootfs 的 `/etc/apk/keys/`，
否则 jail 内的 `apk add` 也会因 UNTRUSTED signature 失败（这正是"apk 环境隔离"能不能用的前提）。

### 坑 3：`/sbin/init` 与 console getty 常驻根 cgroup

它们会随 getty 重启反复出现在根组。委派完成后（`subtree_control` 已写入）再出现的进程不影响委派，
但**委派动作本身要求根组为空**，所以 `dsh-mu-cgroup-init` 必须在实例启动前跑（`need dsh-mu-cgroup` 已保证）。

## 3. 其它实测事实

| 项 | 值 |
|---|---|
| 容器能力 | `CapEff=000001ffffffffff`（全量 capability），所以能 `unshare`/`mount`/`chroot` |
| 可用控制器 | `cpuset cpu io memory hugetlb pids rdma misc dmem` |
| 磁盘 | 根盘 11.1G 可用；模板 rootfs（alpine-base+bash+git+util-linux+curl+bubblewrap+nodejs+npm+pnpm）实测占用见 M2 |
| 已装（平台级） | openresty 1.31.1.1、node 24.18.1、npm、pnpm 11.20.0、python3 3.14、util-linux、lua-resty-{string,hmac,openssl}、dsh 0.2.0-rc.2 |
| openresty Lua 能力 | 自带 `cjson.so`（`/usr/lib/nginx/lualib/cjson.so`）、`resty.sha256`/`resty.hmac`；`lua-resty-openssl` 提供 `resty.openssl.kdf`（scrypt/PBKDF2） |
| nginx 用户 | `uid=100(nginx) gid=101(nginx)` → 网关状态文件用 `0640 root:nginx` 即可被 worker 读取 |
