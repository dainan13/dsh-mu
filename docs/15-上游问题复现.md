# DSH subprocess runner 在 mount-namespace jail 内失败（已定位并修复）

> 这是**给上游（DSH）**的最小复现包。本平台的分层/隔离本身没有问题，
> 现象只在"进程处于一个我们自己创建的 mount namespace + chroot 里"时出现。

## 现象

`ctx.subprocess.spawn({ argv: ["bash","-c","echo hi"], … })` 在 jail 内抛
`SubprocessExecutableNotFoundError`，上层渲染成 `Error: spawn bash ENOENT`。

## 环境

- Alpine 3.24，kernel 7.0.14（PVE 容器内），musl
- Node v24.18.1，`@deepseek-ai/dsh` 0.2.0-rc.2，`dsh-subprocess-local` 与 `koffi 3.1.1` 正常加载
- jail：`unshare --mount --uts` + chroot + cgroup v2；能力集 `sys_admin,setuid,setgid`
- **对照组**：同一套 runtime、同一次调用，在**普通 chroot**（无 jail）里成功

## 复现（30 秒）

```sh
node tests/dsh-subprocess-repro.mjs
```

| 位置 | 输出 |
|---|---|
| 普通 chroot | `OUTCOME: {"exitCode":0,"signal":null}` |
| jail 内 | `SPAWN FAILED: Error \| spawn bash ENOENT` |

## 已排除的假设（都有实测）

| 假设 | 结论 |
|---|---|
| 没有 bash | 否：`/bin/bash` 存在、可执行，`bash -c 'echo ok'` 直接跑成功 |
| PATH 缺失 | 否：`scrubbedParentEnv()` 保留 `/usr/local/sbin:…:/bin`；纯 node `spawn("bash")` 在 inherit / 无 PATH / minimal / 绝对路径四种情况下都成功 |
| cwd 不存在 | 否：`cwd` 为可写目录，且用 `cwd` 的 spawn 也成功 |
| 能力不足 | 否：加 `CAP_SYS_PTRACE` 后仍失败（已回滚） |
| bwrap/沙箱 | 否：`bwrap --dev-bind / / echo` 在 jail 内 `BW-OK` |
| koffi/原生绑定 | 否：`koffi OK 3.1.1` |
| tmpdir 不可写 | 否：`os.tmpdir()=/tmp`，`mkdtempSync` 成功 |

## strace 证据

`strace -f -e trace=execve` 显示：父进程正常 `execve("/usr/bin/node", …)` 后，
**两个子进程以 127 退出，且日志里没有任何一次 `execve("bash", …)`** ——
说明失败发生在 **runner bootstrap 阶段、`execve` 目标之前**。

## 我们的判断

`LocalSubprocessRuntime.resolveExecutable()` 只在**子进程 env** 的 PATH 里找候选路径
（`resolve(process.cwd(), PATH_entry, command)`），找不到就抛 `SubprocessExecutableNotFoundError`；
而真正的失败原因由 runner 写入 launch 文件、父进程用 `readLinuxStartupError()` 读回后丢弃，
所以调用方只能看到 `spawn bash ENOENT` —— **这个错误名会误导排障方向**。

建议上游：把 `readLinuxStartupError()` 的内容附加到抛出的错误上（如 `err.cause`），
这样"找不到可执行文件"与"runner 启动失败"就能区分开。

## 二分进度（0.8.5，每步用同一份复现脚本）

| 追加条件 | 结果 |
|---|---|
| 普通 chroot（网关 rootfs） | 成功 |
| 普通 chroot（**实例 rootfs** + bind 运行时） | 成功 |
| `+ unshare -m`（新 mount namespace） | 成功 |
| `+ --no-new-privs` | 成功 |
| `+ 实例的精确能力集` | 成功 |
| `+ 新挂载的 procfs` | 成功 |
| `+ 只读（ro）bind 运行时` | **疑似挂起/失败** ← 当前最强嫌疑 |
| 真实 jail（`dsh-muctl instance exec`） | 失败 `spawn bash ENOENT` |

**下一步（5 分钟）**：把 jail 里运行时的 bind 从 `ro` 改为 `rw` 再测一次。

- 若 rw 后成功 → 说明 runner 需要在其**自身包目录**下写临时/启动文件；
  修法：ro 挂载 + 对需要的子目录套一层 tmpfs（而不是整体放开为 rw，避免实例改写共享运行时）。
- 若仍失败 → 继续加 `/sys`(ro) / `/dev`(tmpfs) / 自身 bind / cgroup 逐项二分。

### 追加排除（0.8.9）

| 条件 | 结果 |
|---|---|
| 运行时 bind 改为 **rw**（0.8.7 实验） | 仍失败 → 不是只读挂载 |
| **关闭 jail 的 self-bind**（`DSHMU_SELF_BIND=0`，0.8.9 加了开关） | 仍失败 → 不是 `/` 的挂载点语义 |

剩余未测项（按嫌疑排序）：

1. **`/dev` tmpfs**（jail 自建 `/dev`，runner 可能依赖 `/dev/shm`、`/dev/null` 的语义）
2. `/sys` 只读 bind + rslave
3. `/home/dsh` 从 `$INSTANCES/<name>/home` bind
4. **cgroup 归组**（jail 把进程放进 `dsh-mu/<name>`，而所有成功的对照实验都没进 cgroup）
5. `unshare --uts --fork` 的组合（单独 `-m` 已排除）

其中 **4（cgroup）** 目前嫌疑最高：所有成功的对照实验都在宿主默认 cgroup 里。

`jail/dsh-mu-jail` 里保留了一个开关：`DSHMU_SELF_BIND=0` 可关闭 self-bind（默认 1 = 现有行为），
方便下一次二分时直接 A/B，不必重新打包。

## 结论：已定位并修复（0.9.1）

**根因**：jail 自建的 `/dev` tmpfs（只有手工 `mknod` 的几个节点）缺少 DSH runner 需要的
完整设备视图（`/dev/pts`、`/dev/fd` …），runner 起不来，错误被包装成
`SubprocessExecutableNotFoundError` → `spawn bash ENOENT`。

**修复**：`jail/dsh-mu-jail` 里把 `/dev` 改为**只读 bind 宿主 `/dev`**（实例无法 unlink 节点，
安全性质保留），验证：真实 jail 内同一复现脚本返回 `{"exitCode":0,"signal":null}`。

**给上游的建议仍然成立**：把 `readLinuxStartupError()` 的内容挂到抛出的错误上，
"runner 启动失败"与"可执行文件不存在"就不该共用一个错误名。
