# 设计备忘：把「套餐 / 模型 / key」从网关配置文件改成查询式

状态：**待做（UI 改造完成后再动）** 记录时间：2026-11-07

## 1. 现在的问题（实测确认）

模型请求的凭据链路是：

```
实例 (只有 relay token) → 网关 127.0.0.1:8099/mu-llm/<token>/plan-xxxx
                        → 网关按 relay.json 里的 route 注入上游 key
```

`relay.json` 由 `render_gateway()` 在每次 sync 时整份重写（`write_relay_document`），
然后由网关进程**读进内存**（启动/init 阶段）。

于是出现一个不该有的耦合：

* 文件层面：改 key 后 `relay.json` 立刻是对的（host 与 gateway jail 两份都同步）。
* 生效层面：**网关进程不会重读**，旧 key 继续可用。
  * `rc-service openresty reload` 只换 worker，不足以刷新 init 阶段加载的表。
  * 只能 `restart` 网关 —— 这会让所有实例的模型请求中断 1–2 秒。

结论：**把"凭据/模型清单"当成"配置"塞进文件、再让长驻进程缓存，是设计缺陷**，
不是实现 bug。任何"改了就生效"的需求都会被这一层卡住（key、模型子集、配额、路由都同理）。

## 2. 目标形态：查询式

```
网关 (relay) 每次请求（或带短 TTL 的缓存）→ 查询 KV/状态存储
    token → user → plan → { upstream, auth, key, models }
```

要点：

1. **单一事实来源**：套餐、key、模型子集、可用性探测结果只存一处（平台状态或 sqlite/kv），
   `relay.json` 退化为"启动时的引导信息"（监听地址、占位符）或直接取消。
2. **写操作不碰网关进程**：新增/修改/删除套餐、换 key、改模型子集 = 只写存储，立即对下一次请求生效。
3. **缓存策略**：网关侧每请求读 + 进程内 TTL 缓存（如 1–5 秒），或存储变更时发一个"版本号"，
   网关比对版本号再重载 —— 避免每请求落盘。
4. **可观测**：`/api/health` 里暴露"relay 缓存版本"，doctor 增加一行
   `relay cache version matches state`（防止再次出现"文件新、进程旧"的静默不一致）。
5. **兼容**：过渡期保留 `relay.json` 生成（供旧版本网关读取），但网关优先查存储。

## 3. 明确不要做的事

* 不要靠"改完配置就 restart 网关"当常规手段（会中断所有实例）。
* 不要把 key 写进实例 patch（现在也没这么做，保持）。
* 不要让"生效"依赖实例重启 —— 实例只持有 token，与本议题无关。

## 4. 判定完成的标准

| 场景 | 期望 |
| --- | --- |
| 改 key | 下一次模型请求即生效，网关不重启，实例不重启 |
| 改模型子集 | 实例页 F5 即生效（当前已满足，改造后保持） |
| 新增/删除套餐 | 秒级返回，无进程重启 |
| doctor | 能查出"存储与网关缓存不一致" |

## 5. 临时手段（在改造前）

目前 `plan_key` 写操作会 **restart 网关**（中断约 1–2 秒）以让新 key 生效；
`plan_models` / `plan_add` / 顺序 / 默认链只做 sync（不重启），因为实例侧走 patch，
用户 F5 即可见。改造完成后这些临时手段全部删除。
