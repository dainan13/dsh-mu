# dsh-mu 运维手册（Runbook）

> 面向"接手这台机器的人"。前置：`docs/05-打包与安装.md`（怎么装）、`docs/02-架构设计.md`（怎么设计的）。
> 所有命令都需要 root；`dsh-muctl <子命令> --help` 有完整参数说明。

## 0. 一分钟体检

```sh
dsh-muctl doctor                 # 30+ 项（随实例数增长）：内核/容器能力、cgroup 委派、apk keys、镜像、nginx 集成、
                                 # 运行态一致性、记录一致性（悬空实例/缺目录）、管理员账号、日志轮转
dsh-muctl doctor --json | jq .summary
dsh-muctl doctor --fix           # 可修的直接修（cgroup 服务、nginx 运行时依赖、拉起该跑的实例、纠偏状态）
```

隔离边界（在活着的实例里逐条断言，含跨租户探测）：

```sh
sh /usr/local/lib/dsh-mu/tests/isolation.sh <实例>          # 20 项，PASS/FAIL 明细
sh /usr/local/lib/dsh-mu/tests/isolation.sh <实例> --json
```

故障与恢复（会短暂停服务，结束前自动恢复）：

```sh
python3 /usr/local/lib/dsh-mu/tests/failure-modes.py --user <用户> --password <口令> --instance <实例>
```

CLI 契约（改过 `dshmuctl.py` 的命令/参数后必跑，秒级）：

```sh
sh /usr/local/lib/dsh-mu/tests/cli-contract.sh <实例>   # 34 项：错误必须干净、只读必须成功
```

管理 API 契约（改过 `admin/dsh-mud` 的路由或校验后必跑）：

```sh
python3 /usr/local/lib/dsh-mu/tests/api-contract.py --instance <实例>   # 35 项
```

界面自洽性（改过 `admin/index.html` 或面板后必跑，秒级）：

```sh
node /usr/local/lib/dsh-mu/tests/ui-lint.mjs /usr/src/dsh-mu   # 或任何源码树路径
```

持续负载（怀疑内存/句柄泄漏、或上线前压一压）：

```sh
python3 /usr/local/lib/dsh-mu/tests/soak.py --minutes 10 --workers 6 --user <用户> --password <口令>
# 断言：后端未被重启、nginx worker 数不变、RSS 预热后无上升趋势（≤1MB/min）、fd 不增长、零 5xx
```

一键盘点（本机全部验收层 + 干净 Alpine 排练）：

```sh
sh /usr/local/lib/dsh-mu/tests/regression.sh --user <某用户> --password <口令> --instance <实例>
# 或在源码目录： sh tests/regression.sh …           加 --fast 可跳过 chroot 排练
```

## 1. 日常对象

| 对象 | 查看 | 创建 | 修改 | 删除 |
|---|---|---|---|---|
| 用户 | `dsh-muctl user list` | `dsh-muctl user add <名> --password … [--instance auto\|none\|<实例>]` | `user passwd` / `user enable\|disable` | `user del <名>` |
| 实例 | `dsh-muctl instance list` | 建用户时自动建，或 `instance create <名> --user <用户>` | `instance port` / `instance limits` / `instance provider` / `instance api-key` | `instance del <名> [--purge]` |
| 模型接入 | `dsh-muctl provider list` | `provider add` / `provider import` | `provider model` / `provider header` | `provider del` |
| 管理员 | `dsh-muctl user list`（`role=admin`） | 由宿主系统账号 + `ADMIN_SYSTEM_USERS` 决定 | `dsh-muctl config admin_system_users …` | 同上 |

要点：

- **管理员不是平台账号**：`root`（或 `ADMIN_SYSTEM_USERS` 里列出的系统账号）用**宿主系统口令**登录 `/admin/`。
  系统账号没有口令时 `doctor` 会报 FAIL（`passwd <账号>` 即可）。平台账号一律普通用户。
- `user add --instance none` 表示"这个账号不配实例"（登录后看到"实例不存在"提示页）。
- 改口令/密码会推进会话 epoch，**旧会话立即失效**；`--must-change` 只是给用户面板的提示，不是登录锁。
- **强制下线某人的所有会话但不改口令**：`dsh-muctl user kick <名>`（页面用户表的「踢下线」按钮、
  `POST /api/users/<名>/kick` 同效）。它会推进 epoch 并**留下审计记录**（`user.change`，含 epoch 变化）。
- 实例限额对外是"核数 / MB / 进程数 / 不限"，运行中改**立即生效**：`dsh-muctl instance limits <实例> --cpu 2 --mem 2048 --pids 512`。
- 实例端口：`dsh-muctl instance port <实例> --port 3200 --restart`（`--auto` 自动挑空闲端口，`--dry-run` 只看）。

## 2. 用户侧

- 登录 `http://<主机>/`，**登录即自动拉起实例**（未就绪时显示"实例正在启动"，3 秒自刷新）。
- 左侧边缘的角色图标（面板）：实例信息、启动实例、修改密码、退出登录。
- 用户拿到的地址就是宿主地址；每用户一个 loopback 端口，网关按会话转发，用户互相看不到。

## 3. 变更与发布

```sh
# 网关/服务
dsh-muctl gateway install          # 幂等：渲染片段、nginx -t、失败回滚、reload
dsh-muctl gateway status
dsh-muctl sync                     # 重渲染网关视图（users/upstreams/config.json）
dsh-muctl admin restart            # 后端脚本改了之后必须重启（它在 import 时缓存库）

# 升级
apk add --allow-untrusted dsh-mu-<新版本>-r0.apk
dsh-muctl install                  # 会重装/补齐依赖、重建模板、重装片段、重启后端、跑 doctor
dsh-muctl doctor
```

数据（`/etc/dsh-mu`、实例数据、模板）在 `apk del`/升级中**始终保留**。

## 4. 备份与恢复

```sh
dsh-muctl backup --out /var/backups/dsh-mu-$(date +%F).tgz            # 记录（0600，含密钥）
dsh-muctl backup --out /a.tgz --with-instances                        # 另加各实例 home
dsh-muctl restore /var/backups/dsh-mu-2026-10-16.tgz --dry-run        # 只看计划
dsh-muctl restore … --force                                           # 执行；先存 <ETC>.bak-<ts>.tgz
```

管理页「平台」标签也能下载备份。恢复后建议：`dsh-muctl doctor` → `dsh-muctl gateway install` → 对需要的实例 `instance restart`。

备份**包含**每个实例的两个持久卷：`home/`（DSH_HOME：会话、凭据、profile）**与 `workspace/`**
（用户实际写文件的工作区，jail 内挂载在 `/home/dsh/workspace`）。**不含** `rootfs/`（每个 140MB 的根文件系统
副本）——所以备份通常很小，但也意味着恢复后实例的 rootfs 需要重建。

恢复前先看体检报告：`dsh-muctl restore <归档> --dry-run` 会**逐个点名将被写入的卷**并标注
`OVERWRITES live data`，归档比现网旧时还会提醒（那意味着会丢掉比它更新的改动）。

恢复时平台会按**记录**重新设定实例卷（`home/`、`workspace/`）的属主——即使归档来自换过 uid 的机器，
恢复后实例依然能写自己的目录（tar 只会还原归档里记录的属主，不能作数）。

网关（jail 模式，默认）常用命令：`dsh-muctl gateway jail-status`（是否在答）、`gateway logs`、
`gateway conf`（重渲染配置）、`gateway restart`；配置在 `/var/lib/dsh-mu/gateway/conf`，
日志在 `/var/log/dsh-mu/gateway*.log`。有特殊需求的用户可以把 `gateway/conf` 整份抄走，
用自己装的 http 服务加载（那就别再启动平台 jail）。

**灾难恢复演练**（不是"我们备份了"，而是"演练过恢复"）：`tests/fresh-rehearsal.sh` 的第 9 步会在干净
Alpine 里建账号+实例 → 备份 → **删掉整个 `/etc/dsh-mu`** → 重装 → `restore --force`，并断言口令散列/端口、
会话密钥、网关视图、实例 home 文件、安全副本都回来了；随后第 10 步的运行时冒烟就跑在恢复后的平台上。
想单独演练恢复，可在任意机器上照这个顺序手工做一遍（备份务必先复制到机器之外）。

## 5. 故障对照表

| 现象 | 先看 | 常见原因与处理 |
|---|---|---|
| 管理页打不开（后端挂了） | `rc-service dsh-mud status`、`dsh-muctl admin status` | 后端没跑：`dsh-muctl admin restart`；网关对**管理员会话**会直接给出带修复命令的提示页（502/503→`@gw_admin_down`）。匿名访问只会被送去登录页，属正常 |
| 登录页打不开 | `dsh-muctl gateway status`、`tail /var/log/dsh-mu/gateway.err.log` | nginx 没起：`rc-service openresty start`；配置坏：`nginx -t` 后 `dsh-muctl gateway install` |
| 登录失败（401） | `dsh-muctl user list` | 口令错，或账号被 disable。管理员（系统账号）另需确认**系统口令已设置**（`passwd root`） |
| 提示"实例不存在" | `dsh-muctl instance list`、`doctor` | 该账号 `instance=none`，或实例被删（`instance create` 重建并 `user set-instance`） |
| 卡在"实例正在启动" | `dsh-muctl instance status <名>`、`journalctl`/`/var/log/messages`、`dsh-muctl logs dir` | jail 起不来（模板缺文件、cgroup 没委派：`dsh-muctl doctor --fix`）；端口被占：`instance port --auto` |
| 页面一直 502/503 | `dsh-muctl instance status`、实例服务 `rc-service dsh-mu-<名> status` | 实例进程崩了：`instance restart`；`cgroup.kill` 清残留见 `instance stop` |
| 模型报"api key invalid" | `dsh-muctl instance-patch <名>`、`provider list` | 实例没有凭据：`instance api-key`；或 provider/模型不对：`instance provider` |
| 管理页 403 | 用哪个账号登录 | `/admin/` 只认 `ADMIN_SYSTEM_USERS` 里的系统账号 |
| 限额/端口记录与运行态不一致 | `dsh-muctl doctor`、`dsh-muctl instance limits <名>` | 记录里的 `cpu_max/mem_max/pids_max` 必须是 `max`/`<n>`/`<quota> <period>`；doctor 会点名并给修复命令（改完立即写入 cgroup 生效） |
| 磁盘涨 | `dsh-muctl logs size`、`du -sh /var/lib/dsh-mu/*` | 日志：`logs rotate`；实例 rootfs：`instance del --purge` 重建 |
| 用户面板图标/浮层不出现 | 浏览器强刷；`curl -I http://127.0.0.1/mu-static/panel.js` | 静态资源没装：`apk add --allow-untrusted …` 重装或 `dsh-muctl install` |

## 6. 安全清单（正式使用前）

```sh
passwd root                                  # 管理员必须有强口令
dsh-muctl user passwd alice                  # 换掉测试口令（alice/bob/ops 是测试账号）
dsh-muctl user del ops                       # 不需要就删
shred -u <任何存过密钥的临时文件>
dsh-muctl backup --out /root/dsh-mu-first.tgz && chmod 600 /root/dsh-mu-first.tgz
```

- 网络边界：网关只应暴露必要端口（80/443）；`/mu-api/`、`/mu-internal/` 仅回环，且 `/mu-api/` 现在还要求共享令牌。
- 跨站防护：会话 cookie 为 `HttpOnly; SameSite=Lax`，登录有双提交 CSRF，写操作还有同源栅栏
  （跨站 `POST` → 403）。要确认它仍在生效，跑 `node tests/selftest.mjs`（5f 四条）。
- 密钥：`/etc/dsh-mu/secret.key`、`admin.token`、实例凭据库均 `0600/0640`，不要贴进工单或聊天。
- 实例以 `danger-full-access` 运行（LXC 无 userns/landlock），**jail 就是边界**：不要给用户宿主目录挂载。

## 会话与管理界面的几个开关（0.13.0）

| 项 | 怎么调 | 说明 |
|---|---|---|
| **会话空闲过期** | `dsh-muctl config session_idle_minutes 1440` + `gateway restart` | 默认 **1440（24h）**；`0` 关闭。空闲到期后浏览器下一次请求会被拒（`/me` 返回 401 / 页面跳登录） |
| **实例日志实时刷新** | 后台「实例」→ 实例日志 → 勾选 **实时刷新** | 2 秒轮询；**标签页不可见时自动暂停**；读失败会自动关掉，避免打爆后端 |
| **用户面板资源占用** | 无需配置 | 抽屉「我的实例」显示 **内存（已用/上限）· CPU% · 进程数**，来自 cgroup v2；**只在抽屉打开时**每 5 秒刷新 |

> 会话空闲验证方法（想复现时）：`config session_idle_minutes 1` → `gateway restart` → 登录后静默 75 秒
> → 访问 `/me` 得到 **401** → 再设回 1440。

### 实例日志为什么可能是空的

`logrotate` 用的是 **copytruncate**（服务持有日志描述符，不能 rename 走），所以轮转瞬间
`/var/log/dsh-mu/<实例>.log` 会变成 **0 字节**，历史在 `.log.1` / `.log.2.gz` 里。

后台的日志视图因此会：

1. 实时文件有内容 → 直接显示（`source=live`）；
2. 实时文件为空但有轮转文件 → **自动回落**读 `.1`/`.2`/`.gz`，并在顶部写明"已轮转"；
3. 两者都空 → 显示**文件路径、字节数、最后修改时间、原因**，不再是空框。

命令行等价：`dsh-muctl logs <实例>`，或直接 `tail -n 200 /var/log/dsh-mu/<实例>.log`。

## UI 约定：先按钮、后表单（0.18.4 起）

后台与用户抽屉里，凡是**新增 / 修改**类操作，都必须：

1. 界面上只放**一个按钮**（「＋ 创建 X」/「设置」/「修改」）✓，并**显示当前状态** ✓
   （例如"未设置（新会话按平台默认：Kilo Free）"或"已设置：myog · glm-5.3"）；
2. 点按钮才**弹出对话框** ✓，表单在对话框里 ✓；
3. 用户点「保存」才提交 ✓，取消 / 遮罩 / 关闭都**不改变任何东西** ✓。

理由：把表单平铺在页面上时 ✓，用户看不出"我到底设过没有"✓（预填值看起来像已设置 ✓），
也容易误以为改动已经生效 ✓。这一条在 0.18.3 的「我的默认模型」上踩过 ✗（当时是平铺的 ✓）。

## 实验记录：jail 加固两项（2025-10 实测，尚未产品化）

两项都在真机上跑过全项验证 ✓，但**目前是手工状态**（配置改了、规则是我临时加的 ✓），
还没有纳入 `dsh-muctl` ✓。结论如下。

### A. 去掉实例的 `CAP_SYS_ADMIN`

配置：`INSTANCE_KEEP_CAPS=""`（原来是 `sys_admin,setuid,setgid`）。

| 检查项 | 结果 |
|---|---|
| 实例进程 `CapEff` | `0000000000000000` ✓（完全无能力） |
| DSH 启动 / cookie 刷新 | 正常 ✓ |
| 模型调用（relay `/models`） | 200 ✓ |
| `node` / bash 工具 / 文件系统 | 正常 ✓ |
| 插件安装（`pnpm add`） | 成功 ✓ |
| 插件仍在（alice 的 native 插件） | 列表正常 ✓ |
| 只读挂载内 `echo >` / `rm` | **Read-only file system** ✓ |
| 只读挂载内 `umount` | **must be superuser to unmount** ✓ |
| 实例内 `mount -t tmpfs` | **permission denied** ✓ |

→ 结论：**去掉 `sys_admin` 不影响 DSH** ✓，而且**只读挂载的保护从此是真的** ✓
（之前能 `umount` 绕过 ✗）。

### B. nftables 按 cgroup 匹配的出网策略（N2）

依赖：宿主需要 `nftables`（`apk add nftables` ✓，**不在 dsh-mu 依赖里** ✗）。
规则挂在 `table inet dshmu` ✓，用
`socket cgroupv2 level 2 "dsh-mu/<实例>"` 区分实例 ✓。

实测矩阵（bob 挂了规则 ✓，alice 作为对照 ✓）：

| 目标 | bob（有规则） | alice（无规则） |
|---|---|---|
| 自己的端口 `127.0.0.1:3101` | OK ✓ | — |
| relay `127.0.0.1:8099` | OK ✓ | — |
| 另一个实例 `127.0.0.1:3100` | **BLOCKED** ✓ | OK ✗（说明规则必须覆盖所有实例） |
| admin API `127.0.0.1:8787` | **BLOCKED** ✓ | OK ✗ |
| 内网网关 `192.168.13.61:80` | **BLOCKED** ✓ | — |
| 内网路由器 `192.168.13.1:80` | **BLOCKED** ✓ | — |
| `registry.npmjs.org` | 200/405 ✓ | — |
| 宿主 → bob 的端口 | 401，**0.9ms** ✓ | — |

两个必须注意的实现细节 ✗：

1. **必须有 `ct state established,related accept`** ✓ —— 只按 `dport` 匹配会把实例自己的**回包**
   （dport = 对端临时端口）挡掉 ✗，表现为"端口在听但连不上"✗（我第一次就是这么错的 ✓）；
2. **DNS 必须显式放行** ✓ —— 实例的 `resolv.conf` 指向内网 `192.168.13.1` ✓，
   否则插件装不了 ✓。长期建议在网关里跑本地 DNS 转发 ✓，实例只连 `127.0.0.1:53` ✓。

## 实例出网策略（0.19.0 起，默认禁内网）

```ini
INSTANCE_EGRESS="no-intranet"          # open | no-intranet | allowlist
INSTANCE_EGRESS_ALLOW="10.1.2.3:443"   # 白名单/豁免，可带端口
```

```sh
dsh-muctl egress show                                  # 每实例生效策略 + 全部实例规则
dsh-muctl egress set no-intranet                       # 新实例的默认策略
dsh-muctl egress allow-add --allow '10.0.0.0-10.0.0.9:10000-11000'   # 全部实例共享规则
dsh-muctl egress allow-rm  --allow '10.0.0.0-10.0.0.9:10000-11000'
dsh-muctl egress instance alice allowlist --allow 10.0.0.7:5432      # 单实例
dsh-muctl egress instance alice --reset                              # 回到默认
dsh-muctl sync                                                       # 渲染并原子装载 egress.nft
```

三档策略（实例表格里**只读显示**，修改只在实例行的「配置」里 ✓）：

| 策略 | 公网 | 内网 | 「出网特殊规则」里的目标 |
|---|---|---|---|
| **全限制**（`allowlist`） | 拒 ✗ | 拒 ✗ | **只允许这些** ✓ |
| **禁内网**（`no-intranet`，默认 ✓） | 放行 ✓ | 拒 ✗ | **例外放行** ✓ |
| **不限制**（`open`） | 放行 ✓ | 放行 ✓ | 不生效 ✓ |

目标写法 ✓：`ip`、`ip/24`、`ip1-ip2`，每种都能带 `:443` 或 `:10000-11000`
（IPv6 带端口写 `[2001:db8::1]:443` ✓）；规则里的实例可以选 **全部实例** ✓（并入每个实例 ✓）。

后台交互 ✓：实例行「配置」里选策略 ✓、「出网特殊规则」卡片里加/删目标 ✓
（都是**按钮 → 弹窗 → 确认** ✓）。改完**立即重载 nft 表** ✓，不需要重启实例 ✓。

要点：
- `nftables` 自 0.21.3 起是 **apk 依赖** ✓（随包安装 ✓，不用手动装 ✓），`doctor` 会检查 ✓；
- 每条链都以 `ct state established,related accept` 开头 ✓ —— 少了它会连回包一起挡掉 ✗；
- DNS 服务器（实例 `resolv.conf` 里的）自动放行 ✓，否则插件装不了 ✓；
- 内核需要 ≥ 5.13（`socket cgroupv2` 匹配）✓；本项目实测在 7.0 内核上 ✓。

## 插件：先下载，再配策略（0.25.0 起）

平台**不代管"谁能装什么"** ✓ —— 用户在自己的 DSH 界面里装 ✓。平台的职责是：
**把要分发的插件先下载好** ✓，然后决定它"删不掉 / 新实例预装 / 推给已有实例"✓。

### 三个开关（后台「插件」页 / CLI）

| 开关 | 生效时机 | 效果 |
|---|---|---|
| **受保护** | 需要**重启实例** | `node_modules/<pkg>` 在 jail 内只读绑定 ✓（内核 EROFS ✓）；`sync` 补回依赖与 bundle ✓、清掉 `disabled: true` ✓。删不掉、停不掉 ✓ |
| **预装** | **新建实例**时 | 只有创建实例才装 ✓（已有实例重启**不会**补装 ✓） |
| **推送** | `sync` 与**每次重启** | 推给已有实例 ✓，并在此后每次启动时补齐 ✓（用户删掉也会在重启后回来 ✓） |

### 添加插件（会先下载）

```sh
dsh-muctl plugin add @scope/pkg[@version]      # npm
dsh-muctl plugin add github:owner/repo[#ref]   # GitHub
dsh-muctl plugin add is-odd --proxy http://127.0.0.1:7890   # 走代理下载
```

- 下载后从 tarball 的 `package/package.json` 解析出**真实包名与版本** ✓
  （`github:` 规格也会变成正常包名 ✓，不再出现"规格/包名对不上"✗）；
- **一个包只占一行** ✓：再添加同名包 = **替换**（旧 tarball 与元数据一起删 ✓）；
- 失败不会产生任何记录 ✓，报错里有 `curl exit=N` + curl 原文 ✓ + 环境代理 ✓；
- 默认代理：`dsh-muctl config download_proxy http://host:port` ✓（页面填的优先 ✓）；
- 连不上时先跑 **`dsh-muctl plugin check`** ✓（分别探测 registry 镜像与 github ✓）。

### 其余命令

```sh
dsh-muctl plugin list                          # 包 + 版本 + 来源 + 三个标志
dsh-muctl plugin protect|unprotect   <包名>
dsh-muctl plugin preinstall|unpreinstall <包名>
dsh-muctl plugin push|unpush         <包名>
dsh-muctl plugin remove <包名> [--delete-asset]   # 移除策略（可选删离线包）
dsh-muctl plugin check                          # 下载链路自检
dsh-muctl plugin cached                         # 已下载的包/缓存报表
```

### 后台页面

- 表里只列**已下载**的插件 ✓ —— 所以"没下载却能勾策略"这种状态不存在 ✓；
- 「添加插件」弹窗只填**规格** + 可选**下载代理** ✓（不做任何策略决定 ✓）；
- **实例列只显示 ■ / □** ✓（■ 已装 ✓，名称在悬浮提示里 ✓）；**点整块**把下面的
  「各实例已装插件」筛到**这个插件** ✓，再点取消 ✓；
- 操作：**更新**（按该行来源重新下载 ✓）/ **移除策略**（保留离线包 ✓）/ **移除并删包** ✓。

### 安装怎么落地（离线）

`plugin add` 下载的 tarball 存在宿主 `/var/lib/dsh-mu/plugin-cache/` ✓；安装时**拷进实例
home** 的 `~/.cache/dsh-mu-plugins/` ✓，再用 `file:` 装 ✓ —— **插件本体不联网** ✓
（它自己的依赖仍走 npm 镜像 ✓，内网需要就配 `download_proxy` 或换镜像 ✓）。

### doctor 相关检查

| 检查 | 含义 |
|---|---|
| `plugin packages` | 下载了几个离线包 ✓ |
| `plugin policy` | 策略是否有对应离线包 ✓；`推送` 是否在所有实例落地 ✓ |
| `admin backend` | 后台进程是否在跑**磁盘上的新代码** ✓（旧了 `sync` 会自动重启 ✓） |
| `nginx temp dirs` | 网关 jail 里的 `/var/tmp/nginx/{client_body,…}` ✓（缺了上传会 500 ✗） |
