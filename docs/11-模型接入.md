# 11 · 模型接入：provider / 套餐 / 实例

> 状态：**provider 配置文件（导入/导出/校验/列模型/查配额）已实现并在真机验证**；
> 「套餐」层与管理后台的界面是下一步（设计已定，见 §4）。

## 0. 给 AI 的提示词（自包含）

`dsh-muctl provider spec` 输出的提示词**不假设对方能跑任何命令**：它要求 AI 只做"读文档 → 输出一个
JSON"，校验交给平台（网页上的「只校验」/ `provider validate`）。提示词里明确写了三种协议的 URL
拼接规则、`base_url` 只能是前缀、缺信息就省略而不是编造、只输出 JSON 不要围栏。
若 AI 给的是文件，网页上可用「下载为文件」把规范/提示词或导出的配置存下来。

## 1. 三个概念

| 概念 | 是什么 | 存在哪 |
|---|---|---|
| **provider** | 一家供应商的接入方案：协议、地址、鉴权方式、模型目录、可选的"列模型"与"查配额"接口 | 内建包 + `/var/lib/dsh-mu/providers/<id>.json` |
| **套餐（plan）** | `provider + 一把 key + 一个人能看懂的名字`。**模型选择器的分组就是套餐** | 下一步：`/var/lib/dsh-mu/plans/` |
| **实例** | 一个用户的工作区；它会看到"该用户可见的所有套餐"，并可自由切换 | `instances/<name>` |

关键点：**provider 是目录，不是账号**。多个 opencode go 账号 = 一个 provider + 多把 key
（每把 key 属于一个套餐），而不是多个 provider。

## 2. 配置文件规范（`dsh-mu.provider/v1`）

完整规范与"给 AI 的提示词"随包发布，随时可打印：

```sh
dsh-muctl provider spec
```

要点（完整字段见 `provider spec`）：

- `schema` 固定 `dsh-mu.provider/v1`；`id`（小写字母/数字/连字符）、`label` 必填。
- `auth.type`：`bearer`（`Authorization: Bearer <key>`）或 `x-api-key`（Anthropic 风格）。
- `base_url` + `api` 是默认值；**每个模型可以覆盖 `api`（协议）和 `base_url`**。
  同一个 `base_url` 下不同协议的模型会落在**同一个分组**里（这正是 opencode go 的情况：
  deepseek 系列走 `chat/completions`，gpt 系列走 `responses`，claude 系列走 `messages`）。
- 三个协议：`openai-completions`、`openai-responses`、`anthropic-messages`。
- `discover`：给一个 `GET` 地址和 JSON 路径，平台就能自己去上游拉模型目录。
- `usage`：给一个 `GET` 地址和"窗口名 → JSON 路径"，平台就能读配额百分比与重置时间。

### 给 AI 的提示词

`dsh-muctl provider spec` 的输出里有一段"把下面整段连同供应商文档一起发给 AI"的提示词，
要求 AI 只输出一个符合规范的 JSON，并说明：怎么选 `auth.type`、不同模型走不同协议时怎么写、
`discover`/`usage` 怎么填、以及"不要编造文档里没有的地址"。生成后用
`dsh-muctl provider validate <文件>` 自检。

## 3. 已实现的命令（真机验证过）

```sh
dsh-muctl provider spec                       # 规范 + AI 提示词
dsh-muctl provider validate my.json           # 结构与取值检查（会指出第几个模型哪个字段错）
dsh-muctl provider import my.json             # 校验并入库；同时进 catalog（可 assign 给实例）
dsh-muctl provider export opencode-go         # 导出（含刷新过的模型目录）
dsh-muctl provider models opencode-go --key K --refresh --detect-api
dsh-muctl provider usage opencode-go --key K  # 配额
```

`--detect-api` 会**逐个模型探测协议**（每个模型最多试三种协议，取第一个不报
"协议不支持"的），因为上游的模型列表接口不告诉你协议，而协议是不可互换的。

实测（2026-10-17，两个真实账号）：

| 操作 | 结果 |
|---|---|
| `provider import deepseek.json` / `opencode-go.json` | OK，写入 `/var/lib/dsh-mu/providers/` |
| `provider models deepseek --refresh` | 2 个模型，带 `context_window`/`max_output_tokens` |
| `provider models opencode-go --refresh --detect-api` | **37 个模型**，31 个是上游新增；`gpt-5.6-luna → openai-responses`、`claude-haiku-5-5 → anthropic-messages`，其余 `openai-completions`（约 90 秒，一次性） |
| `provider usage opencode-go` | `rolling 0% / weekly 0% / monthly 0%` + 各自的重置时间 |

两个内建包在 `provider-packages/`：`deepseek.json`（`anthropic-messages`，`x-api-key`）与
`opencode-go.json`（`bearer` + `x-opencode-session`，三种协议混排）。

## 4. 套餐（下一步实现，设计已定）

按你的决定：

- **个人套餐在抽屉里添加**（先做后台，抽屉稍后一起改）；
- 加/改套餐**允许 2 秒重启**实例来生效；
- **默认套餐**：后台只给"团队套餐"设默认；另外"记住上次用的"由 DSH 自己按会话记；
  **不做**按实例设默认（真要的话放抽屉里由用户自己设）；
- **团队套餐强制可见、用户不可删除**（锁死的设计逻辑）；
- **套餐级模型子集**：支持（例如公司套餐只开放 glm/kimi）。

渲染到实例时，每个可见套餐 → 一条 pi-ai 路由：

```
displayName: <套餐名>            ← 模型选择器的分组名
apiKeyEnv:   DSHMU_PLAN_<id>     ← 只引用，不把密钥写进配置
baseURL/api/headers: 来自 provider
models: 来自 provider（可按套餐裁剪），每个模型可带自己的 api
```

实例的 `~/.dsh/.credentials.yaml` 里每个可见套餐一行 `DSHMU_PLAN_<id>: <key>`（0600、属主是实例 uid）；
实例重启后生效。

## 3.1 实测补充：URL 拼接与 Gemini（2026-10-18，另一个 harness 的产出）

用真实账号跑过一遍第三方生成的配置后确认的两件事：

1. **`base_url` 只能是前缀**，平台按协议追加路径：
   `openai-completions` → `/chat/completions`、`openai-responses` → `/responses`、
   `anthropic-messages` → `/v1/messages`。opencode 的 anthropic 端点是
   `https://opencode.ai/inference/go/anthropic`；写成 `…/go/v1` 会变成
   `…/go/v1/v1/messages`（404）。现在 `provider validate` 会**直接拦下**这种重复后缀。
   三种协议实测：`glm-5.3-flash`（completions）、`grok-4.6`（responses）、
   `claude-haiku-5-5`/`minimax-m3`（messages）全部 **200**。
2. **只支持三种协议**：pi-ai 没有 google `:generateContent` 适配，所以 Gemini 模型接不进来。

`provider-packages/opencode-go.json` 已换成这份实测通过的配置：**30 个模型**
（20 completions / 2 responses / 8 messages），默认 `glm-5.3-flash`，
`discover` 用 `/go/v1/models`、`usage` 用 `/go/v1/usage`。

## 4.1.1 抽屉的交互规范（2026-10-19 改版）

结构（自上而下，越常用越靠上）：

```
[用户名]  [角色徽标]                 ← 页头，无边框卡片
[修改密码] [退出登录]
──────────────────────────────
我的实例        名称 / 端口 / 状态 / 模型        [启动] [重启]
我的套餐                                           [＋ 添加]
  名字（单行，超出省略，悬停看全名）
  provider · N 个模型（单行省略）      团队/我的   改名  删除
```

规则：

- **所有需要输入的动作都走同一个弹层**（修改密码、添加套餐、重命名、删除确认、重启确认），
  抽屉里不再平铺任何输入框；弹层支持 `Esc`、点遮罩、取消关闭，输入框里按 `Enter` = 确定。
- **默认套餐**在抽屉里用一枚实心「默认」徽标标出（团队/个人都可能成为默认：后台设的优先，
  否则按名字取第一个）——用户能看到"当前生效的是哪一组"。
- **我的套餐**每行两行文字：标题=套餐名，副标题=`provider · N 个模型`，两者都**单行省略**
  （`text-overflow: ellipsis` + `title` 提示），所以 provider 名或套餐名再长也不会把行撑歪；
  右侧徽标与操作按钮 `flex: 0 0 auto`，不会被压缩换行。
- **重启**在「我的实例」里，确认后调用 `POST /me {action:"restart"}` → 后端 `202` 接受；
  界面在 6 秒与 20 秒后各刷新一次状态（弹层里已写明会中断当前对话）。
- **修改密码 / 退出登录**放在页头（用户名与角色徽标下面），**不套卡片边框**，只用一条分隔线与
  下面的卡片区分；修改密码点击才展开弹层。系统账号（root）不显示该按钮（口令要用服务器上的
  `passwd` 改），页头会多一个「系统账号口令」徽标说明这一点。
- 团队套餐只读：行内不出现改名/删除，只有「团队」徽标。

## 4.3 套餐接管模型选择（2026-10-18，手工测试反馈）

启用套餐后，**内置的那条 DeepSeek 路由会被清空目录**（patch 里写 `llm-deepseek: models: []`），
原因：它仍然是一个可被选中的 provider，而套餐模式下我们不再写 `DEEPSEEK_API_KEY`，选中它就会报
`no API key for provider route "deepseek-official"`。现在：

- 模型选择器里**只剩套餐分组**（`<套餐名>` 或 `<套餐名> · chat/messages`）；
- `agent-default-model` 指向默认套餐（后台"设默认"优先，否则按名字取第一个）；
- 兼容：`refs:` 里仍写一份 `DEEPSEEK_API_KEY = 默认套餐的 key`，这样**升级前建的会话**（其模型仍记为
  `deepseek-official`）不会突然报错；
- 抽屉的 provider 下拉**只列已导入的包**（内置 preset 不再出现，之前那个"不知哪来的 opencode"就是它）。

实测（alice，两个套餐）：抽屉 providers = `['deepseek', 'opencode-go']`、`GET /` 200、
patch 头部 `llm-deepseek: models: []` + 两个 plan 路由 + `agent-default-model`。

## 4.3.1 图片输入：模型要声明 `input_modalities`

**症状**：发带图片的消息时，无论选哪个模型都提示「当前模型不支持图片，请切换支持图片的模型」。

**真因**：我的规范漏了"模型支持哪些输入模态" ✗ —— patch 里的模型条目没有 `inputModalities`
时，harness 按**纯文本**处理 ✗，于是任何图都被拒。

**修法**（已全部打通）：
- 规范新增模型级 `input_modalities`（`["text"]` / `["text","image"]`）；`provider validate` 会校验；
- `discover` 能把上游的 `input_modalities`（如 DeepSeek 的 `/models` 就提供）读进目录；
- 渲染成 patch 里的 `inputModalities: [text, image]`；
- 内置包已更新：`deepseek-flash` = text+image、`deepseek-v4-pro` = text；opencode-go 的
  `gpt-*`/`claude-*`/`gemini-*`/`glm-5*`/`kimi-k3`/`minimax-m3`/`qwen3.8-max` 标为 text+image，其余保守按 text。

已经导入过的包可以原地改 JSON 再 `dsh-muctl plan sync` + 重启实例；实测 alice 的 patch 里现在有
**109 处** `inputModalities`，`GET /` 仍 200。

## 4.3.3 图片能力到底写哪个字段（2026-10-18，查源码定案）

**症状**：包里声明了 `input_modalities: ["text","image"]`、patch 里也生成了，但发图依旧提示
「当前模型不支持图片」。

**真因**：字段名用错了 ✗。pi-ai 路由的模型条目字段是 **`input`** ✗：

```ts
// dsh-llm-pi-ai/lib/types/catalog.d.ts
export interface PiAiModelProfile {
  id: string; name?: string; contextWindow?: number; maxTokens?: number;
  /** Request modalities this model accepts. Absent keeps the installed catalog
   *  entry's modalities, then the route's `defaultInput`.
   *  Declaring images is what makes a hand-declared vision model usable ... */
  input?: PiAiModality[];
  ...
}
```

而 `inputModalities` 是**内置 DeepSeek 适配器**（`dsh-llm-deepseek`）的字段 ✗ —— 在 pi-ai 路由上被忽略 ✗。
`grep -rl inputModalities` 在 `dsh-llm-pi-ai/lib` 里根本没有命中，这就是判据 ✓。

**修法**：`plans_patch_yaml()` 现在输出 `input: [text, image]`（用户侧仍然只写 `input_modalities`，
平台负责翻译 ✓）。实测 patch：

```yaml
- id: "gpt-6-astra"
  contextWindow: 1050000
  maxTokens: 128000
  input: [text, image]
```

## 4.3.2 导出→改→导入 会丢字段的坑（2026-10-18）

**症状**：按"导出 → 改 JSON → 再导入 → plan sync → 重启"的流程给模型加 `input_modalities`，
结果**没生效**；再导出看，字段还在，但模型的 `context_window`/`max_tokens` 反而**没了**。

**两个叠加的真因**：
1. `provider export` 输出的是**内部规范化形式**（`inputModalities`、`contextWindow`），
   而 `import` 只认**文档里的写法**（`input_modalities`、`context_window`）→ 往返一次字段就丢；
2. `load_provider_package()` 会把**已规范化的文件**再校验一遍，同样只读 snake_case →
   **每次加载都把 `contextWindow`/`maxTokens` 丢掉**（这就是 1050000/128000 消失的原因）。

**修法**：
- `validate_provider_package()` 同时接受两种写法（`context_window`/`contextWindow`、
  `max_tokens`/`maxTokens`、`base_url`/`baseURL`）；
- `provider export` 改为一律输出**规范写法**（`package_for_display()`），并顺便省略与包级默认相同的
  `api`/`base_url`，让导出的文件更像人手写的。

**实测**：`export | jq` 得到
`{"context_window":1050000,"input_modalities":["text","image"],"max_tokens":128000,…}`，
往返后 patch 里是 `contextWindow: 1050000 / maxTokens: 128000 / inputModalities: [text, image]`。

> 教训：任何"导出→编辑→导入"的闭环都要有**往返测试**，否则内部命名和文档命名一分叉就会静默丢字段。

## 4.4 一次会让实例"再也起不来"的坑（2026-10-18，手工测试发现）

**症状**：在抽屉里创建私有套餐后，实例像是自己重启了一次，然后**再也不起来**；
`dsh-muctl instance start/restart` 也没有用；新建的 bob 同样起不来。

**真因**：写 `.credentials.yaml` 时产生了**重复键** ✗：

```
credentials-local: invalid document at /home/dsh/.dsh/.credentials.yaml:
DUPLICATE_KEY at line 5, column 3      -> dsh: startup failed: 1 required plugin did not activate
```

我加"兼容老会话"的 `DEEPSEEK_API_KEY` 时，没注意到文件里**保留的那份**也叫这个名字 ✗ →
同一个 key 出现 3 次 ✗ → harness 的 credentials 插件拒绝整个文件 ✗ → 实例启动失败 ✗。
（它在 `*.err.log` 里说得非常清楚，只是 `instance start` 当时只报"等待 banner 超时"，把原因盖住了。）

**修法**：
1. `write_instance_refs()` 改成**按名字合并**（显式值覆盖保留值），不可能写出重复键；
2. `instance start` / `refresh-cookie` 失败时会**打印 harness 自己的原因**
   （`the harness refused to start -> dsh: startup failed: … DUPLICATE_KEY …`）；
3. 首次启动的等待上限 300 s → **900 s**（冷启动要在 jail 里 npm 装整个 profile）；
4. 已经被写坏的实例用 `dsh-muctl plan sync` 就地修复（重渲染 refs，保留 `records:`）。

实测：`refs` 里 `DEEPSEEK_API_KEY` 计数从 3 → **1**、`records:` 保留 ✓，alice/bob 的 `/` 都回到 **200**。

  3 个模型里 gpt 走 responses、claude 走 messages、`agent-default-model` 指向默认套餐）。

**已解决（2026-10-18）**：启用套餐后实例返回 **401** 的根因不是 patch 内容，而是
`sync_instance_plans` 把实例的 `~/.dsh/.credentials.yaml` **整文件重写**，丢掉了里面的
`records:` 段——那是 web 客户端的 **browser-session 签名密钥**。密钥一丢，网关 mint 出来的
cookie 就验不过，harness 于是对 `/` 回 401，而且**任何日志里都没有配置错误**（所以很难查）。

修法：同步只重写 `refs:` 段，其余段（`records:` 及将来的新段）**原样保留**；
`instance refresh-cookie` 现在会打印 cookie 的**值指纹**（便于确认是否真的换了）；
`tests/plans.py` 守住这个回归（先种一个 `records:` 段，同步后必须还在），作为回归第 31 层（全量 `PASS=32 FAIL=0`）。

实测：套餐启用状态下 alice `GET /` → **200 / 34955 字节**，凭据文件 `refs(2) + version + records` 完整。

## 6. 已知限制（必须知道）

1. **key 可见性**：实例要能用某个套餐，就必须能读到那把 key，所以"团队套餐"的 key
   对**能看到它的用户**是可读的（和今天"平台 key 就在实例里"同一级别）。要真正藏住，
   只能把模型流量也经平台中转（另一个量级的工程，暂不做）。
2. **按套餐限额做不到**：额度由上游管；平台只能启用/停用套餐。
3. **协议探测有成本**：`--detect-api` 每个模型最多发 3 个 1-token 请求，模型很多时慢（37 个约 90 秒），
   但只在上游新增模型时才有必要。
4. **同一 `base_url` 之外的差异**（不同模型连地址都不同）：会拆成多个分组（分组名带后缀）；
   配置文件里仍是一个 provider。

## 5. provider 是目录，套餐才是"这个 key 能用什么"（0.9.9 起）

职责重新划分（这是产品逻辑修正）：

| 层 | 负责 | 不做 |
|---|---|---|
| **Provider（目录层）** | 协议、base URL、**全量 models**、默认 model | 不再有"刷新模型 / 查配额"按钮 |
| **套餐（可用层）** | 用**这个 key** 实测能用哪些模型 → `available_models`；从里面**勾选**子集；配额查询 | 不再靠猜 provider 有没有新模型 |

### 操作

```sh
dsh-muctl plan probe <id>              # 用该套餐的 key 去上游实测，记住可用集合
dsh-muctl plan models <id>             # 看目录：* = 已选，ok / UNUSABLE = 该 key 是否可用
dsh-muctl plan models <id> --set a,b   # 精确指定（不在可用集合里会被拒绝）
dsh-muctl plan models <id> --all       # 选全部可用的
dsh-muctl plan models <id> --clear     # 清空（= 全部，不筛选）
dsh-muctl plan usage <id>              # 配额/限流窗口
```

管理界面同样：provider 行只剩「导出 / 下载 / 删除」；**套餐行**有
「检测可用模型 / 配额 / 编辑模型」；编辑模型是一个勾选面板，**该 key 不可用的模型会标灰且不可勾**。

### 语义

- `plan probe` 会把上游列出的模型与 provider 目录对比：
  - 在目录里 → 进入 `available_models`（可勾选）
  - **不在目录里** → 报告出来（"add them there first"），因为**不能凭空编造怎么请求它**
- 渲染进实例 patch 的模型 = `已选 ∩ 可用`；勾了但不可用的**直接丢弃**，并在界面上明确提示
- 未探测过的套餐（`available_models == null`）保持旧行为：只按已选子集渲染，不额外过滤

### 生效时机

模型子集写进实例的 `~/.dsh-mu-provider.yml`，**实例启动时读取** →
改完要 `dsh-muctl instance restart <name>`。抽屉里改完会亮起
「有改动要重启才生效 / 立即重启」提示，用户自己点一下即可。

### 界面上你能看到什么（0.10.1）

「编辑模型」是一个**表格**，不是一堆勾选框：

| | 模型 id | 名称 | 可用? | 状态 |
|---|---|---|---|---|
| ☑ | `deepseek-v4.1-flash` | DeepSeek-V4.1-Flash | ✅ | 已选 |
| ☐ | `glm-5.3` | GLM-5.3 | ✅ | 未选 |
| ☐ | `some-model` | … | ⛔ | 该 key 不可用（不可勾选） |

表格上方一行摘要：**目录 N 个 · 已选 K 个 · 可用 M 个 · 上次检测 <时间>**，
下面跟一行**上次检测的变化**（新增可用 n / 失去可用 n / 目录缺口 n）。

「检测可用模型」不再是"报个数字"：它会明确说**变了什么** ——

```
可用 29 个（上次 27）：新增可用 3（glm-5.4, kimi-k4, …）；失去可用 1（glm-5.0）；目录缺口 8
首次检测：可用 29 个 / 目录 30 个；上游有 8 个不在目录里。可到「编辑模型」勾选。
可用 29 个（上次 29）：可用集合没有变化
```

## 6. 推理等级（reasoning efforts）

DSH 的 pi-ai 模型项原生支持 `reasoningEfforts` —— 键是**选择器里能选的等级**，值是**发给上游的写法**
（[pi-ai README](https://github.com/anomalyco/opencode) 里的例子：`off:` + `high: high`，
也支持 `max: ultra` 这种改写法）。本平台从 0.10.3 起把这一项**透传到实例 patch**。

### 怎么填

模型行现在支持第 5 个字段（用 `|` 分隔）：

```
id | 名称 | contextWindow | maxTokens | 推理等级
```

`推理等级` 的写法：

| 写法 | 含义 |
|---|---|
| `off,high` | 两个等级，等级名就是发给上游的写法 |
| `off:off,high:ultra` | 两个等级，`high` 这一档在上游发 `ultra` |
| `false` / `none` / `-` | 明确声明"这不是推理模型" |
| 留空 | 不声明（沿用上游目录的能力，pi-ai 的行为） |

命令行例：

```sh
dsh-muctl provider add myprov --kind pi-ai --route myprov --api openai-completions \
  --base-url https://api.example.com/v1 --model m1 \
  --models "flash|Flash|1000000|128000|off,high
reasoner|Reasoner|200000|64000|off,low,high:ultra"
```

渲染出来的实例 patch：

```yaml
          - id: "flash"
            name: "Flash"
            reasoningEfforts:
              off:
              high: "high"
```

### 界面上看得到什么

「编辑模型」表格多了一列 **推理等级**：`off / high` 这种就是可选的档位，
`非推理` 表示该模型被声明成不支持推理。选中带等级的模型后，
实例的模型选择器里就会显示 `模型名 + 档位`（例如 `DeepSeek-V41-Flash High`）。

### 一个限制：内置 preset 不能带推理等级

`opencode` / `opencode-go` / `deepseek` 这些**内置 preset** 的模型定义在代码里，
`plan_package()` 优先用导入的包、没有才回落到 preset。所以想给它们加推理等级时：

```sh
dsh-muctl provider import ./opencode-go.json     # 变成"自定义包"，之后就能随便改
dsh-muctl provider show opencode-go > /tmp/x.json  # 或者先导出现状再手工加字段
```

字段名用 `reasoningEfforts`（也接受 `reasoning_efforts`）：

```json
{ "id": "gpt-6-astra", "name": "GPT-6 Astra",
  "reasoningEfforts": { "off": "", "high": "high" } }
```

`false` 表示"明确不是推理模型"；整个字段省略表示"沿用上游目录的能力"。

## 7. 开箱即用的默认套餐：Kilo Free（keyless）

`install` 会维护一个**团队套餐** `Kilo Free（默认）`，id 固定为 **`plan_default`** ——
**不需要任何 API Key**。

这个 id 有三条固定语义（0.18.0 起）：

| 语义 | 行为 |
|---|---|
| **占位符** | id 固定 ✓，升级时按新版本的内置定义**覆盖内容** ✓（将来内置默认换成别的套餐，也还是 `plan_default` ✓，不会留下旧 id 的残留 ✓） |
| **不可删除** | 可**停用**（`plan disable plan_default`）✓，但删除会被拒绝 ✓（CLI 与 API 都是 ✓） |
| **保底可用** | 一个用户**一个可用套餐都没有**时，即使 `plan_default` 处于停用状态，它也**仍然可用** ✓（否则该用户没有任何模型可选 ✓） |

`enabled` 字段升级时**保留** ✓（别的字段覆盖 ✓），所以你停用过的默认套餐不会被下一次升级悄悄打开 ✓。

| 项 | 值 |
|---|---|
| 上游 | `https://api.kilo.ai/api/gateway`（OpenAI Chat Completions） |
| 模型 | `kilo-auto/free`（网关自动路由，实测落到 `stealth/glyph-cluster`） |
| 凭据 | **无**（pi-ai 的 keyless profile；relay 不发 Authorization） |
| 推理等级 | `off/low/medium/high/max`（`off` 的线上写法是 `none`） |
| 工具调用 | 支持 ✓（`finish_reason=tool_calls`） |
| 流式 | 支持 ✓（SSE） |

### 实测（2026-10-20）

```
无 key             → 200（首次冷启动可能 30s+，之后 6s 左右）
带一个假 key        → 401 INVALID_TOKEN      ← 所以绝不能发 Authorization
tools              → 200 + tool_calls
stream:true        → text/event-stream
reasoning_effort    → none/minimal/low/medium/high/max 全部 200
经本平台 relay      → 200（实测 6.5s）
```

### 为什么需要"keyless"这条路径

pi-ai 的 profile 里 **`apiKeyEnv` 可以省略** —— 省略即 "configured but keyless"。
本平台据此实现了三处配合，缺一不可：

1. 套餐路由不给 keyless 计划渲染 `apiKeyEnv`（`plan_routes`）；
2. `relay.json` 里该路由 `auth: ""`、`key: ""`；
3. `relay.lua` 放行 keyless，并且让 **Authorization / x-api-key 都不发出去**
   （nginx 里空 header 值 = 不发送该 header）。

> 注意：这个通道是第三方公共服务，可能变慢、限流或随时关闭 —— 它适合"装上就能对话"，
> 生产用途请换成自己的 provider。运营者也可以随时停用/删除该套餐。

## 8. 从线上模板库导入 provider（0.14.0）

不用手写 JSON：模板放在**项目仓库**的 `provider-packages/` 目录里，后台可以列出并一键导入。

### 后台

「模型接入」页顶部 → **从线上模板库导入**：

| 列 | 意思 |
|---|---|
| 模板 / 说明 | `index.json` 里的 `label` / `description` |
| 协议 / 模型数 | 便于判断是不是你要的 |
| 状态 | 已导入 / 未导入 |
| 操作 | 导入（已导入的会提示"覆盖吗？" ✓ 不会静默覆盖 ✓） |

导入后**不会自动建套餐** ✓ —— 仍然是"provider 是目录、套餐才是可用性"的分工 ✓。

### 命令行

```sh
dsh-muctl template list                    # 列出模板库
dsh-muctl template import deepseek         # 下载 + 校验 + 保存
dsh-muctl template import opencode-go --force   # 覆盖已有同名 provider
dsh-muctl template source                  # 看当前模板库地址
dsh-muctl template source --url https://raw.githubusercontent.com/you/repo/main/provider-packages
```

模板库地址也可写进配置：`dsh-muctl config provider_template_base <url>`（支持 `https://` 与 `file://` ✓）。

### 安全约束

1. **只允许 `https://` 与 `file://`** —— 拒绝 `http://`、`ftp://` 等明文源；
2. 下载后**先过 `validate_provider_package()`** —— 有问题的模板会被拒绝，不会落盘；
3. **不覆盖**已有 provider（除非 `--force` / 界面里确认）；
4. **不会自动创建套餐 / 不会自动启用**；
5. 模板名只允许 `[A-Za-z0-9._-]` —— `../etc/passwd` 这类路径穿越会被拒绝；
6. 每次导入都记审计（`provider.template.import` + `sha256`）并打印 `sha256` ✓。

### 模板库索引（`provider-packages/index.json`）

```json
{"version": 1, "templates": [
  {"name": "deepseek", "label": "DeepSeek 官方", "description": "…", "api": "anthropic-messages", "models": 2}
]}
```

有 `index.json` 时直接读它（**不消耗 GitHub API 限额** ✓）；没有时会回落到
GitHub contents API 自动列出该目录里的 `*.json` ✓（未登录限额 60 次/小时 ✓）。

### 离线机器怎么办

模板库地址可以指向本地目录：`dsh-muctl template source --url file:///srv/templates` ✓ ——
把 `provider-packages/` 拷过去即可 ✓。回归里的 `tests/provider-templates.py` 就是这么测的（完全离线 ✓）。

## 9. web_search 的 key（0.15.2）

实例里的 `web_search` 工具由 `web-search-deepseek` 插件提供，它有**独立的 baseURL 和凭据**
（默认读 `DEEPSEEK_API_KEY`，并在 baseURL 后面拼 `/messages`）。

在"套餐 + relay"模式下，`DEEPSEEK_API_KEY` 在实例里是占位符 `mu-relay` ✓ ——
所以它如果**直连** `api.deepseek.com`，就会得到：

```
WebError: WEB_PROVIDER_ERROR
Error: DeepSeek API error (HTTP 401): Authentication Fails,
Your api key: ****elay is invalid
```

（`****elay` 就是 `mu-relay` 的尾巴 ✓。）

### 平台怎么处理

`plans_patch_yaml` 现在会**自动给 web-search 也写一份配置**：

```yaml
- id: web-search-deepseek
  config:
    # relay 模式：仍然只把占位符发出去，真 key 由 relay 注入
    baseURL: "http://127.0.0.1:8099/mu-llm/<token>/<plan-route>/v1"
    apiKeyEnv: DSHMU_PLAN_XXXX
```

- **选哪个套餐**（0.21.0 起，搜索是"平台能力"）：
  1. 先找**平台搜索套餐** `search_plan()` ✓：在**所有套餐**（含 `hidden`）里，
     按 `order` 取第一个能跑 DeepSeek 搜索的（`api=anthropic-messages` 且
     `base_url` 指向 `api.deepseek.com`）✓ —— 这样"只有 opencode-go 的用户"也能搜 ✓，
     而费用落在管理员指定的那个套餐上 ✓；
     它通过 relay 的固定路由 **`__search`** 走：
     `baseURL: http://127.0.0.1:8099/mu-llm/<token>/__search/v1` ✓
     （`apiKeyEnv: DSHMU_SEARCH`，值只是占位符 ✓）；
  2. 没有平台搜索套餐 → 回退到**用户自己的** base_url 是 `api.deepseek.com` 的套餐 ✓
     （插件是 DeepSeek 的，服务端 `web_search` 工具只在它自家端点上有 ✓）；
  3. 再否则 → **注册但不可用**：`baseURL` 指向一个不会被用到的地址，
     `apiKeyEnv: DSHMU_WEB_SEARCH_UNCONFIGURED`（谁也没设这个变量）✓

     DSH 会报：`configured web provider "deepseek-official" is registered but unavailable`
     —— 这是它能给出的**最准确**提示（比 `not registered` 和 401/403 都好）✓。

     ⚠️ **不要禁用 `web-search-deepseek`**：`dsh-web` 的 `searchProvider` 仍然指着它 ✓，
     插件被禁用后工具会报 `configured web provider "deepseek-official" is not registered` ✗
     （0.15.4 就踩了这个坑 ✓）。

     光有"注册但不可用"还不够（0.15.5 实测：模型还是会去调它，只是把报错换成了
     `DeepSeek search has no API key for "DSHMU_WEB_SEARCH_UNCONFIGURED"` ✗）。
     所以 0.15.6 再补一刀：**把工具本身藏起来** ✓

     ```yaml
     - id: tool-web
       config:
         search: false     # 只关搜索；web_fetch 保留
     ```

     `dsh-tool-web` 的 schema 是 `search: bool` + `fetch: bool` ✓ 两个独立开关 ✓，
     所以网页抓取不受影响 ✓。从此**没有红字** ✓ —— 模型干脆不知道有 `web_search` ✓。

  > 为什么不再"挑一个 anthropic 兼容的"：试过两次都错 ——
  > Kilo（OpenAI 协议）给 401 `You need to sign in to use this model`，
  > opencode-go 的 anthropic 路由给 403 `error code: 1010`（Cloudflare）。
  > 猜别的供应商只会制造误导性报错，所以自动只认官方 DeepSeek，其他由 `web_search_plan` 显式指定。

  > 注意：**指向 OpenAI 协议的网关（Kilo、多数中转）一定会失败** —— 插件只会给
  > baseURL 拼 `/messages`。所以没找到兼容套餐时宁可**禁用**，也不乱指（0.15.3 修）。

  他如果只有 Kilo 套餐，`web_search` 就是"未配置"状态。要真正启用，给他一个
  DeepSeek（或任何 Anthropic Messages 兼容）套餐，然后指过去：

  ```sh
  dsh-muctl plan add --provider deepseek --name "DeepSeek" --key-file /root/keys/deepseek.txt
  dsh-muctl config web_search_plan <新套餐的 id>
  dsh-muctl sync && dsh-muctl instance restart <实例名>
  ```
- **为什么是 `/v1`**：插件会自己拼 `/messages`，而 DeepSeek 的真实路径是
  `https://api.deepseek.com/anthropic/v1/messages` —— relay 按原样转发路径，所以 baseURL 要带 `/v1`；
- **没有 relay 时**（单机直连）：写成 `https://api.deepseek.com/anthropic/v1` + 该套餐自己的凭据引用。

配置项：`dsh-muctl config web_search_plan <plan_id>`（留空 = 自动挑）。

改完要**重启实例**才生效 ✓。

## 10. 默认模型：按优先级回退（0.17.0）

**为什么不是一个"默认套餐"**：每个人能看到的套餐不同 ✓ —— 一个默认套餐对别人可能不可见 ✗。
所以改成一条**优先级链** ✓：新会话的起始模型 = **第一条这个用户能看到的**（套餐 + 模型）✓。

### 后台

「模型接入」→ **默认模型（按优先级）**：

| 优先级 | 套餐 | 模型（新会话起始） | 操作 |
|---|---|---|---|
| 1 | `team-deepseek` | `deepseek-flash` | ↑ ↓ 删除 |
| 2 | `kilo-free` | （套餐默认） | ↑ ↓ 删除 |

- 「＋ 添加一档」追加 ✓，「保存默认模型」写入 ✓；
- 模型的候选项 = 该套餐**实际生效**的模型 ✓（已选 ∩ 可用 ✓）；
- 保存后 `dsh-muctl sync` + 重启实例生效 ✓。

### 命令行

```sh
dsh-muctl default list                      # 看当前优先级
dsh-muctl default add plan_default           # 追加一档（不指定模型 = 用套餐默认）
dsh-muctl default add plan_8f7c3b30 --model glm-5.3
dsh-muctl default set plan_default           # 只保留这一档
dsh-muctl default rm 2                      # 按序号或套餐 id 删除
```

### 语义

1. 渲染实例时按顺序取**第一条该用户可见的**条目 ✓ → `agent-default-model` ✓；
2. 条目的模型不在该套餐的可用集合里 → 视为不可用 ✓ → 继续下一条 ✓；
3. 整条链都用不上 → 回落到"该用户能看到的第一个套餐" ✓；
4. `default_plan` 仍保留 ✓（抽屉的「默认」徽章用 ✓），它 = 链的**第一条** ✓；
5. **会话内的选择优先**：用户在本会话换过模型后 ✓，DSH 的 `modelSelection.lastUsed` 记着 ✓ ——
   链只在**新会话**里生效 ✓（0.16.5 查明的机制 ✓）。

## 11. 套餐的「隐藏」与「顺序」（0.21.0）

| 字段 | 作用 |
|---|---|
| `hidden` | 用户在抽屉/模型选择器里**看不到、选不到** ✓，也不进默认链 ✓；但平台**仍可用它做 web_search** ✓ |
| `order` | 数字，越小越靠前 ✓ —— 同时决定 **① 抽屉展示顺序 ✓ ② web_search 用哪个套餐 ✓**；**不影响默认模型** ✓ |

```sh
dsh-muctl plan hide  <plan-id>            # 用户不可见
dsh-muctl plan show  <plan-id>
dsh-muctl plan order <plan-id> --order 10 # 越小越靠前（也是用户看到的顺序）
```

**"平台买单的搜索"怎么配**（三步）：

```sh
dsh-muctl plan add --name "平台搜索" --provider deepseek --key-file /root/ds.key
dsh-muctl plan hide  <新套餐 id>
dsh-muctl plan order <新套餐 id> --order 10
dsh-muctl sync && dsh-muctl instance restart <实例>
```

之后所有用户（哪怕只有 opencode-go）都会有 `web_search` ✓，花这个套餐的额度 ✓；
后台「套餐」页顶部会写明「当前搜索将使用：<套餐>」✓，`doctor` 也有一项
`web search plan` ✓（没有可用套餐时 WARN ✓）。

> ⚠️ 隐藏套餐 = **平台买单的共享资源** ✓。本项目给小型团队用 ✓；
> 如果不打算为搜索出钱，就**不要**加隐藏套餐 ✓（`doctor` 会一直 WARN ✓ 是提醒 ✓）。
