# dsh-mu 多实例托管平台 — 需求整理（v0.1 待确认）

> 目标环境：`dsh-mu` = `192.168.13.61`（Alpine LXC，特权容器，root）
> 目标版本：DeepSeek Harness `0.2.0-rc.2`
> 本文档只做需求与方案确认，确认后进入实现。

---

## 1. 目标

在 `dsh-mu` 上做一个 **多实例 DSH 托管平台**：

1. 用户只用**一个统一入口**（网关）访问，不需要知道端口、token、实例路径。
2. 未登录 → 跳登录页；登录后网关按会话把请求 **反向代理** 到该用户对应的 `dsh web` 实例。
3. 每个实例跑在**自己的一份 Alpine 根文件系统**里（jail 式隔离：mount namespace + chroot + cgroup），
   目录与 apk 安装环境互不干扰；网络与内核**共享**（不做网络命名空间）。
4. 实例可被创建/启动/停止/重启/限额/看日志，平台重启后自动恢复。

**一句话验收**：浏览器打开 `http://dsh-mu/` → 登录 → 直接进入自己的 harness（能对话、能跑工具、WebSocket 长连接不断），且看不到也影响不到别人的实例。

## 2. 已核实的事实（侦察结论，作为设计依据）

### 2.1 目标机 `dsh-mu` 现状

| 项 | 实测值 | 影响 |
|---|---|---|
| 系统 | Alpine Linux 3.24.1，LXC 特权容器（根盘 `/dev/loop7`） | 与安装文档同构，可直接复用其经验 |
| 内核 | `7.0.14-19-pve`（PVE 宿主内核） | cgroup v2 / overlayfs / ns 由内核提供 |
| 能力 | `CapEff=000001ffffffffff`（全量 capability） | `unshare` / `mount` / `chroot` / cgroup 全部可用 |
| cgroup | `/sys/fs/cgroup` = cgroup2，**rw**，控制器含 `cpuset cpu io memory pids` 等，可 `mkdir` | 资源限额方案可行 |
| 隔离工具 | `unshare` `nsenter` `setpriv` `chroot` `mount`（util-linux）齐备 | jail runner 无需自写 C |
| 磁盘 | 根盘 11.7G，已用 22.3M（**≈11.1G 可用**） | 决定单机能放多少实例，见 §9 |
| IP | `eth0 = 192.168.13.61/24` | 网关对外地址 |
| 已装 | 仅基础系统 + sshd/crond/networking（OpenRC） | node/dsh/openresty **需从零安装** |
| 未装 | node、npm、pnpm、dsh、nginx/openresty、curl、python3、sqlite3 | 选型要尽量减少依赖 |

### 2.2 DSH 0.2.0-rc.2 内部机制（已读源码确认）

| 机制 | 结论 | 对方案的影响 |
|---|---|---|
| 启动 token | 每次进程启动随机生成 32B base64url，只写 stdout（`dsh-client-connection` `processLaunchToken`） | 不能靠静态 URL；**由网关代持** |
| token 换 cookie | `GET /?token=xxx` → `303` + `Set-Cookie: dsh-auth-<b64url(sha256(authority))>=v1.<payload>.<hmac>`，默认 30 天 | 网关可自动完成换取并缓存 |
| 签名密钥 | 持久化在 `$DSH_HOME/.credentials.yaml` 的 `client-connection/browser-session` | 实例重启后 cookie 仍有效 |
| `/api` 信任栅栏 | `Host` 必须是 loopback 或在 `--trusted-host` 白名单；有 `Origin` 时必须等于 Host；`Sec-Fetch-Site: cross-site` 拒绝 | 网关转发时要**归一化 Host/Origin** 并配 `--trusted-host` |
| 关闭鉴权开关 | **不存在**（无 `--no-auth` 之类的配置项） | 网关侧代持 cookie 是正解，不改 DSH 源码 |
| `DSH_HOME` | 环境变量可覆盖 harness home（`dsh-home-paths`） | 每实例独立状态（sessions/storages/credentials/profiles） |
| CLI 参数 | 只有 `--host` `--port` `--trusted-host` `--no-open` | 无路径前缀（mount）支持 → **不做 `/u/alice/` 式路径路由** |
| 插件安装 | 两步：`pnpm add` + 写进 `dsh.profile.bundles`；插件 UI 在「设置」里 | 需要预置插件的实例在模板里预装 |
| 「设置」分区 | 客户端按**浏览器地址栏 hostname** 判断 loopback，非 loopback 时 `persistence=memory`，整个设置分区显示 "unavailable" | 网关场景下**必然触发**，见 §8 待确认 |

## 3. 功能需求

### FR-1 统一入口与认证（网关）

- `FR-1.1` 单一入口 `http://dsh-mu/`（可扩展 HTTPS）；未登录访问任何受保护路径 → `302 /login?next=<原路径>`。
- `FR-1.2` 登录页：用户名 + 密码；密码用 `scrypt`（Node 内置）加盐散列存储。
- `FR-1.3` 会话 cookie：`HttpOnly`、`SameSite=Lax`、`Path=/`，签名（HMAC）+ 服务端可撤销；支持绝对过期 + 空闲过期。
- `FR-1.4` 注销 `/logout`；改密后使该用户其他会话失效。
- `FR-1.5` 防爆破：按用户名 + 来源 IP 限速/锁定（如 5 次/分钟，连续失败锁定）。
- `FR-1.6` 未认证的 `/api/*` 返回 `401 JSON`（不重定向），页面请求才重定向。
- `FR-1.7` 管理员可强制下线任意会话。

### FR-2 用户与实例管理

- `FR-2.1` 用户：增删改查、启用/禁用、改密、角色（`admin` / `user`）。
- `FR-2.2` 实例：一个用户默认 1 个实例（预留 1:N）；实例属性 = 名称、端口、rootfs 路径、`DSH_HOME`、工作目录、cgroup 限额、状态（stopped/starting/running/error）、PID。
- `FR-2.3` 实例操作：创建、启动、停止、重启、删除（可选保留数据）、查看日志（最近 N 行）、管理员进 shell 排查。
- `FR-2.4` 首次创建实例：从 Alpine minirootfs 模板生成 rootfs → 装 node/pnpm/dsh → 初始化 `DSH_HOME`（写模型 API key、预置插件、预置 `bundles`）→ 首次启动生成 web profile。
- `FR-2.5` 用户自助能力按配置开关：是否允许自助注册 / 自助创建实例（默认关闭，管理员创建）。
- `FR-2.6` 管理界面：轻量 Web UI（`/admin`，仅 admin 角色）；同时保留 CLI/HTTP API 便于脚本化。

### FR-3 反向代理

- `FR-3.1` 支持 HTTP、**WebSocket**（`/api/remote.mux`）、SSE、流式响应；长连接不能被 60s 默认超时砍断（对齐安装文档：`proxy_read_timeout 3600s`、`proxy_buffering off`、正确的 `Upgrade/Connection` map）。
- `FR-3.2` 上游解析：按会话 cookie → 用户 → 实例 → `127.0.0.1:<port>`；**每请求解析，不写死**（实例重启换端口/重启后无需 reload 网关）。
- `FR-3.3` 上游 cookie 代持：网关从实例日志抓 launch token → 回环发起 `/?token=` 换取 cookie → 缓存到实例记录；上游返回 401 时自动重新换取。浏览器**永远看不到**也不持有上游 cookie。
- `FR-3.4` 请求头归一化：转发时设置固定的 `Host` 与匹配的 `Origin`，并给实例配 `--trusted-host`；剥离浏览器自带的 `Cookie`（避免串号）；透传 `X-Forwarded-For/Proto/Host`。
- `FR-3.5` 大文件上传：`client_max_body_size 512m`；请求体直通不落盘。
- `FR-3.6` 实例不可用时：返回友好 503 页（"实例正在启动/异常"，含实例名与日志入口），不是 nginx 默认页。
- `FR-3.7` 实例端口**只监听 127.0.0.1**，外部无法绕过网关直连。

### FR-4 实例隔离与生命周期（jail）

- `FR-4.1` 隔离模型（对齐 `rjailor.py`）：
  `fork` → `unshare(CLONE_NEWNS | CLONE_NEWUTS)` → `mount --make-rprivate /` → 按白名单 `rbind` 宿主目录 → `chroot(rootfs)` → 丢弃 capability → `setuid/setgid` → `exec dsh web`。
- `FR-4.2` 目录隔离：每实例独立 `rootfs/`（含独立 `/etc/apk/world`、`/lib/apk/db`、`/etc/apk/repositories`）；apk 安装只影响自身。
- `FR-4.3` 共享（不严格隔离）的部分按白名单显式绑定：`/proc`、`/sys`(ro)、`/dev`、`/dev/pts`、`/dev/shm`、私有 tmpfs `/tmp`、`/etc/resolv.conf`、以及按需的宿主数据目录。
- `FR-4.4` 持久卷（宿主目录，实例重建可保留）：`home/`（= 实例内 `/home/dsh`，含 `DSH_HOME`）、`workspace/`（= 实例工作区）。
- `FR-4.5` cgroup v2 限额：`memory.max`、`memory.high`、`cpu.max`、`pids.max`、可选 `io.max`；实例进程启动后写入对应 `cgroup.procs`；限额可在线调整。
- `FR-4.6` 实例以**非 root** 用户运行（每实例一个 uid/gid，或统一低权限用户 + 独立 rootfs），jail 内不可写宿主文件。
- `FR-4.7` 网络共享宿主（不做 netns）：实例监听 `127.0.0.1:<port>`，端口由管理器从可配区间分配并记录。
- `FR-4.8` 进程守护：实例异常退出自动重启（退避），崩溃计数与最近崩溃时间入库；管理进程重启后能恢复/接管既有实例。
- `FR-4.9` 可选增强（默认关，配置开启）：PID namespace（`unshare --pid --fork`）、实例 hostname（`<实例名>.<网关域名>`，默认开）。

### FR-5 可观测与运维

- `FR-5.1` 日志：每实例 stdout/stderr 落盘（含轮转/上限）；管理器与网关自身日志；审计日志（登录、增删改、启停）。
- `FR-5.2` 开机自启（OpenRC）：网关 + 管理器 + 需要常驻的实例；崩溃自愈。
- `FR-5.3` 自检脚本（可复跑的端到端验收）：未登录跳转、登录、代理、WebSocket 长连接、实例隔离、cgroup 限额、重启恢复。
- `FR-5.4` 升级路径：更新 `dsh` 版本 → 更新模板 → 批量升级实例（保留 `DSH_HOME` 与工作区）。
- `FR-5.5` 备份：`DSH_HOME` + 平台数据库 + 配置的一键打包/恢复。

## 4. 非功能需求

| 类别 | 要求 |
|---|---|
| 安全 | 网关自身会话与上游 cookie 分离；实例端口仅 loopback；jail 内非 root；jail 内不暴露宿主凭据；不记录明文密码/API key 到日志；管理接口仅 admin |
| 资源 | 默认配额：`cpu.max` 约 1 核、`memory.max` 1.5–2G、`pids.max` 256；全部可按实例调整 |
| 性能 | 网关每请求额外开销 ≤ 1 次回环子请求；WebSocket 全程直通不断流 |
| 规模 | 单机实例数目标见 §9 磁盘测算；架构上支持 10–50 实例 |
| 兼容 | Alpine 3.24 + OpenRC；DSH `0.2.0-rc.2`；DSH 升级不应要求改网关代码 |
| 可维护 | 单仓库、依赖尽量为零（优先 Node 内置模块）、有 README 与一键安装脚本 |

## 5. 架构选型（建议方案）

```
                   浏览器
                     │  http://dsh-mu/
                     ▼
        ┌─────────────────────────────────────────┐
        │ openresty :80                           │
        │  /login /logout /admin /assets → 控制面 │
        │  /  → auth_request + 变量化 proxy_pass   │
        └───────┬──────────────────────┬──────────┘
                │ 回环子请求            │ proxy_pass http://127.0.0.1:<实例端口>
                ▼                      ▼
   ┌────────────────────────┐   ┌──────────────────────────────┐
   │ 控制面 / 管理器 (Node) │   │ jail: <实例>                  │
   │  127.0.0.1:8787        │   │  mount ns + chroot + cgroup   │
   │  · 用户/会话/实例      │   │  rootfs(独立 apk)             │
   │  · 实例启停 + 日志     │   │  dsh web --host 127.0.0.1     │
   │  · 上游 cookie 代持    │   │          --port <port>        │
   │  · SQLite 状态         │   │          --trusted-host ...   │
   └────────────────────────┘   └──────────────────────────────┘
```

- **openresty**：对外 80；`auth_request` 调控制面的 `/internal/auth`，用 `auth_request_set` 拿到
  `X-DSH-Upstream`（如 `127.0.0.1:3101`）与 `X-DSH-Cookie`，再 `proxy_pass http://$upstream`。
  好处：复用安装文档已经验证过的 WebSocket / 超时 / 头部配置；动态上游**不需要 nginx reload**。
- **控制面 / 管理器**：单个 Node.js 进程（Node 24 内置 `node:sqlite`、`node:http`、`node:crypto`），
  **零 npm 依赖**，只依赖 `apk add nodejs`；同时提供管理 Web UI 与 JSON API。
- **jail runner**：一个 POSIX shell 脚本 + util-linux（`unshare`/`mount`/`chroot`/`setpriv`），
  或直接由 Node 调用这些外部命令；cgroup 放置由管理器在拿到子进程 PID 后写入 `cgroup.procs`。

备选方案（供对比，见待确认 Q1）：
- 纯 Node 单进程网关（含反向代理 + WS）：实现集中、但长连接/超时/大文件要自己保证。
- 纯 openresty + Lua：少一个进程，但用户/实例管理逻辑写在 Lua 里可维护性差。

## 8. 关键设计决策（需确认）

| 编号 | 决策点 | 建议 | 理由 |
|---|---|---|---|
| D1 | 架构 | openresty 反代 + Node 控制面 | 复用已验证的 WS/超时配置；动态上游免 reload |
| D2 | 上游 Host/Origin | 转发时重写为 loopback（`Host: 127.0.0.1:<port>`，`Origin` 同步） | 信任栅栏自动放行，实例无需 `--trusted-host`，且不依赖网关域名 |
| D3 | 去掉 token 的方式 | 网关代持 cookie（自动换取 + 401 重取） | DSH 无关闭鉴权开关；不改源码，升级安全 |
| D4 | 路由形式 | 会话决定后端，**不用路径前缀** | DSH 无可配置路径前缀，路径前缀会破坏 `/api`、`/plugins` 等绝对路径 |
| D5 | 实例端口 | 127.0.0.1 区间分配（默认 3100–3999） | 外部不可直连，绕过网关无门 |
| D6 | apk 隔离 | 每实例独立 rootfs + 独立 apk db | 满足"目录与 apk 安装环境隔离" |
| D7 | 网络隔离 | 不做 netns（共享宿主网络栈） | 用户明确要求"网络不严格隔离" |
| D8 | cgroup | v2 每实例一个子组，memory/cpu/pids 限额 | 用户明确要求 cgroup 封装 |

## 9. 磁盘与规模测算（待实测修正）

11.1G 可用空间下，单实例占用差异很大：

| 方案 | 单实例增量 | 可放实例数（留 20% 余量） |
|---|---|---|
| A. 每实例完整拷贝 rootfs（含 node + dsh 全局包 + profile 依赖） | 约 400–700 MB | 约 12–20 个 |
| B. 共享只读 DSH 运行时（bind 宿主 `/usr/local/lib/node_modules` + `node`），rootfs 只做拷贝 | 约 150–250 MB | 约 35–50 个 |
| C. overlayfs：共享只读 base + 每实例可写上层 | 约 50–120 MB | 更多，但 apk 与 bind 组合需额外验证 |

> 注：DSH 全局包 `@deepseek-ai/dsh` 依赖树非常大（数百个子包），是主要占用来源；「设置」里装插件还会往 `DSH_HOME/profiles/web` 再写一份依赖。

## 11. 验收标准

1. 匿名访问 `http://dsh-mu/` → 跳 `/login`；登录后 → 自己的 DSH UI 可用（对话、工具、插件）。
2. WebSocket `/api/remote.mux` 保持 ≥ 95s 不断（对齐安装文档的 soak 测试）。
3. 隔离验证：实例 A 内 `apk add` 某包 → 宿主与实例 B 无变化；实例内看不到宿主未绑定目录；实例内写不出去。
4. cgroup 验证：`memory.max` 触发 OOM、`pids.max` 触发 fork 失败、`cpu.max` 限速生效。
5. 交叉验证：用 A 的会话访问永远落到 A；A 的 cookie 无法命中 B。
6. 重启 `dsh-mu` → 网关/管理器/实例自动恢复；杀掉实例进程 → 自动重生且 cookie 仍有效（或网关自动重取）。
7. 审计日志可查到登录、增删改、启停记录。
