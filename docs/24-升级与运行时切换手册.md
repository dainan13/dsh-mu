# 24 · 升级与运行时切换手册（现场/离线都适用）

本文是一份**可照着做**的操作单：从 1.8.x/1.9.x 升到当前版本，并把实例切到新的运行时镜像。
每一步都写了"怎么验、失败了怎么办"。客户机可能**连不上外网**，所以文末有离线路径。

---

## 0. 先记住四条规则（这几轮踩坑换来的）

1. **装包 ≠ 生效**：`apk add` 只替换文件；进程还在跑旧代码。装完**必须**跑一次 `dsh-muctl sync`。
2. **改「默认运行时」不重启实例**（1.9.95 起）：它只改指针 + 重写各实例配置，返回
   `pending_restart`（哪些实例"重启后才生效"）。要真正切过去，由你决定何时重启。
3. **切默认 ≠ 切实例**：运行中的实例仍跑旧运行时；`dsh-muctl instance restart <name>`
   才会让它读新配置（每台 20–40 秒）。
4. **别让接口等长时间操作**：任何"跨多台实例"的动作都要拆成"改配置（秒级）+ 逐台重启（你做主）"。

## 1. 升级前（5 分钟）

```sh
# 1.1 记录现状（出问题时要靠它）
mkdir -p /root/pre-upgrade && cd /root/pre-upgrade
dsh-muctl --version > snapshot.txt
dsh-muctl runtime list >> snapshot.txt 2>&1
dsh-muctl doctor   >> snapshot.txt 2>&1
cp /etc/dsh-mu/dsh-mu.conf dsh-mu.conf.bak
tar czf etc-dsh-mu.tgz -C / etc/dsh-mu 2>/dev/null
for c in /etc/dsh-mu/instances/*.conf; do
  n=$(basename "$c" .conf); p=/var/lib/dsh-mu/instances/$n/home/.dsh/profiles/web/cordis.patch.yml
  [ -f "$p" ] && mkdir -p patches && cp "$p" patches/$n.patch.yml
done
ls -la; du -sh .

# 1.2 基线健康（升级后要逐项对比）
for c in /etc/dsh-mu/instances/*.conf; do
  n=$(basename "$c" .conf); P=$(grep -o 'PORT=[0-9]*' "$c" | cut -d= -f2)
  printf '  %-14s %s\n' "$n" "$(curl -s -o /dev/null -w '%{http_code}' --max-time 6 http://127.0.0.1:$P/)"
done
curl -sk -o /dev/null -w 'https %{http_code}\n' https://127.0.0.1/
df -h / /var | tail -2
```

**检查点**：所有实例应为 `401`；`https` 应为 `302`（开了 TLS 时）；磁盘至少留 **3 GB** 余量。

## 2. 装新版本（1 分钟 + sync）

```sh
apk add --allow-untrusted --force-overwrite /root/dsh-mu-<ver>-r0.apk
dsh-muctl --version            # 必须是新版本号
dsh-muctl sync                 # 重新渲染网关/实例配置，并重启 admin、重载网关
```

`sync` 会顺带做这些（都是幂等的）：补 node-pty、重挂运行时镜像、拉起 `dsh-mu-watchdog`、
对齐 admin/gateway 到新代码、应用 egress 表。

> **装完包 admin 暂时打不开？** apk 会把服务停掉，钩子只能在装完之后再拉起。
> 现在的钩子是"延迟 5 秒重启 admin/网关/watchdog"，正常装完就能用；
> 如果还是打不开，跑一次 `dsh-muctl sync`（它会检查并启动 dsh-mud），
> 或者等 ≤60 秒让 `dsh-mu-watchdog` 自动拉起。

**检查点**

```sh
dsh-muctl doctor                 # 期望 FAIL = 0；WARN 见第 6 节
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8787/ \
  -H "X-DSH-MU-Admin: $(cat /etc/dsh-mu/admin.token)"     # 期望 200
```

> 如果 doctor 出现 `admin backend: running the previous build` 或 `gateway lua: stale`，
> 再跑一次 `dsh-muctl sync` 即可（admin 那条已能自愈，gateway 那条靠这次 sync）。

## 2.5 用 `dsh-muctl upgrade` 一条命令升级（推荐）

以前升级是「`apk add` + 记得重启 admin + 记得重启实例」，任何一步漏了都会留下
「装完了但页面还是旧代码 / 实例还在跑旧文件」的假象（客户机上真实发生过）。

现在升级是一个带**预检 / 快照 / 验证 / 自动回滚**的动作：

```sh
# 1) 升级（失败会自动退回旧版本，并把原因写进 job 文件）
dsh-muctl upgrade /root/dsh-mu-1.9.132-r0.apk \
    --previous /root/dsh-mu-1.9.131-r0.apk

# 2) 只有"文件已新、进程仍旧"的实例才会被重启（可先预览）
dsh-muctl instance restart-stale --dry-run
dsh-muctl instance restart-stale --concurrency 3

# 3) 收尾体检（期望 0 WARN / 0 FAIL）
dsh-muctl doctor
```

**它每一步做什么**

| 阶段 | 内容 | 失败时 |
| --- | --- | --- |
| 预检 | apk 版本（apk v3 用 `apk adbdump` 读，不看文件名）/ 磁盘 ≥2GB / cgroup 可写 / doctor 无 FAIL | **直接中止，不安装** |
| 快照 | `records + 配置 + secrets + tls` → `/var/backups/dsh-mu-upgrade-<时间>.tgz` | 中止，不安装 |
| 安装 | `apk add --allow-untrusted --force-overwrite` | 报错并留输出 |
| 接管 | `zap` 旧 supervisor → 清掉占着 admin 端口的旧进程 → `start` | 继续验证 |
| 验证 | ① `VERSION` 文件 ② admin `/api/health.version`（**进程自报，权威**）③ 每个 running 实例端口 ④ 漂移统计 | 进入回滚 |
| 回滚 | `apk del` + `apk add <旧包>`（这个 apk 没有 `--force-downgrade`）→ 恢复快照 → 杀残留 supervisor/端口 → `start` 重试两次 | 报"回滚未成功"并给快照路径 |

**看进度 / 看结果**

```sh
cat /run/dsh-mu/upgrade-job.json          # {ok, phase, steps[], rolled_back, drift[]}
dsh-muctl upgrade ... --verify-timeout 40 # 缩短验证等待（默认 120 秒）
```

**回滚窗口（必须提前告知用户）**

```
坏包的情况下，回滚期间（约 1–2 分钟）admin 页面是不可用的 ✗
这是坏包本身的必然，不是升级工具的缺陷 ✓
实例不受影响（它们跑在 jail 里，且升级不重启实例）✓
```

**为什么还需要 `restart-stale`**

升级会更新实例"看得见"的三类文件，但**故意不重启实例**：

| 文件 | 谁更新 | 不重启会怎样 |
| --- | --- | --- |
| `/opt/dsh-mu-plugins/*`（内置插件，只读挂载） | apk 覆盖 | 进程还用旧代码 |
| `/opt/dsh-mu-probe/*`（崩溃探针） | apk 覆盖 | 新探针不生效 |
| `profiles/*/cordis.patch.yml`、`.dsh-mu-provider.yml` | `sync` 重渲染 | 计划/模型改动不生效 |

`instance restart-stale` 的判据是「文件 mtime > 进程启动时间」，不是端口归属 ——
实例的运行时来自只读镜像（内容寻址），版本从挂载就能读出来，不存在"旧代码还在跑"的问题。

## 3. 装运行时镜像

### 3.1 有外网（推荐）

admin → 供给 → 运行时 → 「读取线上版本」→ 找到目标版本 → **下载**（有进度、可看速度）。

### 3.2 没有外网（离线客户机）

```sh
# 在能上网的机器上下载，然后 SFTP/USB 拷到客户机
scp dsh-<id>.squashfs root@<客户机>:/root/
```
admin → 运行时 → **上传镜像**（弹窗有进度/预计剩余/可取消；上传中不能误关）。

### 3.3 从"旧的 npm 树"打包成本地镜像（老机器专用）

```sh
dsh-muctl runtime pack 0.2.1-rc.5      # 产物 id: 0.2.1-rc.5-local-<sha6>
```
适合"不想依赖外网、也不想改变现有内容"的场景；打包会临时占用约 600 MB（用完自行清理）。

**检查点**：`dsh-muctl runtime list` 里出现该 id，模式 `mounted`，大小 ≈ 95–105 MB。

## 4. 切换实例的运行时（关键步骤）

```sh
# 4.1 先做 canary：只切一台
dsh-muctl instance restart <canary>       # 或 admin 实例页「修改配置」里指定运行时
# 4.2 真实验证这一台：登录 → 发一条消息 → 打开终端（pty）
# 4.3 再把默认指向新镜像（**不会重启任何实例**）
dsh-muctl runtime use <new-id>            # 或 admin 运行时页「设为默认」
# 4.4 按窗口逐台重启（每台 20–40 秒，用户掉线重连，数据不丢）
for n in $(ls /etc/dsh-mu/instances | sed 's/\.conf$//'); do
  dsh-muctl instance restart "$n"
done
```

**检查点**

```sh
dsh-muctl runtime status                  # configured = 新 id
for c in /etc/dsh-mu/instances/*.conf; do
  n=$(basename "$c" .conf); P=$(grep -o 'PORT=[0-9]*' "$c" | cut -d= -f2)
  printf '  %-14s %s\n' "$n" "$(curl -s -o /dev/null -w '%{http_code}' --max-time 6 http://127.0.0.1:$P/)"
done
dsh-muctl doctor | tail -2
```

## 5. 清理旧运行时（**确认之后再删**）

```sh
# 5.1 确认没有实例还指向旧树
grep -l 'gateway/rootfs/usr/local/lib/node_modules' /etc/dsh-mu/instances/*.conf || echo "no legacy refs"
# 5.2 确认都在跑镜像
dsh-muctl runtime status | head -3
# 5.3 删除（旧的 npm 树，约 830 MB）
rm -rf /var/lib/dsh-mu/gateway/rootfs/usr/local/lib/node_modules/@deepseek-ai
# 5.4 同步 DSH 版本号，避免 doctor 报版本不一致
dsh-muctl config dsh_version <new-dsh-ver> && dsh-muctl sync
```

> 想留回滚点就先别删（占 830 MB，不算多）；stable 跑 2–3 天再删更稳。

## 6. doctor 常见 WARN 的含义

| WARN | 含义 | 处理 |
| --- | --- | --- |
| `instance patch freshness: stale: …` | 实例启动后 patch 被改过（升级常见） | 下次重启自然消失；急就 `instance restart` |
| `instance supervision: N 个实例没有 supervisor` | openrc 的守护进程溜了 | 有 `dsh-mu-watchdog` 时这条会变 PASS（60 秒兜底）；没有就 `dsh-muctl sync` |
| `egress rules: no table` | 没有需要限制的实例 | 新版本已改为 PASS |
| `runtime: 使用旧的 npm 树` | 还在用 1.8.x 的 npm 树 | 按第 3 节固化成镜像 |

## 6.5 实例"启动着但端口不通"（bundle 解析失败）

典型日志（`/var/log/dsh-mu/<name>.err.log`）：

```
dsh: skipping profile bundle "@dsh-mu/dsh-client-models": Error:
     cannot resolve profile bundle ... from the dsh installation or
     /home/dsh/.dsh/profiles/web; run 'dsh plugin --profile web install' ...
```

原因：平台把内置插件放进 `node_modules` 和 `bundles`，却**没写进 dependencies**；
用户在实例里装插件触发 `pnpm install` 时，pnpm 把它当"多余包"挪进
`node_modules/.ignored/`，DSH 启动时解析失败 → 在绑定端口前退出（端口一直 000）。

处理：

```sh
dsh-muctl instance-repair <name> --restart   # 重新落内置插件 + 清 .ignored + 重启
```

平台侧已修（1.9.100）：内置插件现在声明为 `file:/opt/dsh-mu-plugins/<name>`
（jail 里只读挂载），pnpm 不会再删它们；`doctor` 也新增 `profile bundles` 检查。
**若某个用户插件已经被删除**，需要用户重新安装那一个插件（`instance-repair` 不动它）。

## 7. 出问题怎么退

| 场景 | 处理 |
| --- | --- |
| 新版本有问题（平台层） | `apk add --force-overwrite` 旧 apk → `dsh-muctl sync` → `dsh-muctl doctor` |
| 实例起不来（运行时层） | `dsh-muctl runtime use <旧 id>`（不重启）→ `dsh-muctl instance restart <name>` |
| 配置写坏了 | `tar xzf /root/pre-upgrade/etc-dsh-mu.tgz -C /` → `rc-service dsh-mud restart` → `dsh-muctl sync` |
| 单台实例瘫痪 | `dsh-muctl instance restart <name>`；看 `/var/log/dsh-mu/<name>.err.log` |
| 实例全都 000（端口不通）| 先看 `dsh-mu-cgroup` 是否被重启过（会清掉实例 cgroup）；`dsh-muctl sync` + 等 watchdog 一轮 |
| admin 页面 502 / 打不开 | `rc-service dsh-mud status`；停了就 `dsh-muctl sync`（会自动拉起）|

## 8. 一页速查（复制粘贴版）

```sh
# 备份
mkdir -p /root/pre-upgrade && tar czf /root/pre-upgrade/etc.tgz -C / etc/dsh-mu
# 升级
apk add --allow-untrusted --force-overwrite /root/dsh-mu-<ver>-r0.apk
dsh-muctl sync && dsh-muctl doctor | tail -2
# 装镜像（有网：admin 读取线上版本；没网：admin 上传镜像）
# 切默认（不重启）→ 逐台重启 → 校验
dsh-muctl runtime use <id>
for n in $(ls /etc/dsh-mu/instances | sed 's/\.conf$//'); do dsh-muctl instance restart "$n"; done
dsh-muctl doctor | tail -2
# 清理旧树（确认后）
grep -l 'gateway/rootfs/usr/local/lib/node_modules' /etc/dsh-mu/instances/*.conf || \
  rm -rf /var/lib/dsh-mu/gateway/rootfs/usr/local/lib/node_modules/@deepseek-ai
```

## 9. 附：这轮新增的两个保障

- **`dsh-mu-watchdog`**：每 60 秒扫一遍"应该跑但端口不通"的实例并重启它。
  openrc 的 `supervise-daemon` 有时会自己退出（表现为 `rc-service status` 显示 `unsupervised`），
  有 watchdog 后自愈不再依赖 openrc。手动跑一次：`dsh-muctl watchdog --once --dry-run`。
- **「设为默认」不再重启实例**：返回 `pending_restart` 列表；批量切换由你决定时机。

### 2.6 自测（不需要运行中的平台）

```sh
dsh-muctl selftest --unit        # 21 项纯函数检查，1 秒内跑完
```

覆盖：配置项说明完整性、doctor 人话词表、`/proc` 进程启动时间、drift 判据（含"未来时间戳"
与"装包晚于启动"）、cell 判活、restart job 文件读写。改完代码先跑它，能挡住大部分低级错误。

### 运行时镜像的挂载方式（1.9.202 起自动选择）

```
特权容器 / 裸机（有 loop）   → 直接挂 squashfs（零解压，最快）
非特权容器（无 loop，有 fuse）→ 随包 squashfuse（不依赖 loop，只需 /dev/fuse）
两者都没有                   → unsquashfs 解压成目录（可用，但每次升级运行时都要解压）
```

查看本机用的是哪种：`dsh-muctl runtime-mount-test`（doctor 里也有「运行时挂载方式」一条）。
非特权容器请确保 `/dev/fuse` 可用（PVE：容器 → 选项 → 功能 → 勾选 FUSE）。
