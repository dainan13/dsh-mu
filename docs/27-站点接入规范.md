# 27 · 站点（site）接入规范

状态：**评审稿 v1**（2026-11-21）　适用范围：给 dsh-mu 写扩展、并希望对外提供 HTTP 服务的人

本文定义 dsh-mu 里的一个抽象：**站点（site）**。
站点不是 nginx 的 `server` 块本身，而是"**挂在 dsh-mu 体系下的一个 HTTP 服务集合**"：
它有入口、有身份、有它能碰的数据范围、有出口、有生命周期。

> 与 `docs/18`（jail/socket/egress/token）和 `docs/21`（扩展页面形态 ext-ui）的关系：
> 18 号管"扩展怎么被跑起来"，21 号管"扩展的页面长什么样"，本文管"扩展怎么对外提供 HTTP 服务"。

---

## 1. 定义与边界

一个站点必须同时满足：

| 条件 | 说明 |
|---|---|
| **是 HTTP 服务** | 非 HTTP（纯 socket RPC、定时任务）不归本文管 |
| **跑在 dsh-mu 这台机器上** | 跑在别处的服务不归本文管（那是外链） |
| **由 dsh-mu 的 gateway 对外** | 用户访问的一定是 gateway；这样"停用即断"才成立 |
| **处理者是某个扩展** | 站点属于某个扩展包，随扩展安装/升级/卸载 |

### 1.1 谁管什么（这是全文最重要的一张表）

| 事项 | dsh-mu（平台） | 扩展 |
|---|---|---|
| 入口路径 / 域名 | ✅ 分配、可改、可迁移 | ❌ 只能给"偏好"，平台可无视 |
| 监听端口 / socket 路径 | ✅ 指定（由平台建目录） | ❌ 不得自选对外端口 |
| 对外 TLS | ✅ gateway 统一终止 | ❌ |
| 身份识别（是谁） | ✅ 会话/令牌/外部断言 | ❌ 不得自己解析 cookie |
| 租户（哪个实例） | ✅ 注入 `X-DSH-MU-Tenant` | ✅ 按该值拼路径（契约） |
| 请求体大小 / 超时 | ✅ 站点字段声明，平台渲染 | ❌ |
| 内容、业务逻辑 | ❌ | ✅ |
| 站点内部权限（谁能看哪个文件） | ❌ 只给租户边界 | ✅ 在边界内自决 |
| 出网策略 | ✅ 按站点声明渲染 | ❌ 声明需求 |
| 审计事件 | ✅ 记录 | ✅ 可补充业务事件 |
| 启停 | ✅ 一条命令立刻生效 | ❌ 不能绕过平台自启 |

## 2. 两类站点（最终都收敛成"一个 unix socket 上游"）

### 2.1 `socket` 型（默认，推荐）

扩展自己写 HTTP 服务进程，监听 **unix socket**；gateway `proxy_pass` 过去。

```
用户 → gateway(80/443) → /s/<site>/ → unix:/run/dsh-mu/sites/<site>/upstream.sock → 扩展进程
```

- 控制力最强：停用 = 不渲染 location + 关 socket（立刻断）
- 不占端口、不出现在 `ss -ltn`、容器外不可达
- 扩展可以用任何语言写（Python/Go/Node…）

### 2.2 `nginx` 型（可选，需要运维显式批准）

扩展提供一段 **nginx 配置**（真正的 nginx site），由平台编译成一个**独立的 server 块**，
监听一个由平台分配的 unix socket；主 gateway 仍然 `proxy_pass` 到那个 socket。

```
用户 → gateway → /s/<site>/ → unix:/run/dsh-mu/sites/<site>/nginx.sock
                                   ↑ 这一段是 openresty 自己跑的独立 server{}
```

为什么这样设计而不是"把扩展的配置直接拼进主 server"：

```
· 一个坏指令只影响该站点自己的 server 块，不会把整个 gateway 弄挂
· 仍能在 include 前用 nginx -t 校验；校验失败 → 保留上一版（last-good）并报错
· 入口、身份、strip 仍由主 gateway 统一处理（扩展拿不到入口定义权）
· 停用 = 移除 include + reload + socket 消失
```

`nginx` 型的限制（写进校验器）：

```
禁止：load_module / env / daemon / user / worker_* / include（任意路径）
禁止：listen（平台注入）/ server_name（平台注入）
允许：location / proxy_pass / try_files / rewrite / return / add_header / auth_basic /
      client_max_body_size / expires / gzip 等"站点内"指令
允许（需显式批准）：content_by_lua_file 等 lua_*（见 §2.3）
路径：只能引用 /etc/dsh-mu-gateway/ext/<site>/ 与其 mounts 目标
```

### 2.3 关于"扩展 Lua 运行在网关进程内"（2026-11-24 决议）

`nginx` 型站点要支持 WebDAV 这类需要 Lua 的协议，就必然让**扩展的代码**跑在
dsh-mu 的 openresty 里。这是有代价的，必须显式批准：

| 后果 | 说明 |
|---|---|
| 无 jail 隔离 | 扩展 Lua 与网关同进程/同权限，不再受 jail 约束 |
| 能看到 mounts 目录 | 声明了 `instances` 就会看到**所有租户**的 home/workspace |
| 可能影响网关 | 死循环/大内存会拖垮 worker；配置语法错误由 nginx -t 拦截 |

因此：

```
site.nginx.requires_approval: true  → site sync 后站点是"待批准"状态（入口 503）
dsh-muctl site approve <name>       → 运维显式批准，页面/CLI/doctor 都记录
```

批准前：不落任何扩展配置、不加载扩展 Lua、入口返回 503 并提示如何批准。
批准后：平台把 `site.conf` 编译成独立 `server{}`（监听 `/run/dsh-mu/sites/<site>/nginx.sock`），
主 gateway 仍负责入口/身份/令牌/只读/停用。

> 结论：`socket` 型覆盖 90% 需求；`nginx` 型给"需要 nginx 特性且不想自己写服务"的扩展。
> 两者对上游的契约**完全一致**（见第 5 节），所以扩展可以先用 nginx 型起步，后续换成 socket 型。

## 3. manifest 字段（完整契约）

```jsonc
{
  "name": "dav-ext",
  "version": "1.0.0",

  "site": {
    "name": "dav",                  // 稳定标识：^[a-z][a-z0-9-]{1,30}$，不参与 URL
    "label": "文件访问",
    "kind": "socket",               // socket | nginx

    "socket": {                     // kind=socket 时必填
      "path": "api.sock",           // 相对扩展 api 目录；平台建目录并 rw 挂进扩展 jail
      "strip": true,                // true：上游收到去掉入口前缀后的路径
      "timeouts": { "connect": 10, "read": 300 },
      "body_limit": "512m"
    },

    "nginx": {                      // kind=nginx 时必填
      "file": "site.conf",          // 相对扩展目录；平台读取、校验、编译成 server{}
      "requires_approval": true     // 安装/升级时不自动启用，需运维在页面确认
    },

    "entry": {                      // 入口"偏好"，平台可覆盖（见第 4 节）
      "prefer_path": "/files/",     // 必须带首尾斜杠；平台可能拒绝或改写
      "prefer_host": null           // 例如 "files.corp.example"
    },

    "auth": {
      "mode": "platform",           // platform | external | both | none
      "session": true,              // 接受平台会话 cookie
      "token": {
        "enabled": true,
        "formats": ["basic", "bearer"],
        "scopes": ["ro", "rw"]      // 站点支持哪些令牌粒度
      },
      "pass_authorization": false,   // 是否把原始 Authorization 透给上游
      "anonymous": false            // true 仅建议用于 "health" 之类
    },

    "scope": {
      "tenant": "instance",         // instance | site | none —— 决定 X-DSH-MU-Tenant 怎么来
      "readonly": false             // 站点整体只读（令牌 rw 也会被降级）
    },

    "mounts": [                     // 站点进程能看到的宿主目录
      { "source": "instances", "target": "/tenants", "mode": "rw" }
    ],

    "egress": [],                   // 站点进程能否主动出网（默认全拒）；填 CIDR

    "health": { "path": "/health", "expect": 200, "timeout": 3 },

    "audit": { "requests": "all" }  // all | mutations | none
  }
}
```

字段级说明（评审重点）：

| 字段 | 谁写 | 谁读 | 缺省 | 说明 |
|---|---|---|---|---|
| `site.name` | 扩展 | 平台 | 必填 | 全局唯一；冲突 → 平台拒装（不静默改名） |
| `site.kind` | 扩展 | 平台 | `socket` | `nginx` 需运维批准 |
| `socket.path` | 扩展 | 平台 | `api.sock` | 只允许相对文件名，禁止 `/` 与 `..` |
| `socket.strip` | 扩展 | gateway | `true` | 见 §5.1 |
| `entry.prefer_path` | 扩展 | 平台 | 无 | 仅"偏好"，平台分配算法见 §4 |
| `entry.prefer_host` | 扩展 | 平台 | 无 | 域名入口需运维确认（涉及 DNS） |
| `auth.mode` | 扩展 | 平台 | `platform` | 见 §6 |
| `auth.token.scopes` | 扩展 | 平台 | `["rw"]` | 平台只签发其中列出的粒度 |
| `scope.tenant` | 扩展 | 平台 | `instance` | 决定 `X-DSH-MU-Tenant` 来源 |
| `mounts` | 扩展 | 平台 | `[]` | 安装时展示给人看；越界路径直接拒装 |
| `egress` | 扩展 | 平台 | `[]` | 与现有 `net.egress` 合并（站点级更细） |
| `audit.requests` | 扩展 | 平台 | `mutations` | `all` 会给磁盘带来压力 |

## 4. 平台注册表与入口分配（"动态允许"的落地）

### 4.1 注册表在平台状态里，不在扩展里

```jsonc
// /var/lib/dsh-mu/state.json → sites{}
"sites": {
  "dav": {
    "extension": "dav-ext",
    "kind": "socket",
    "enabled": true,
    "entry": { "path": "/s/dav/", "host": null, "strip": true },
    "assigned_by": "platform",        // platform | operator
    "preference": "/files/",          // 记录扩展的偏好，仅作展示
    "auth": { "mode": "platform", "token": {"enabled": true, "scopes": ["ro","rw"]} },
    "mounts": [{ "source": "instances", "target": "/tenants", "mode": "rw" }],
    "egress": [],
    "created_at": 0, "updated_at": 0
  }
}
```

### 4.2 入口分配算法（扩展只说"我是谁"，平台决定"我在哪"）

```
1. 取站点名 → 规范化（小写、非 [a-z0-9-] 替换为 -）→ slug
2. 基础前缀 sites.base_path（平台配置，默认 /s/）→ 候选 /s/<slug>/
3. 若扩展给了 prefer_path 且通过保留表校验且不冲突 → 采用（assigned_by=platform,
   preference_respected=true）
4. 冲突则追加 -2 / -3 …（不覆盖别人的入口）
5. 任一情况下都写入注册表，页面显示"实际入口"，可随时改成任意合法路径
   （assigned_by=operator，之后不会被自动算法覆盖）
6. 域名入口：prefer_host 或运维手工指定；需 DNS 指向本机 + 页面确认
```

**保留命名空间（不可占用）**：

```
/  /admin  /login  /logout  /me  /mu-api/  /mu-internal/  /mu-static/
/ext/  /ext-api/  /__search  /s/（本身）  /dav/（历史保留，避免与未来平台功能撞）
```

冲突、越界、正则注入（路径里出现 `{}` `~` `\`）→ **拒装/拒改并明确报错**，不静默跳过。

### 4.3 入口迁移（不断会话）

```
dsh-muctl site set dav --path /files/
  → 写入新入口，同时保留旧入口 300 秒（双前缀窗口）
  → gateway reload
  → 300 秒后自动移除旧前缀（或 `site prune dav` 立刻移除）
页面提示："旧地址 5 分钟后失效"
```

## 5. proxy_pass 契约（反驳① 的落地：怎么把"真实域名与路径"传给上游）

### 5.1 路径语义

```
strip=true （默认）
  用户请求  https://host/s/dav/a/b?x=1
  上游收到  GET /a/b?x=1
  头部      X-Forwarded-Prefix: /s/dav/
            X-Original-URI:     /s/dav/a/b?x=1

strip=false
  上游收到  GET /s/dav/a/b?x=1   （上游自己认得前缀）
```

> 上游生成自引用 URL（WebDAV 的 `href`、重定向、`Location`）时必须用
> `X-Forwarded-Prefix` + `X-Forwarded-Host` + `X-Forwarded-Proto` 拼，**不能用自己看到的路径**。

### 5.2 平台注入的请求头（全部覆盖写，入站的同名头一律先清掉）

| 头 | 示例 | 说明 |
|---|---|---|
| `X-Forwarded-Proto` | `https` | 用户侧真实协议 |
| `X-Forwarded-Host` | `dsh.example.com` | 用户侧 Host（域名入口时是站点自己的域名）|
| `X-Forwarded-Prefix` | `/s/dav/` | 被剥掉的入口前缀（可能为空）|
| `X-Original-URI` | `/s/dav/a/b?x=1` | 原始 URI（含前缀与查询串）|
| `X-DSH-MU-Site` | `dav` | 站点名 |
| `X-DSH-MU-Principal` | `alice` | 身份（见 §6）|
| `X-DSH-MU-Tenant` | `pppsss` | 租户（实例名；`scope.tenant=none` 时为空）|
| `X-DSH-MU-Scopes` | `rw` 或 `ro` | 令牌粒度 |
| `X-DSH-MU-Verified-By` | `platform` / `external` | 身份来源，站点据此决定信任级别 |
| `X-DSH-MU-Request-Id` | 随机串 | 与审计事件关联 |

**上游必须做到**：
1. 只信任来自 socket 的这些头（不要在 jail 内再监听 TCP 让外界直连）；
2. 用 `X-DSH-MU-Tenant` 拼数据路径，**不得**从请求路径反推租户；
3. 自引用 URL 用 `X-Forwarded-*`（§5.1）。

## 6. 身份与会话契约

### 6.1 三种模式

| mode | 谁认证 | 平台做什么 | 典型场景 |
|---|---|---|---|
| `platform` | dsh-mu | 校验会话 cookie 或站点令牌 → 注入身份 | 客户只有 dsh-mu（场景一）|
| `external` | 上游/外部 IdP | 校验外部断言（受信头或 OIDC）→ 映射成 Principal | 客户有自己的内网系统（场景二）|
| `both` | 两者 | 有外部身份用外部，否则回落平台 | 迁移期 |
| `none` | 不认证 | 只放行 health | 公开页面（谨慎）|

### 6.2 平台侧认证流程（gateway 内，一次 subrequest）

```
请求进来
  ├─ 若 mode ∈ {platform, both} 且带 Cookie  →  admin 会话校验（现状逻辑）
  ├─ 若带 Authorization                      →  /mu-internal/site/verify
  │     · Basic: 用户名=令牌（或 user:token），密码可空
  │     · Bearer: 令牌
  │     → 200：返回 principal/tenant/scopes/token_id
  ├─ 若 mode ∈ {external, both} 且有受信外部头 → 直接采用（来源 IP 白名单 + 头名可配）
  └─ 都失败 → 401（带 WWW-Authenticate，Basic 或 Bearer，按站点支持列表）
```

令牌细节：

```
存储：state.db  dav_tokens(id, site, user, tenant, scope, hash, label,
                          created_at, last_used_at, revoked_at)
签发：dsh-muctl site token dav create --tenant pppsss --readonly --label windows
撤销：dsh-muctl site token <站点> revoke --id <id>      → 下一次请求即失效（无缓存或 ≤5s 缓存）
粒度：scope=ro 时，网关直接拒绝非安全方法（PUT/DELETE/MKCOL/MOVE/COPY/LOCK/PROPPATCH…）
     → 站点写没写对都不影响这条边界
```

### 6.3 站点的"自己的协议"怎么办

```
· 站点若需要与客户端用某种协议（WebDAV Basic、OAuth…）：
  默认平台**不透传** Authorization 给上游（pass_authorization=false），
  上游只看到 X-DSH-MU-*（已经解析好的身份）；
  若站点确实需要原始凭证（例如自己要再向外部系统换取令牌），
  显式声明 pass_authorization=true，平台才转发（并在审计里标记）✓
· 站点不得自己实现登录页（那会绕开平台的会话体系）；
  需要登录态就用平台会话或令牌 —— 这也保证"停用一个站点"不会留下孤儿会话
```

## 7. 出口（egress）

**这不是站点新引入的限制**：扩展本来就在 jail 里跑，防火墙链由
`render_ext_egress()` 生成——默认全拒，只放行 manifest `net.egress` 里声明的 CIDR
（`docs/18` §3）。站点只是继承这条既有策略：

```
站点进程的出网许可 = 所属扩展的 net.egress（继承）
  站点可以**收窄**（site.egress 子集），不能扩大到扩展没声明的范围
例：WebDAV 站点 → 继承 []         （只被访问，不出网）
    同步型站点 → 继承 ["10.0.0.0/8"]（要访问内网某 API）
```

为什么默认全拒（三条理由，与"是否信任扩展作者"无关）：

```
1. 小团队离线优先：绝大多数部署没有出网条件，默认放行会掩盖"某个扩展偷偷依赖公网"
2. 供应链：扩展被替换/写坏时，没有出网通道就没有外传路径
3. 可审计：每个扩展/站点能连哪里写在 manifest 里，出问题时一眼能查
```

> 注意区分两件事：**扩展进程出网**（本节，受控）与 **gateway 的 proxy_pass**
> （只连本机 unix socket，结构上不存在"被当成代理"的可能）。

events                             site.request / site.enabled / site.disabled / site.token.created

## 9. 渲染与校验

```
sync 时：
  1. 读注册表 → 逐站点校验（字段、入口、保留表、冲突、kind 与字段匹配）
  2. 渲染 gateway 片段 sites.d/<name>.conf（或 server 块）
  3. 校验不通过的站点：不渲染 + doctor FAIL（写明原因），旧版本保留（last-good）
  4. 所有片段渲染完 → nginx -t（chroot 内）→ 通过才 SIGHUP；不通过 → 回滚并报错
```

启停语义：

```
site disable <name>
  → 注册表 enabled=false → 渲染为 503 提示页（不删数据）
  → 若 kind=socket：断开/移除 socket 目录（连接直接 refused）
site enable <name>   反向操作
site uninstall <name> 移除注册表 + include + socket 目录（扩展数据保留）
```

## 10. 与"运行时内嵌站点"的区别（将来的形态 2）

```
本文的站点：独立进程，服务多实例/多用户 → 必须靠 X-DSH-MU-* 传递身份（C 形态）
运行时内嵌：进程跑在某个实例 jail 里，天然只有一个实例 → 不需要身份头（A 形态）
后者属于"运行时能力"（例如实例内的文件浏览器），不在本文范围；
两者共享同一条 gateway 入口规则与审计格式。
```

## 13.1 决议（2026-11-23）：WebDAV 走 Lua，不改 openresty

原计划 a（给 openresty 编 `nginx-dav-ext-module`）的成本：

```
· 需要与 rootfs 里 openresty **同版本**的源码重新编译（版本/ABI 必须对齐）
· 需要 rootfs 补 expat（库 + 头文件）
· .so 是架构相关的 → 进 apk，且**每次 openresty 升级都要重编**；错一步网关起不来
```

改为 b：**只用 openresty 现有能力**，PROPFIND/PROPPATCH/LOCK/UNLOCK 用 Lua 实现
（`gateway/lua/dav.lua`），写方法与读方法都在同一个 `content_by_lua_file` 里。

```
· 零新增二进制、零构建改动 → 随 apk 升级即可
· 站点类型新增 kind=dav（平台内置，不需要扩展进程）
· 数据根：/var/lib/dsh-mu/instances/<tenant>/home（租户来自 X-DSH-MU-Tenant）
· 锁表放 lua_shared_dict davlocks（假锁，够 Windows 资源管理器；不做互斥语义）
· 身份/只读仍由 site.lua 先完成（scope=ro 的写请求到不了 dav.lua）
```

用法（内置 DAV 站点示例，manifest 见 `extensions/ext-dav/manifest-builtin.json`）：

```sh
mkdir -p /usr/share/dsh-mu/extensions/ext-dav-builtin
cp extensions/ext-dav/manifest-builtin.json \
   /usr/share/dsh-mu/extensions/ext-dav-builtin/manifest.json
dsh-muctl site sync            # 平台分配入口（如 /s/files/），并把实例目录挂进网关 jail
dsh-muctl site token files create --subject svc:me --tenant <实例> --label win
# Windows：映射网络驱动器 → http://<主机>/s/files/
```

**扩展只能使用现有能力**：不提供"往 openresty 里塞第三方模块"的通道；
需要新协议时，要么用 Lua/现成模块，要么走 socket 型站点自己做。

## 14. 控制边界与已知缺口（2026-11-21 决议）

### 14.1 平台到底"强制执行"了什么

| 控制点 | 强制手段 | 效果 |
|---|---|---|
| 入口 | 平台分配并渲染 gateway location | 用户访问的一定是 gateway；扩展无入口定义权 |
| 上游可达性 | 只给扩展一个 socket 目录，且不挂进实例 | 外界无法直接从网络到达扩展 socket |
| 身份 | `X-DSH-MU-*` 由 gateway 覆盖写 | 扩展看到的身份一定是平台验过的；客户端伪造无效 |
| 停用 | 不渲染 location / 渲染 503 | 立刻断，扩展无法自恢复 |
| 只读 | 网关按 scope 拒绝写方法 | 与扩展实现无关 |

### 14.2 扩展自己做认证：允许，但只能是"附加"

```
扩展可以在自己的服务里再立一道门（自己的 cookie / token / header）。
平台不阻止，因为：
  · 那是"更严"，不是"更松"；平台拒绝的请求到不了扩展
  · 但扩展**不能**用自建认证替代平台认证，除非站点显式声明 anonymous（本版不做）
```

### 14.3 已知缺口：扩展自开端口可绕过 gateway（**本轮明确不补**）

```
现状：nftables 只有 egress 链；jail 共享宿主网络栈 → 扩展或实例若 bind 0.0.0.0:<port>，
      局域网可直连，绕过认证/审计/停用。
决定（2026-11-21）：**暂不补**。理由：客户需求多样，先信任扩展；
      需要"匿名访问"等场景时，反而可以利用这个通道（不属本文契约，风险自负）。
将来若补：ingress 白名单（默认 gateway-only：放行 80/443/22 + loopback，其余 DROP）
      + doctor 检查"非 loopback 监听"。已记入 docs/26 长期项。
```

### 14.4 匿名访问：本版不做

```
site.auth.anonymous 字段保留但**不实现**（v1 若设置会告警并回落到 platform）。
理由：没有真实需求时少开口子；将来做时按 §14.5 的"能力 URL"优先。
```

### 14.5 将来的"分享"更推荐能力 URL

```
/s/<site>/share/<32 位随机串>/…   随机路径即凭证：可过期、可撤销、天然只读
实现成本低（平台已有 random_hex），比 anonymous 更可控。
```

| # | 决议 | 说明 |
|---|---|---|
| 1 | **v1 只做 `socket` 型**；同时交付一个参考实现扩展（`ext-test-site`）供验收 | nginx 型放到第二步；WebDAV 按"两阶段"落地（见 §13）|

## 13. WebDAV 的技术前提（第二步的关键事实）

实测本机 openresty：

```
nginx -V → --with-http_dav_module  ✓
            --with-http_auth_request_module ✓
            --with-http_realip_module ✓
```

含义（必须说清，否则会误判工作量）：

```
nginx 自带的 dav 模块只提供写方法：PUT / DELETE / MKCOL / COPY / MOVE
它**不提供** PROPFIND / PROPPATCH / LOCK / UNLOCK ✗
而 Windows「映射网络驱动器」和 macOS Finder 都依赖 PROPFIND（列目录）与 LOCK ✗

所以"WebDAV 挂在 openresty 上"有两条可行路线：
  a) 给 openresty 加 nginx-dav-ext-module（补 PROPFIND/LOCK）→ 需要我们自己编这个模块，
     并把它加进网关的 openresty 构建
  b) 用 Lua 实现 PROPFIND/LOCK（其余写方法交给 dav 模块）→ 不用改构建，但 XML 生成与
     目录遍历要做对（工作量 1–2 天，性能中等）

两阶段计划：
  第一步（本规范 v1）：socket 型站点跑通 → 用 Python(wsgidav 或自写 200 行)做 DAV 验收
  第二步：把该用例迁到 openresty（a 或 b），届时再评估"站点进程"是否还需要
